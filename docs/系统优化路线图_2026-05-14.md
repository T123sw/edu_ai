## 一、当前状态（已完成）

### 1.1 已完成的改造

**异步后台任务 — Chat Stream 路径（P0-A，2026-05-14）**

- 新增 `app/chat/tasks/task_store.py`：线程安全任务状态存储，TTL 1小时自动清理
- 新增 `app/chat/tasks/background_runner.py`：daemon 线程执行 workflow，完成后回调持久化
- `MainOrchestrator.dispatch_stream()`：workflow 路径不再同步阻塞，立即返回 `task_submitted` 事件
- `ReplyServiceV2.reply_stream()`：传递 `on_workflow_complete` 回调，后台任务完成时自动写库
- `routes.py`：新增 `GET /api/chat/tasks/{task_id}` 查询接口
- 前端 `chatV2.ts`：支持 `task_submitted` 事件类型，新增 `pollChatTask()` 函数
- 前端 `ChatPanel.tsx`：`backgroundTaskId` state + 独立 useEffect 轮询，`isLoading` SSE 结束后立即释放

**效果**：通过 Chat Stream 触发的报告/PPT/教案/练习题生成不再阻塞对话界面，用户等待期间可继续发消息。

### 1.2 已知技术债

| 问题 | 位置 | 影响 |
|------|------|------|
| 任务存储为进程内 dict | `task_store.py` | 进程重启后任务状态丢失，多 worker 进程间不共享 |
| 双路由并存 | `/api/chat/stream` 旧 vs `/api/chat/v2/stream` 新 | 维护负担，后续只维护 v2 |
| 任务失败无重试机制 | `background_runner.py` | 用户看到失败只能重发 |
| PPT 依赖 html2ppt 外部进程 | `PptWorkflowRuntime` | 故障点多，超时管理缺失 |
| `ppt/outline` 仍同步 | `routes_v2.py` | 大纲生成约 5~15s，用户在确认页等待可接受 |

## 二、优先级路线（重排版）

### P0：解除阻塞 + 基础观测

**目标**：让所有请求不阻塞用户，并知道时间花在哪里。

#### P0-A ✅ 已完成（2026-05-18）：全链路异步后台任务

所有资源生成入口（报告、PPT、教案、练习题、小游戏）在 chat stream 和 direct 两条路径上均已改为异步后台任务。

#### P0-B ✅ 已完成（2026-05-18）：FastChatRuntime 三路检索并发

RAG/Web/Video 并行执行，首 token 延迟降低约 50%。

#### P0-C ✅ 已完成（2026-05-18）：关键路径 Trace

**当前问题**：不知道报告/PPT 慢在哪个阶段，优化后也无法量化收益。  
**已实现**：
```
{
  "trace_id": "uuid",
  "route": "fast|workflow",
  "timings": {
    "rag_ms": 480, "web_ms": 0, "video_ms": 0,
    "llm_calls": [{"stage": "report.section", "duration_ms": 2100, "retry": 0}],
    "total_ms": 8800
  }
}
```
**改动范围**：
- `fast_chat_runtime.py`：新增 `trace_id`，对 LLM 调用计时，`llm_calls` 列表，`total_ms`
- `report_generation.py`：`_generate_section()` 返回 `elapsed_ms`，checkpoint 包含 `llm_calls`（含 stitch 阶段）
- `background_runner.py`：任务完成后注入 `total_ms` + `trace_id` 到结果 trace

### P1：报告/PPT 生成提速

**目标**：把报告生成时间从 60~120s 降到 20~40s，PPT 从 90~180s 降到 30~60s。

#### P1-A ✅ 已完成（2026-05-18）：报告正文多模式生成

- `report_generation.py`：新增 `_build_report_fast()`，一次 prompt 生成全部正文
- `build_report_markdown()` 新增 `mode` 参数（`"fast"` / `"balanced"`）
- 自动检测：`length_requirement` 含"5000字以内/短篇/概述/摘要"，或大纲 ≤2章×4节时，自动切 fast 模式
- balanced 模式（并发小节，最后 stitch）已在之前版本实现，本次保留

**实际延迟收益**：fast 模式 1 次 LLM 调用 vs balanced 模式 `max(section_time)` + stitch，适合短篇报告延迟降低约 50%

#### P1-B ✅ 已完成（2026-05-18）：前置 LLM 调用规则短路

- `universal_report_engine.py` → `extractor_node()`：所有 REQUIRED_SLOTS 已从 gathered_context 预填充且非低信号时，跳过 LLM 抽取
- `report_context_organizer.py` → `_report_context_organize_v4()`：新增 `_is_context_data_sufficient()` 检查，subject+focus 已解析且 key_points≥2 或 evidence_points≥2 时直接走规则路径，不调用 LLM

**实际延迟收益**：对话中已积累足够上下文时，节省 1~2 次 LLM 调用（约 2~6 秒）

#### P1-C ✅ 已完成（2026-05-18）：PPT 生成进度可观测

- 新增 `tasks/progress.py`：线程本地进度回调注册表（`set_progress_callback` / `report_progress` / `clear_progress_callback`）
- `background_runner.py`：任务执行前注入进度回调（`task_store.update_progress`），任务结束后清理
- `post_outline_executor.py`：html2ppt job 提交后立即上报 `{html2ppt_job_id, phase="submitted"}`；每次 phase 变化时调用 `report_progress` 更新进度
- `task_store.py`（见 P2-A）：新增 `update_progress()` 方法 + `progress_json` 列

**效果**：`GET /api/chat/tasks/{task_id}` 在 PPT 任务运行期间返回实时 `progress`：
```json
{"status": "running", "progress": {"html2ppt_job_id": "xxx", "phase": "generating_slides", "progress": 45}}
```

### P2：任务基础设施升级

**目标**：任务状态持久化，支持多 worker，支持查看历史任务。

#### P2-A ✅ 已完成（2026-05-18）：任务存储从 dict 升级为 SQLite

- `task_store.py` 完全重写：`sqlite3`（stdlib）替换内存 dict，持久化连接 + `threading.Lock()`
- DB 路径：`{api}/data/tasks.db`，可通过 `TASKS_DB_PATH` 环境变量覆盖
- 新增列：`progress_json`（用于 P1-C 实时进度）
- 新增方法：`update_progress(task_id, progress: dict)`
- 公共接口完全不变（`create/mark_running/mark_complete/mark_failed/get`）
- 单例改为懒加载（双重检查锁定），避免 import 时创建 DB

**效果**：进程重启后任务状态保留（TTL 1小时），多次查询均一致。

#### P2-B ✅ 已完成（2026-05-18）：统一资源类型协议

- `background_runner.py`：新增 `submit_callable_task(fn, workflow_type, on_complete)` — 接受任意 callable，拥有与 `submit_workflow_task` 完全相同的进度回调、trace 注入、total_ms 统计
- 公共路径提取为 `_inject_trace(result, total_ms)` 内部函数，两条路径共用
- `api/routes_v2.py`：4 个 direct 端点（report/quiz/game/ppt）全部从内联 threading+task_store 改为 `submit_callable_task`，删除 `threading` 和 `get_task_store` 导入
- 所有资源现在统一经过 background_runner → 进度回调和 trace 注入自动生效

**效果**：6 种资源生成（chat stream 路径用 `submit_workflow_task`，direct 路径用 `submit_callable_task`）都走同一套 task_store + 查询接口 + 可观测基础设施。

### P3：多模态融入（图片进报告/PPT）

**目标**：让报告和 PPT 能使用 RAG 检索到的图片和用户上传图片。

#### P3-A ✅ 已完成（2026-05-19）：MediaAssetManifest — PPT 图片融入

**当前**：RAG 已能返回图片 source，html2ppt 已支持 Media 块，已完成桥接。  
**已实现**：
- 新增 `workflows/ppt/rag_image_bridge.py`：`MediaAsset` 数据类、`extract_image_assets(sources)` 从 RAG source 列表提取图片、`inject_media_blocks(markdown, assets, max_images=3)` 将 Media 块分散注入 content 幻灯片
- `knowledge_base_summary_provider.py`：新增 `get_document_image_sources(selected_doc_ids, owner, query_text, top_k)` 方法，调用 RAG query + `_scrub_response_sources` 归一化，过滤 `modality=image` 返回
- `knowledge_base_direct_ppt_outline_service_v2.py`：大纲生成时额外调用 `get_document_image_sources()`，将 `image_sources` 保存至 draft
- `knowledge_base_direct_ppt_generation_service_v2.py`：`_DirectPreparation` 新增 `image_assets` 字段，`build_direct_ppt_metadata_from_draft()` 从 draft 读取 `image_sources` 传入
- `post_outline_executor.py`：内容 markdown 生成后、验证前，调用 `inject_media_blocks()` 将图片注入 content 幻灯片（每张幻灯片最多 1 个 Media 块，全文最多 3 张图）

**效果**：直接生成路径的 PPT 现在会在内容幻灯片中自动插入 RAG 检索到的图片，图片错误不会影响正常生成（异常静默忽略）。

### P4：ReAct Agent 化

**目标**：用模型决策替换 `route_rules.py` 中的规则路由，RAG/Web/资源生成封装为工具。

#### P4-A：Workflow as Tool（第一层）

**当前**：`route_rules.py` 有 10+ 条 if/else 路由规则。  
**改法**：
- 保留现有 workflow 不动
- 在 `fast_chat_runtime` 上层包一个 ReAct 循环
- 工具集：`rag_search`、`web_search`、`generate_report`（返回 task_id）、`generate_ppt`、`generate_lesson_plan`、`generate_quiz`
- 普通问答走 fast path 不经过 ReAct（保持延迟）

**时机**：P0-P1 稳定后开始，不依赖 P2/P3。

#### P4-B：Plan-Execute（第二层）

复杂资源生成任务由 planner 拆子任务，每步可恢复、可审计。预算控制：最大 LLM 调用次数、最大耗时。

## 四、风险与注意事项

1. **任务存储升级前**：如果生产有多 worker，当前 in-memory dict 会出现跨进程查询失败，需尽早评估部署形态。
2. **报告并行生成**：一次生成完整正文依赖大 context window，需要对不同长度分档位，保留串行 fallback。
3. **Agent 化节奏**：不要跳过 P0-P1 直接做 P4，ReAct 循环会增加每次请求的 LLM 调用次数，在生成性能未优化前会让整体变慢。
4. **旧路由清理**：`/api/chat/stream`（非 v2）应明确弃用时间点，避免双路维护负担长期积累。
5. **PPT html2ppt 依赖**：外部进程故障时需要有降级策略（返回 Markdown 而不是 PPTX）。
