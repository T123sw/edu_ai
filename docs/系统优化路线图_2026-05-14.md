## 一、当前状态（已完成）

### 1.1 已完成的改造

**异步后台任务 — Chat Stream 路径（P0-A，2026-05-14）**

- 新增 `app/chat/tasks/task_store.py`：线程安全任务状态存储，TTL 1小时自动清理
- 新增 `app/chat/tasks/background_runner.py`：daemon 线程执行 workflow，完成后回调持久化
- `MainOrchestrator.dispatch_stream()`：workflow 路径不再同步阻塞，立即返回 `task_submitted` 事件
- `ReplyServiceV2.reply_stream()`：传递 `on_workflow_complete` 回调，后台任务完成时自动写库
- `routes.py`：新增 `GET /api/chat/tasks/{task_id}` 查询接口
- 前端 `chatV2.ts`：支持 `task_submitted` 事件类型，新增 `pollChatTask()` 函数
- 前端 `ChatPanel.tsx`：`backgroundTaskId` state + 独立 useEffect 轮询，`isLoading` SSE 结束后立即释放

**效果**：通过 Chat Stream 触发的报告/PPT/教案/练习题生成不再阻塞对话界面，用户等待期间可继续发消息。

**异步后台任务 — 直接接口路径（P0-A 补全，2026-05-18）**

- `POST /api/chat/v2/report/direct`：改为立即返回 `{task_id, status: pending, workflow_type}`，后台 daemon 线程执行
- `POST /api/chat/v2/quiz/direct`：同上
- `POST /api/chat/v2/game/direct`：同上
- `POST /api/chat/v2/ppt/generate`：同上（原有 `time.sleep()` 轮询阻塞最长 30 分钟，已消除）
- `schemas_v2.py`：新增 `ChatDirectTaskSubmittedResponseV2` 统一响应模型
- 前端 `chatV2.ts`：4 个 generate 函数返回类型改为 `ChatDirectTaskSubmittedV2`
- 前端 `StudioPanel.tsx`：`directBgTasks` state + useEffect 每 2 秒轮询，完成时弹出 `notification` 并自动打开文件

**效果**：所有资源生成入口（6 种类型，chat stream + direct 两条路径）均已改为非阻塞后台异步任务。

---

**FastChatRuntime 三路检索并发（P0-B，2026-05-18）**

- `fast_chat_runtime.py`：RAG/Web/Video 三路检索从串行改为 `ThreadPoolExecutor` 并行
- 新增 `trace.timings`：记录 `rag_ms`、`web_ms`、`video_ms`、`prep_ms`
- 实测：串行 ~190ms → 并行 ~82ms（三路同时开启）

---

### 1.2 已知技术债

| 问题 | 位置 | 影响 |
|------|------|------|
| 任务存储为进程内 dict | `task_store.py` | 进程重启后任务状态丢失，多 worker 进程间不共享 |
| 双路由并存 | `/api/chat/stream` 旧 vs `/api/chat/v2/stream` 新 | 维护负担，后续只维护 v2 |
| 任务失败无重试机制 | `background_runner.py` | 用户看到失败只能重发 |
| PPT 依赖 html2ppt 外部进程 | `PptWorkflowRuntime` | 故障点多，超时管理缺失 |
| `ppt/outline` 仍同步 | `routes_v2.py` | 大纲生成约 5~15s，用户在确认页等待可接受 |

## 二、优先级路线（重排版）

### P0：解除阻塞 + 基础观测

**目标**：让所有请求不阻塞用户，并知道时间花在哪里。

#### P0-A ✅ 已完成（2026-05-18）：全链路异步后台任务

所有资源生成入口（报告、PPT、教案、练习题、小游戏）在 chat stream 和 direct 两条路径上均已改为异步后台任务。

#### P0-B ✅ 已完成（2026-05-18）：FastChatRuntime 三路检索并发

RAG/Web/Video 并行执行，首 token 延迟降低约 50%。

#### P0-C：关键路径 Trace

**当前问题**：不知道报告/PPT 慢在哪个阶段，优化后也无法量化收益。  
**需要记录**：
```
{
  "trace_id": "uuid",
  "route": "fast|workflow",
  "timings": {
    "rag_ms": 480, "web_ms": 0, "video_ms": 0,
    "llm_calls": [{"stage": "report.section", "duration_ms": 2100, "retry": 0}],
    "total_ms": 8800
  }
}
```
**改动范围**：`FastChatRuntime`（基础已有 timings）、`ReportWorkflowRuntime`、`background_runner.py`。

---

### P1：报告/PPT 生成提速

**目标**：把报告生成时间从 60~120s 降到 20~40s，PPT 从 90~180s 降到 30~60s。

#### P1-A：报告正文改为章节并行生成

**当前问题**：`build_report_markdown()` 按小节串行调用 LLM，3章×3节 = 9次串行调用。  
**改法**：
```
fast 模式：一次 prompt 生成完整正文（适合 5000 字以内）
balanced 模式：按章节并行（ThreadPoolExecutor），最后拼接
quality 模式：章节并行 + 最终一次审校调用
```
**改动范围**：`universal_report_engine.py`，`report_generation.py`。  
**风险**：一次生成完整正文对 context window 要求高，需要分档位 fallback。

#### P1-B：前置 LLM 调用规则短路

**当前问题**：slot 抽取、focus 评估、就绪判断每次都调用 LLM，即使信息足够。  
**改法**：信息充足时走规则判断，跳过 LLM；只在边界情况才调用模型。  
**改动范围**：`GenerationReadinessJudge`，`ReportContextOrganizer`。

#### P1-C：PPT 生成拆成可观测 job steps

**当前问题**：`PptPostOutlineExecutor` 内部仍同步轮询 html2ppt（虽然已移到 daemon 线程，不阻塞用户，但任务内部仍是轮询等待）。  
**改法**：html2ppt 提交后立即返回 job_id，写入 task_store，定期 check。  
**改动范围**：`PptWorkflowRuntime`，`Html2PptClient`。

---

### P2：任务基础设施升级

**目标**：任务状态持久化，支持多 worker，支持查看历史任务。

#### P2-A：任务存储从 dict 升级为 SQLite

**当前问题**：进程重启后正在运行的任务状态丢失。  
**改法**：用 `aiosqlite` 或同步 `sqlite3` 替换内存 dict，schema：
```sql
CREATE TABLE tasks (
  task_id TEXT PRIMARY KEY,
  workflow_type TEXT,
  status TEXT,
  result_json TEXT,
  error TEXT,
  conversation_id TEXT,
  owner TEXT,
  created_at REAL,
  updated_at REAL
);
```
**改动范围**：`task_store.py`（接口不变，只换存储后端）。

#### P2-B：统一资源类型协议（ResourceJob 抽象）

**当前问题**：report/ppt/lesson_plan/quiz/blog/game 各自一套状态、轮询、持久化逻辑。  
**改法**：定义统一的 `ResourceJob`，所有资源生成走同一套 task_store + 查询接口。  
**时机**：等 P0-P1 各资源链路稳定后再统一，避免重构正在变化的代码。

---

### P3：多模态融入（图片进报告/PPT）

**目标**：让报告和 PPT 能使用 RAG 检索到的图片和用户上传图片。

#### P3-A：MediaAssetManifest

**当前**：RAG 已能返回图片 source，html2ppt 已支持 Media 块，但两者之间没有桥接。  
**改法**：
```json
{
  "asset_id": "img_0001",
  "source": "rag|upload",
  "public_url": "/api/rag/image?...",
  "related_topics": ["..."],
  "caption": "..."
}
```
**落地路径**：先做 PPT（html2ppt 已有 Media 块协议，收益最快），再做报告。

---

### P4：ReAct Agent 化

**目标**：用模型决策替换 `route_rules.py` 中的规则路由，RAG/Web/资源生成封装为工具。

#### P4-A：Workflow as Tool（第一层）

**当前**：`route_rules.py` 有 10+ 条 if/else 路由规则。  
**改法**：
- 保留现有 workflow 不动
- 在 `fast_chat_runtime` 上层包一个 ReAct 循环
- 工具集：`rag_search`、`web_search`、`generate_report`（返回 task_id）、`generate_ppt`、`generate_lesson_plan`、`generate_quiz`
- 普通问答走 fast path 不经过 ReAct（保持延迟）

**时机**：P0-P1 稳定后开始，不依赖 P2/P3。

#### P4-B：Plan-Execute（第二层）

复杂资源生成任务由 planner 拆子任务，每步可恢复、可审计。预算控制：最大 LLM 调用次数、最大耗时。

---

### P5：记忆模块完善

**目标**：分层记忆（对话级 / 任务级 / 课程级 / 用户级），支持用户查看和删除。

**时机**：最靠后，当前规则抽取已能满足基本需求，过早投入收益不确定。

## 四、风险与注意事项

1. **任务存储升级前**：如果生产有多 worker，当前 in-memory dict 会出现跨进程查询失败，需尽早评估部署形态。
2. **报告并行生成**：一次生成完整正文依赖大 context window，需要对不同长度分档位，保留串行 fallback。
3. **Agent 化节奏**：不要跳过 P0-P1 直接做 P4，ReAct 循环会增加每次请求的 LLM 调用次数，在生成性能未优化前会让整体变慢。
4. **旧路由清理**：`/api/chat/stream`（非 v2）应明确弃用时间点，避免双路维护负担长期积累。
5. **PPT html2ppt 依赖**：外部进程故障时需要有降级策略（返回 Markdown 而不是 PPTX）。
