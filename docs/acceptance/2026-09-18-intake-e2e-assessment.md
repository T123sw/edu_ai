## 失败机制与时间代价

MinerU 返回的 Markdown 对下划线进行了转义，例如 `call\_id`。模型在引用时增加或删除反斜线，引用并非原文连续字符串。附件理解前两次因此失败，第三次才正确保留转义。

最终需求阶段的 REQ-4、REQ-5、REQ-6 三次均删除了引用中的转义。REQ-10 还把附件摘要中的缩写句子当成直接引用；该句不在已核验的 relevant_points 引用集合中。三次都收到相同的通用错误，没有成功修正。

总耗时 **215.20 秒**，6 次业务决策、**12 次模型 API 调用**，SQL 账本记录 **72,035 tokens**。其中附件处理三步共 99.56 秒，需求归纳三步共 115.25 秒；剩余为上传与提交等开销。每次 Harness 决策包含工具提交和结果后的结束回复，失败重试进一步放大了代价。这些是单一样例的实测值，不是总体性能统计。

## 对下一阶段的结论和改进方向

需求结构本身已经能描述“学什么、起点、约束、验收标准”，但当前实现不能可靠交接。本次既有机械引用阻塞，也有范围判断错误，不能用“模型大体理解了”判定合格。

优先改进：

1. 附件要点分配稳定的引用 ID，需求阶段引用 ID，由程序取回已核验原文；减少重复抄写、转义和全文相等判断造成的无效调用，同时保留可核验来源。
2. 校验错误明确指出失败 requirement/point 及可用依据，避免只返回泛化提示后重复生成同一错误。
3. 单独记录“资料缺口”和“目标实现限制”，不要将其写为用户 exclusions；缺少 SDK 时保留用户的实现目标，向研究阶段传递无法满足的证据需求和来源限制。
4. 修复后重新运行本样例，直到实际进入研究、读取附件并产出有引用的研究汇总；再加一组非空全局记忆优先级样例。
