# OpenMAIC 对比分析与借鉴建议

日期：2026-06-30

分析对象：

- 参考项目：`D:\github\OpenMAIC`
- 主项目：`D:\github\edu_ai`

## 1. 总体结论

OpenMAIC 最值得参考的不是某一个功能点，而是它把“在线模型调用、课件结构、媒体生成、语音讲解、聚焦动作、播放与导出”组织成了一条统一的教学场景流水线。

它的核心思路可以概括为：

```text
用户需求 / PDF / 搜索资料
  -> SceneOutline[]
  -> SceneContent + Action[]
  -> 图片 / 视频 / TTS 音频
  -> Stage / Scene 持久化
  -> 浏览器播放 / PPTX 导出 / HTML 导出
```

edu_ai 当前的能力已经有不少基础，例如在线大模型配置、html2ppt、AI_Lecturer、PPT 到视频桥接、MinerU 本地解析等。但这些能力更多是按功能模块串起来的：

```text
PPT 内容 Markdown
  -> html2ppt 服务生成 PPT/HTML
  -> 导出每页图片
  -> AI_Lecturer 生成每页讲稿、语音、数字人视频
  -> FFmpeg 合成完整视频
```

两者最大的差异是：OpenMAIC 有统一的“场景数据模型 + 动作时间线”，而 edu_ai 目前更多依赖 PPT 文件、HTML 文件、图片和外部服务之间的转换。后者能跑通，但后续加聚焦、讲解节奏、视频元素、互动题、局部修订时会比较吃力。

建议 edu_ai 不要简单推翻现有 html2ppt 和 AI_Lecturer，而是引入一个中间层：

```text
TeachingScene / TeachingDeck / TeachingAction
```

让 PPT、讲稿、TTS、视频、聚焦、数字人导出都消费同一份结构化数据。短期可以继续调用 html2ppt 和 AI_Lecturer，长期再把 OpenMAIC 式的浏览器渲染、PPTX 导出、TTS、视频生成、MinerU Cloud Provider 逐步吸收进来。

## 3. OpenMAIC 的工作方式与工作流程

### 3.1 在线模型 Provider 优先

OpenMAIC 的模型入口主要在：

- `D:\github\OpenMAIC\lib\ai\providers.ts`
- `D:\github\OpenMAIC\lib\server\classroom-generation.ts`

它使用 Vercel AI SDK 做统一接入，不把某一个本地模型作为默认依赖。OpenAI、Anthropic、Gemini、DeepSeek、Qwen、Kimi、GLM、SiliconFlow、Doubao、Tencent、MiniMax 等都被抽象成 provider + model。

这有几个好处：

1. 部署门槛低，不需要每台机器准备显卡、本地模型和模型权重。
2. 不同阶段可以使用不同模型，例如搜索 query rewrite、classroom generation、slide generation 可以分开配置。
3. API Key、baseUrl、模型能力、thinking 选项都集中管理。
4. 本地模型可以作为 provider 存在，但不是系统复杂度的中心。

edu_ai 的 `Edu_AI/api/src/core/config.py` 已经有 OpenRouter、DeepSeek、Qwen、远程 embedding 等配置，这是很好的方向。但项目里仍有旧的 Ollama 配置、AI_Lecturer 本地数字人模型、MinerU 本地命令等链路。建议把“所有 AI 能力都是 Provider”作为新的架构原则。

### 3.2 Classroom Generation Pipeline

OpenMAIC 的主链路在：

- `D:\github\OpenMAIC\app\api\generate-classroom\route.ts`
- `D:\github\OpenMAIC\lib\server\classroom-generation.ts`
- `D:\github\OpenMAIC\lib\types\generation.ts`
- `D:\github\OpenMAIC\lib\generation\scene-generator.ts`

它不是一次性让模型吐出完整 PPT，而是分阶段：

1. 接收用户需求、PDF 文本、agent 配置、媒体生成开关、TTS 开关。
2. 如果启用 web search，先生成搜索 query，再拿 research context。
3. 生成 `SceneOutline[]`，每个 outline 有类型、标题、学习目标、关键点、媒体需求等。
4. 按 outline 逐个生成 scene content。
5. 再为每个 scene 生成 action timeline。
6. 如果开启图片/视频生成，根据 `mediaGenerations` 调用 provider，下载并保存媒体文件。
7. 如果开启 TTS，为 speech actions 生成音频，并把 audioUrl 挂回 action。
8. 最后持久化 classroom/stage/scenes。

这个拆分很重要。它让系统可以在每个阶段做 fallback、retry、progress update，也让 PPT、视频、讲解、聚焦、互动都能共享同一份结构。

edu_ai 当前 PPT 生成主要在：

- `D:\github\edu_ai\Edu_AI\api\src\app\chat\workflows\ppt\content_markdown_generator.py`
- `D:\github\edu_ai\Edu_AI\api\src\app\chat\workflows\ppt\html2ppt_client.py`

现有方式是让模型生成 html2ppt 协议 markdown，再交给 html2ppt 服务。这条路短期产物明确，但结构化程度不够。建议新增一层 `TeachingDeck`，先生成结构化 JSON，再由不同 exporter 转成 html2ppt markdown、PPTX、HTML 或前端播放数据。

## 4. PPT 生成：OpenMAIC 为什么更强

OpenMAIC 的 PPT 能力强在“同一个 Slide DSL 贯穿生成、编辑、播放、导出”。

相关文件：

- `D:\github\OpenMAIC\packages\@openmaic\dsl`
- `D:\github\OpenMAIC\packages\@openmaic\renderer\src\SlideCanvas.tsx`
- `D:\github\OpenMAIC\packages\@openmaic\importer`
- `D:\github\OpenMAIC\lib\export\use-export-pptx.ts`
- `D:\github\OpenMAIC\packages\pptxgenjs`
- `D:\github\OpenMAIC\packages\mathml2omml`

它的 PPT 不是 Markdown 的副产物，而是一套可编辑的 slide object：

- slide 有背景、尺寸、元素列表、备注。
- element 可以是 text、image、shape、chart、table、latex、video 等。
- 浏览器通过 renderer 直接渲染。
- 导出 PPTX 时把同一份 DSL 映射到 pptxgenjs。
- speech actions 可以变成 PPTX speaker notes。
- latex 可以通过 mathml2omml 进入 Office 公式体系。
- importer 可以把已有 PPTX 转成 OpenMAIC slide。

相比之下，edu_ai 的 html2ppt 路线更像：

```text
模型输出 content_markdown
  -> html2ppt 服务解释 markdown
  -> 生成 PPTX / HTML / manifest
```

这导致后续功能容易被 PPT 文件格式卡住。例如：

- 想精准聚焦某个元素，需要知道元素 id 和坐标。
- 想让讲稿对应某个元素，需要元素级语义。
- 想插入视频并控制播放，需要 video element 和 action 绑定。
- 想做局部重生成，需要知道 slide/element/action 的稳定 id。
- 想做交互题或白板，需要 scene/action 级别的结构。

建议：

1. 设计 edu_ai 自己的 `TeachingDeck` / `TeachingSlide` / `TeachingElement` 数据模型。
2. 保留 html2ppt，把它改造成一个 exporter：`TeachingDeck -> html2ppt content_markdown`。
3. 新增浏览器 renderer，用于预览、播放、聚焦和编辑。
4. 后续再实现 `TeachingDeck -> pptx`，可以参考 OpenMAIC 的 `use-export-pptx.ts`。

短期不要直接废弃 html2ppt。它已经能产出比较完整的 PPT，是很有价值的过渡层。

## 5. 视频生成、语音讲解与聚焦功能

### 5.1 OpenMAIC 的视频生成

OpenMAIC 的视频不是最终整课视频，而是“课件里的 video media element”。

相关文件：

- `D:\github\OpenMAIC\lib\server\classroom-media-generation.ts`
- `D:\github\OpenMAIC\lib\media\video-providers.ts`
- `D:\github\OpenMAIC\lib\prompts\snippets\video-instructions.md`
- `D:\github\OpenMAIC\lib\prompts\snippets\slide-video-instructions.md`
- `D:\github\OpenMAIC\lib\action\engine.ts`

流程是：

1. outline 阶段决定哪些地方需要视频，写入 `mediaGenerations`。
2. provider adapter 提交视频任务。
3. 轮询远程任务直到成功。
4. 下载远程视频结果，保存到 classroom media 目录。
5. slide element 用 `mediaRef` 或 url 引用视频。
6. action timeline 里用 `play_video` 控制播放。

这样做的好处是视频成为教学场景的一部分，而不是脱离课件的最终产物。一个化学反应、算法执行过程、实验演示，都可以作为 slide 中的一个 video element 出现，并由讲解动作控制播放时机。

### 5.2 edu_ai 当前的视频生成

edu_ai 的相关文件：

- `D:\github\edu_ai\Edu_AI\api\src\app\teaching_video_bridge.py`
- `D:\github\edu_ai\Edu_AI\api\src\modules\AI_Lecturer\unified_gateway.py`
- `D:\github\edu_ai\Edu_AI\api\src\modules\AI_Lecturer\offline_video_maker.py`
- `D:\github\edu_ai\Edu_AI\api\src\modules\AI_Lecturer\LiveTalking-main`

当前链路是：

```text
PPTX 或 deck.html
  -> 导出每页 slide image
  -> 从 content_markdown 提取每页讲解 prompt
  -> 为每页生成讲稿
  -> Edge-TTS / 其他 TTS 生成音频
  -> Wav2Lip / LiveTalking 生成数字人
  -> FFmpeg 把数字人叠到 slide image
  -> 拼接完整 MP4
```

这条链路适合“最终导出一个老师讲课视频”，但不适合承担所有课件播放逻辑。它的问题是：

- PPT 被压成图片后，元素级结构丢失。
- 聚焦某个元素只能靠后处理，无法自然绑定到元素 id。
- 讲稿是视频导出阶段重新生成的，和 PPT 生成阶段不是同一份动作脚本。
- Wav2Lip、LiveTalking、FFmpeg、本地模型和 GPU 依赖较重。
- 一旦要改某一页的讲解或聚焦，需要重新走视频链路。

建议把视频能力拆成两个模式：

#### 模式 A：轻量互动课件模式

参考 OpenMAIC：

```text
TeachingSlide + TeachingAction[]
  -> 浏览器播放
  -> TTS 音频
  -> spotlight / laser / zoom
  -> video element
```

这个模式用于在线教学、预览、交互式课件、边播边问答。

#### 模式 B：重型数字人导出模式

保留 AI_Lecturer，但让它消费同一份 `TeachingAction[]`：

```text
TeachingDeck + TeachingAction[]
  -> slide frame render
  -> speech action 的文本/音频
  -> focus action 的时间点和目标区域
  -> 数字人视频合成
  -> 完整 MP4
```

这样 AI_Lecturer 不再需要重新理解 PPT，也不需要从 markdown 里猜每页讲什么。它只负责最终视频渲染。

### 5.3 OpenMAIC 的语音讲解

相关文件：

- `D:\github\OpenMAIC\lib\audio\tts-providers.ts`
- `D:\github\OpenMAIC\lib\server\classroom-media-generation.ts`
- `D:\github\OpenMAIC\lib\playback\engine.ts`
- `D:\github\OpenMAIC\lib\action\engine.ts`

OpenMAIC 的 TTS 是 provider 工厂：

- OpenAI TTS
- Azure TTS
- GLM TTS
- Qwen TTS
- VoxCPM TTS
- MiniMax TTS
- Doubao TTS
- ElevenLabs TTS
- Lemonade TTS
- browser native TTS
- custom OpenAI-compatible TTS

关键点不是支持多少家，而是音频挂在 `speech action` 上。播放引擎执行到 speech action 时，有预生成音频就播放音频，没有音频再 fallback。

edu_ai 可以借鉴这个设计，把 TTS 从 AI_Lecturer 内部抽出来，作为独立 provider。这样 PPT 预览、互动课堂、数字人导出都能复用同一份音频。

### 5.4 OpenMAIC 的聚焦功能

相关文件：

- `D:\github\OpenMAIC\packages\@openmaic\renderer\src\SlideCanvas.tsx`
- `D:\github\OpenMAIC\lib\action\engine.ts`
- `D:\github\OpenMAIC\lib\prompts\templates\slide-actions\system.md`

OpenMAIC 的聚焦功能是动作系统的一部分：

- `spotlight`：聚焦某个元素。
- `laser`：短暂指示某个元素或位置。
- `highlight`：高亮元素。
- `zoom`：放大到某个元素附近。

这些效果不是视频后期特效，而是在 renderer 里根据 slide element 几何信息实时计算。ActionEngine 执行动作时设置 canvas state，renderer 根据 state 展示聚焦效果。

这点非常值得 edu_ai 学习。推荐先在数据模型层定义：

```json
{
  "type": "spotlight",
  "target_element_id": "element_12",
  "duration_ms": 5000
}
```

然后再分别实现：

- 前端播放时显示聚焦。
- PPTX 导出时可转换为动画或备注。
- 视频导出时转换成 overlay/zoom/pan 指令。

## 6. MinerU Online API 的借鉴

OpenMAIC 的 PDF 解析在：

- `D:\github\OpenMAIC\app\api\parse-pdf\route.ts`
- `D:\github\OpenMAIC\lib\pdf\pdf-providers.ts`
- `D:\github\OpenMAIC\lib\pdf\mineru-cloud.ts`
- `D:\github\OpenMAIC\lib\pdf\constants.ts`

它支持三类 provider：

1. `unpdf`：本地轻量解析。
2. `mineru`：自部署 MinerU API，调用 `/file_parse`。
3. `mineru-cloud`：MinerU 官方云 API。

MinerU Cloud 的流程是：

```text
POST /file-urls/batch 获取 batch_id 和预签名上传 URL
  -> PUT 上传 PDF
  -> 轮询 /extract-results/batch/{batch_id}
  -> 下载结果 ZIP
  -> 读取 full.md、content_list.json、images
  -> 统一转换成 ParsedPdfContent
```

edu_ai 当前主要有：

- `D:\github\edu_ai\scripts\mineru.py`
- RAG/教材解析链路中的本地 MinerU 调用

这说明 edu_ai 已经意识到 MinerU 的价值，但还没有形成在线/本地统一 provider。

建议新增：

```text
DocumentParserProvider
  - pymupdf / basic
  - mineru-local
  - mineru-self-hosted-api
  - mineru-cloud
```

建议环境变量：

```text
PDF_PARSER_PROVIDER=mineru-cloud
MINERU_CLOUD_API_KEY=...
MINERU_CLOUD_BASE_URL=https://mineru.net/api/v4
MINERU_LOCAL_BASE_URL=http://localhost:8000
```

统一返回：

```text
markdown
pages
images
tables
formulas
content_list
warnings
provider_metadata
```

这样教材知识图谱、PPT 生成、RAG 入库、课堂生成都能复用同一份解析结果。

## 7. OpenMAIC 其他亮点

### 7.1 异步任务和进度状态

`generate-classroom` 接口立即返回 `jobId`、`pollUrl`、`pollIntervalMs`，后端用 job runner 执行长任务并持续更新 progress。

edu_ai 的视频任务已有类似状态，但 PPT、PDF、知识图谱、视频等模块可以统一一个任务模型，便于前端展示阶段进度。

### 7.2 Prompt 模块化

OpenMAIC 把不同能力拆成 prompt snippets 和 templates，例如 video instructions、slide video instructions、slide actions system prompt。这样比一个超长 prompt 更容易维护。

edu_ai 的 PPT markdown prompt 很强，但偏集中。建议把“内容规划、页面布局、视频媒体、讲解动作、聚焦动作、练习题、引用资料”拆成可组合片段。

### 7.3 Provider 托管和安全边界

OpenMAIC 对 server-managed provider 和 client-provided baseUrl 有区分，并对 PDF 解析 baseUrl 做 SSRF 风险控制。

edu_ai 后续如果开放用户配置 API baseUrl、MinerU 地址、TTS 地址，也需要类似边界。

### 7.4 PPTX Importer

OpenMAIC 有 `@openmaic/importer`，可以把 PPTX 转成内部 Slide DSL。这对 edu_ai 很有价值，因为用户可能上传已有课件，然后希望系统生成讲解、聚焦、视频或知识图谱。

### 7.5 Action Engine

OpenMAIC 的 `ActionEngine` 把 speech、spotlight、video、whiteboard、widget message 等动作统一执行。这个比单纯“生成 PPT + 生成视频”更适合做教学平台。

1. 短期作为独立 Node sidecar service 调用。
2. 中期抽取协议和数据模型。
3. 长期把关键 provider 和 renderer 思路迁移到 edu_ai 的前后端体系。

## 9. 对 edu_ai 的建议路线

### Phase 0：收敛现有配置

目标：减少本地模型依赖带来的部署复杂度。

- 把 OpenRouter、DeepSeek、Qwen、embedding、TTS、video、PDF parser 都纳入统一 provider 配置。
- 明确本地 Ollama、Wav2Lip、LiveTalking、MinerU local 都是 optional provider。
- 文档上把“默认在线 API 路线”和“本地增强路线”分开。

### Phase 1：引入 TeachingDeck / TeachingScene / TeachingAction

目标：建立统一数据模型。

建议最小结构：

```text
TeachingDeck
  id
  title
  slides: TeachingSlide[]
  scenes: TeachingScene[]

TeachingSlide
  id
  title
  elements: TeachingElement[]
  notes

TeachingElement
  id
  type
  position
  style
  content
  mediaRef

TeachingScene
  id
  slideId
  outline
  actions: TeachingAction[]

TeachingAction
  speech | spotlight | laser | highlight | zoom | play_video | pause | question
```

这一层不需要一开始就完美，但必须有稳定 id。只要有稳定 id，聚焦、局部重生成、讲稿绑定、视频导出都会容易很多。

### Phase 2：让 PPT 生成先产出结构化数据

目标：从“Markdown 即源数据”转为“结构化 JSON 是源数据”。

可以先这样过渡：

```text
LLM -> TeachingDeck JSON -> html2ppt markdown -> 现有 html2ppt 服务
```

同时把 `TeachingDeck JSON` 随材料一起保存。即使前端暂时还展示 html2ppt 的结果，后续也能从 JSON 做播放、讲解、聚焦和再编辑。

### Phase 3：轻量互动播放

目标：先做 OpenMAIC 式的播放，不急着替换数字人视频。

需要：

- 前端 slide renderer。
- Action player。
- TTS audio player。
- spotlight / laser / zoom overlay。
- video element 播放。

这一阶段可以极大提升课件预览和教学演示体验。

### Phase 4：重构 AI_Lecturer 输入

目标：让 AI_Lecturer 从结构化 action script 渲染视频。

当前 AI_Lecturer 不应该承担“重新理解 PPT”的职责。它应该消费：

- 每页 slide render。
- speech action 文本或音频。
- focus action 的目标元素坐标。
- play_video action 的时间段。

这样完整 MP4 仍然可以生成，但它会和互动课件共享同一份教学脚本。

### Phase 5：接入 MinerU Cloud

目标：把文档解析从本地命令升级为 provider。

最小可交付：

- 新增 `/api/parse-document`。
- 支持 `mineru-cloud` provider。
- 返回 markdown + images + content_list。
- 教材知识图谱、PPT 生成和 RAG 入库都调用同一个解析服务。

## 10. 最推荐优先落地的三件事

第一，先做统一 Provider Registry。这个改动收益最大，可以把在线 API 路线变成 edu_ai 的主路线，降低部署成本。

第二，给 PPT 生成加结构化中间层。不要让 html2ppt markdown 继续承担“唯一源数据”的角色。只要有 `TeachingDeck`，后续聚焦、讲解、视频、互动都会自然很多。

第三，把 AI_Lecturer 降级为“最终视频渲染器”，不要让它继续重新生成和解释教学内容。讲稿、聚焦、视频播放应该来自同一份 `TeachingAction[]`。

## 11. 结论

OpenMAIC 的强点不是“某个模型更好”或“某个 PPT 模板更漂亮”，而是它把教学内容生成变成了可编排的场景系统：

```text
结构化课件 + 动作时间线 + 媒体资源 + Provider Registry
```

edu_ai 现在已经有很多单点能力，但需要一个类似的中间层把它们组织起来。最稳妥的做法是：

1. 保留现有 html2ppt 和 AI_Lecturer，继续服务当前功能。
2. 新增 TeachingDeck / TeachingAction 数据模型。
3. 把 PPT、TTS、视频、聚焦、MinerU 都逐步接到 provider 和 action 体系中。
4. OpenMAIC 可以先作为 sidecar API 参考和复用，再逐步迁移关键设计。

这样既不会推倒重来，也能把后续复杂功能从“文件转换链路”升级成“教学场景编排系统”。
