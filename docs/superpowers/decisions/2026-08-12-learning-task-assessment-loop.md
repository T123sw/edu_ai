# 学习任务强制测评闭环实施决策日志

日期：2026-08-12

用途：实施过程中遇到 Spec 未完全限定、但不需要扩大产品范围的决策时，记录所采用的最优可回滚方案。事实需求变化仍需回到 Spec 评审，不在此日志中静默改变。

## D-001 通过后继续挑战与答案揭示

- 问题：学生第二次已经通过，但还有第三次机会；若立即揭示答案，第三次计分失去可信度。
- 采用：通过只解锁“结束测评并查看解析”；学生可选择暂不揭示并继续挑战。完整答案一旦揭示，该测评周期不再允许新的计分作答。
- 备选：通过后立即停止作答；通过后立即揭示且仍允许计分。
- 影响：需要 `answers_revealed_at` 和显式 reveal API；保留最高分规则与重做可信度。

## D-002 测评版本切换

- 问题：教师修订正式测评时，已开始学生是否切换到新版本。
- 采用：零次提交的当前测评分配可更新到新版本；已有提交继续原版本。全班或个人重测创建新的测评周期并保留旧周期。
- 备选：所有学生立即切换；所有学生永不切换。
- 影响：引入 `assessment_assignments`，版本、次数和揭示状态按测评周期冻结。

## D-003 本期编程实现题评分

- 问题：仓库没有安全的不可信代码运行能力。
- 采用：保留编程实现题与 `code_runner` 接口边界，但本期只允许 `rubric_ai_teacher`，AI 给建议分、教师给最终分。
- 备选：直接在 API 主机运行；仅使用前端 iframe；完全禁用代码题。
- 影响：不引入远程代码执行风险，同时保留计算机课程题型和后续演进空间。

## D-004 双存储发布一致性

- 问题：当前学习任务与测评分别使用 `LearningStore` 和 `AssessmentStore`，无法依赖单个数据库事务同时冻结测评版本并发布任务。
- 采用：使用幂等两步提交：服务端先校验当前 `draft_revision` 和质量门禁，再冻结测评版本，最后发布学习任务。第二步失败时任务仍保持草稿且学生不可见；重试会复用已冻结版本并继续发布。接口保持稳定，迁移到统一 PostgreSQL 后可收敛为单事务或 transactional outbox。
- 备选：先发布任务再冻结测评；跨 SQLite 文件模拟分布式事务；本期强制合并两个存储。
- 影响：不会出现学生看见无正式测评的任务；极端失败只会留下“测评已冻结、任务仍为草稿”的可安全重试状态。

## D-005 后端测试执行目录

- 问题：计划最初从 `Edu_AI/api` 执行 `python -m pytest src/tests/...`，当前工程的 `app` 包并未在该目录自动进入模块搜索路径，导致 `No module named app`，无法形成有效红灯或回归证据。
- 采用：所有后端 pytest 与 Alembic 命令从 `Edu_AI/api/src` 执行，测试路径相应写为 `tests/...`。
- 备选：在命令中临时设置 `PYTHONPATH`；修改全局 Python 环境；为测试安装可编辑包。
- 影响：不改变开发机或 CI 全局环境，命令与仓库现有导入布局一致；计划中的执行命令同步修正。

## D-006 旧学习 API 测试迁移

- 问题：原有学习 API 测试默认允许无测评直接发布，与强制发布门禁冲突，并因未覆盖新 dependency 而误用进程级测评服务。
- 采用：测试夹具显式组装隔离的 `AssessmentService`，每个需要发布的旧用例先创建一个质量合格的正式测评草稿，再调用原发布端点。
- 备选：在测试环境绕过门禁；生产路由在缺少 dependency override 时回退旧发布逻辑。
- 影响：旧学习行为继续受测，同时测试与生产规则一致，不保留任何无测评发布后门。
