# 教材知识图谱前端接入与模块归位设计

## 背景

当前项目已经具备课程知识图谱页面、课程知识库上传能力，以及知识图谱的读取与保存能力。用户额外提供了一个教材导入模块 `textbook_knowledge_graph.py`，其目标能力是：

- 前端上传教材文件
- 调用后端教材导入流水线生成课程知识图谱
- 按知识图谱切分教材内容
- 将切分后的内容向量化入库

## 目标

在课程知识图谱页面提供一个课程级“导入教材并生成知识图谱”入口。教师上传教材后，页面调用已有后端教材导入接口，并在成功后直接刷新当前课程知识图谱视图，同时展示导入结果摘要。

## 非目标

- 不替换现有 `/knowledge-base/documents` 普通资料上传接口
- 不将教材导入入口挂到知识点节点级别
- 不在本轮实现导入任务队列、轮询、断点续跑
- 不扩展到未知稳定性的旧版 `.doc` 解析链路

## 用户流程

1. 教师进入课程知识图谱页面
2. 在课程级工具区看到“导入教材并生成知识图谱”入口
3. 选择 `pdf/docx/md/txt` 等教材文件
4. 前端调用后端教材导入接口
5. 页面显示处理中状态，禁止重复提交
6. 接口成功返回后：
   - 刷新知识图谱为后端返回的新图谱
   - 保持当前页面停留在知识图谱工作区
   - 显示导入摘要，包括教材名、解析方式、切分文档数、warning
7. 接口失败时：
   - 不覆盖现有图谱
   - 显示错误信息
   - 允许用户重新尝试

## 交互设计

### 入口位置

教材导入入口放在课程知识图谱页面的课程级操作区，与现有“保存图谱”“刷新图谱”等能力并列，而不是放在节点详情面板中。原因是教材导入结果作用于整棵课程图谱，不属于单个知识点附件上传。

### 组件形态

- 一个主按钮：`导入教材并生成图谱`
- 一个隐藏的文件输入控件，由按钮触发
- 一个导入结果反馈区域，显示最近一次导入的结果摘要

### 状态反馈

- 空闲：按钮可点击
- 上传中：按钮显示 loading，文本切换为“教材导入中...”
- 成功：显示成功提示，并渲染最近一次导入摘要
- 失败：显示错误提示，不清空当前图谱

### 结果摘要内容

接口返回后，前端展示以下信息：

- 源教材文件名
- 解析器类型 `parser_used`
- 大纲来源 `outline_source`
- 切分文档数量
- warning 列表

如果接口返回 `knowledge_graph.root`，前端立即将其作为当前图谱数据源刷新页面。

## 前端架构设计

### Teacher 端页面

主要改动文件：

- `Edu_AI/src/pages/teacher/KnowledgeGraphPage.tsx`
- `Edu_AI/src/services/teacher/api.ts`

职责划分：

- `KnowledgeGraphPage.tsx`
  - 提供课程级教材上传入口
  - 维护导入中的 loading 状态
  - 触发后端教材导入请求
  - 用返回的新图谱刷新当前页面
  - 展示导入摘要和错误信息
- `teacher/api.ts`
  - 新增教材导入接口封装
  - 新增与接口返回结构对应的类型定义

### Stitch 页面

如果 `Edu_AI/src/stitch/pages/KnowledgeGraph.tsx` 是当前启用的知识图谱主页面，也需要同步补上相同能力，避免新旧页面行为漂移。实现策略保持一致：

- 入口为课程级，不是节点级
- 成功后用返回的图谱刷新视图
- 保留现有节点级知识库上传逻辑不变

## 后端对接约定

前端假设后端已经存在一个专用教材导入接口，其语义为：

- 路径位于课程上下文下
- 请求体为 `multipart/form-data`
- 接收一个教材文件
- 返回：
  - 源文档信息
  - `knowledge_graph.root`
  - `split_documents`
  - `vectorized_documents`
  - `warnings`
  - 可选的解析元信息

本轮前端实现不强绑定某个具体字段以外的多余结构，但必须消费以下最小字段：

- `source_document.name`
- `knowledge_graph.root`
- `parser_used`
- `outline_source`
- `split_documents`
- `warnings`

如果后端实际字段与上述命名略有偏差，则前端服务层做一次兼容映射，不把兼容逻辑散落到页面组件中。

## 模块归位设计

用户提供的 `textbook_knowledge_graph.py` 不应继续停留在聊天附件目录下，而应纳入项目后端代码目录。归位原则如下：

- 落到 `Edu_AI/api/Edu_AI/app/` 相邻的教材导入服务位置
- 由后端正式模块 import，而不是运行时从外部绝对路径加载
- 保持其主入口函数 `import_textbook_into_knowledge_graph(...)` 可被路由层直接调用

模块归位时需要做的轻量整理：

- 去掉对外部工作区结构的硬编码假设
- 保持对 `CourseStorageManager` 的项目内引用
- 保持对现有 RAG 系统实例的注入式依赖
- 保持 UTF-8 编码，修复明显乱码注释或异常字符串

本轮不对其内部算法做结构性重写，只做项目内可维护化落位。

## 错误处理

### 前端

- 文件为空或未选中：直接返回，不发请求
- 后端返回失败：展示错误消息，保留当前图谱
- 后端返回成功但缺失 `knowledge_graph.root`：提示导入结果不完整，不覆盖当前图谱

### 模块归位

- 若归位后的模块存在编码异常，优先修复可见错误字符串，保证可导入、可运行
- 若模块中存在当前仓库没有的外部依赖，不在前端中兜底，而是在后端模块层显式报错

- 正确解析返回结构

## 风险与取舍

### 风险 1：现有前端有两套知识图谱页面

仓库中同时存在 teacher 页与 stitch 页的知识图谱实现。若只改一处，可能造成实际运行页面没有教材导入入口。

取舍：

- 先确认当前实际入口页面
- 如果难以在本地快速判定，则两处都补齐相同能力，降低漂移风险

### 风险 2：后端接口命名尚未在前端层体现

目前前端服务层未看到教材导入接口封装，说明页面还不能直接调用这条链路。

取舍：

- 本轮在服务层新增清晰的教材导入 API
- 页面只依赖服务层，不直接拼接 fetch 请求

### 风险 3：导入耗时较长

教材解析、建图、切分、向量化都可能较慢。

取舍：

- 第一版先使用同步请求 + loading 状态
- 页面文案明确提示“处理中”
- 若后续体验不佳，再升级为异步任务模式

## 实施结果标准

完成后应满足：

- 知识图谱页面能从课程级入口上传教材
- 上传后能调用已有后端教材导入能力
- 页面能即时刷新为新生成的知识图谱
- 普通知识库上传逻辑不受影响
- 提供导入摘要与错误反馈
- `textbook_knowledge_graph.py` 已纳入项目目录并可被项目代码正式引用
