# 前端体验优化：对话纪要与交互设计

日期：2026-09-07

状态：设计记录，尚未实施。用户已明确三项需求；本文中的具体交互、版本规则和边界处理为本次对话提出的设计方案，不将未逐项确认的细节视为已验收要求。

## 1. 对话背景与范围演进

1. 用户通过 SSH 转发访问前端，确认成功登录。连接排障已结束，本文不记录连接地址、账号或凭据。
2. 用户最初要求审查前端组织结构，完成了源码与主入口依赖分析，没有修改业务代码。
3. 用户随后明确暂不考虑代码结构，希望改善前端展示与使用体验，让用户愿意持续使用。
4. 讨论了首页继续工作、师生任务差异、工作台视觉中心、快捷任务、作品预览、生成反馈和视觉一致性。
5. 用户选择“首页继续按钮”和“对话明确课程、知识点上下文”，最初要求开始实施。
6. 用户追加“已有资料由 Agent 修改，支持按钮和自然语言触发，不明确时追问”，并将当前任务调整为“先设计这几部分内容”。
7. 用户要求记录本次对话、梳理成文档。因此，本阶段交付为本文，业务实现尚未开始，也未进行功能验收。

8. 用户进一步澄清：继续入口至少直接显示上次课程；课程按知识点组织，“为当前课程生成资料”围绕当前所在知识点，Agent 不清楚时必须追问。此前将该表达解释为整门课程的方案已撤销。用户随后确认暂时没有第 3 点补充；已有资料修改设计保持原记录。

## 2. 用户明确提出的三项需求

### 2.1 首页继续入口

> 教师端继续备课以及学生端继续学习，但是不要过度的展开，只放一个继续按钮就行，放在首页的最上端。

最新澄清：保持紧凑，但至少直接显示上次学习的课程名称，不能只剩按钮或仅在悬停时显示课程。教师继续备课入口采用同样的信息组织。

### 2.2 课程与知识点上下文

> 对话时，围绕着具体的知识点，对话 agent 要清楚地知道用户在围绕着知识点进行提问和工作。比如用户提问“为当前课程生成报告”，agent 要清楚地知道用户要围绕着哪个课程来工作。

最新澄清：课程按知识点组织。用户说“为当前课程生成资料”时，应围绕当前所在知识点生成；Agent 无法明确知识点或用户意图时，必须先澄清。此规则取代此前“按整门课程处理”的解释。

### 2.3 已生成资料的修改更新

> 在资源生成部分提供修改按钮，用户点击后提出修改意见，agent 开始修改；也可以直接在对话中触发，例如“将上次生成的数组的报告修改一下，我觉得……”。agent 要读取报告内容、理解用户意图，遇到不清晰的地方要向用户澄清追问。

## 3. 设计一：首页顶部的紧凑继续入口

### 展示

- 教师端：`继续备课 →`。
- 学生端：`继续学习 →`。
- 放在首页主内容最上方，以课程名称和一个继续按钮组成紧凑区域，不展开进度面板或任务列表。
- 上次课程名称必须直接可见，不能只放在悬停提示中。有可靠记录时可附带知识点作为次要信息。
- 学生端原有“最近学习”大块区域收敛为该入口，避免重复展示。

```text
上次备课：数据结构 · 数组                 [继续备课 →]
上次学习：数据结构 · 数组                 [继续学习 →]
```

以上两行分别用于教师端和学生端，不在同一首页同时展示；知识点可选，课程名称必需。

### 行为方案

1. 返回最近实际备课或学习的位置，尽量恢复课程、知识点、对话或正在查看的资料。
2. 返回首页、访问个人设置等操作不覆盖最近工作位置。
3. 使用记录按账号隔离，教师和学生分别记录。
4. 没有历史记录时不显示按钮；课程已删除或失去权限时不展示失效入口。
5. 恢复前验证目标仍可访问，不以浏览器记录代替权限校验。

### 实施前需明确的细节

- 首版恢复到页面、知识点还是具体资料和对话的粒度；应确保按钮承诺与实际恢复能力一致。
- 课程仍存在但具体资料已删除时，回退到课程工作区还是隐藏入口。
- 是否支持跨设备同步；本次需求没有要求跨设备，不默认扩展范围。

## 4. 设计二：明确当前讨论对象

### 展示与切换

对话标题下固定显示一行范围信息：

```text
当前讨论：数据结构 › 数组                  切换
```

未选择知识点时：

```text
当前讨论：数据结构 › 尚未选择知识点        选择知识点
```

- 课程名称始终可见，避免只显示“当前知识库”或孤立的知识点名称。
- 点击“切换”展示当前课程的知识点树，支持搜索。未选知识点不自动等同于整门课程范围。
- 从知识点页面进入问答时自动带入该知识点。
- 用户明确要求切换且对象可唯一定位时，对话与页面范围同步更新。

### 意图与默认范围规则

| 用户表达 | 处理方案 |
| --- | --- |
| “解释一下这里的概念” | 默认围绕当前知识点 |
| “生成一份报告” | 围绕当前明确的知识点；未明确时先追问 |
| “为当前课程生成报告／资料” | 围绕当前课程中所处的知识点生成；知识点或意图不明确时必须追问 |
| “给数组这一节增加几个例子” | 定位当前课程中的数组知识点 |
| “换到链表继续讨论” | 唯一匹配时切换范围，并更新页面 |
| “给另一门课也做一个” | 未明确课程时追问 |

课程以知识点组织，课程名称标明归属，当前知识点决定本轮默认生成范围。例如当前处于“数据结构 › 数组”，用户说“为当前课程生成报告”，应围绕“数组”生成。Agent 可说明“我将围绕《数据结构》中的‘数组’知识点生成报告”，目标明确时直接继续。

若尚未选择知识点、同名知识点无法区分，或指令与当前上下文存在歧义，必须先追问，例如“你想围绕《数据结构》的哪个知识点生成资料？”并提供可选知识点。等待用户回答后再生成，不能自行猜测或扩大为整门课程。

用户明确提出“整门课程”或跨知识点要求时，需要与当前知识点任务区分；覆盖哪些知识点、如何组织成果不明确时必须澄清。这不改变“为当前课程生成资料”默认指向所处知识点的规则。

一次临时指令可以使用不同范围，但不必永久改变页面默认范围；明确“换到……”时再更新默认范围。若指令与当前引用资料指向不同对象且无法明确判断，应先澄清，不能静默修改错误对象。

### Agent 获得的上下文

- 当前课程的有效标识、名称及必要课程信息。
- 当前知识点的有效标识、名称和章节路径；缺失或无法唯一定位时明确标记，触发澄清，不能用课程范围代替。
- 当前对话、选中资料，以及本轮明确指定的目标。
- 范围和资料归属由服务端校验，不能只信任前端传入的名称或浏览器记录。

切换课程、知识点后，旧对话可保留供查看，但旧课程的资料、选中对象及未完成修改不能混入新范围。前端标明的讨论对象、服务端实际处理对象和成果归属应保持一致。

## 5. 设计三：通过 Agent 修改已有资料

### 5.1 按钮入口

在生成完成结果卡片和资源预览中提供统一按钮：

```text
数组基础报告

[预览]  [让 AI 修改]  [下载]
```

点击后进入或聚焦对话区，输入框上方显示目标：

```text
正在修改：《数组基础报告》 · 第 2 版        ×

请输入修改意见，例如：
增加一个数组插入的示例，并把时间复杂度解释得更直观。
```

- 点击按钮只选定目标；提交修改意见后才启动任务。
- 关闭引用标签后恢复普通对话。
- 保留原有手动编辑入口。

### 5.2 自然语言入口

用户可直接说：

> 将上次生成的数组报告修改一下，我觉得例子太少，增加两个实际案例。

Agent 在用户有权访问的资料中定位对象，优先结合当前引用、当前对话生成记录、当前课程及知识点范围和标题主题。不将全局最新报告直接等同于“上次那份”。

唯一定位后，说明目标和本轮改动并继续，例如：

> 我会修改《数组基础报告》，保留现有结构，补充两个实际案例和对应解释。

随后必须读取真实原文，基于原文修改，不能仅根据标题重新生成。若目标资料与当前课程不一致，应明确处理对象，避免静默跨课程操作。

### 5.3 统一处理流程

```text
按钮选定资料／自然语言提出修改
        ↓
定位目标并校验访问、修改权限
        ↓
读取原文和目标版本
        ↓
理解修改要求
        ├─ 明确 → 执行修改
        └─ 不明确 → 针对性追问 → 保留上下文继续执行
        ↓
保存新版本、展示修改摘要与预览入口
```

### 5.4 追问规则

| 情况 | 交互方案 |
| --- | --- |
| 两份数组报告都可能匹配 | 显示标题等区分信息，让用户选择 |
| 仅说“我觉得不太好” | 询问主要调整内容深度、结构还是表达方式 |
| “第二部分不对” | 先读原文；能确定问题就修正，仍不能判断时引用具体内容追问 |
| 找不到资料 | 说明当前范围未找到，提供选择已有资料入口 |
| 读取失败 | 明确提示读取失败，支持重试，不声称已修改 |
| 要求清楚且目标唯一 | 直接执行，不增加重复确认 |

追问期间保留目标资料、版本和原修改意见。用户补充回答后继续原任务，不要求重新选择资料或复述要求。

### 5.5 完成反馈与版本方案

```text
《数组基础报告》已更新

新增了两个实际案例；
补充了插入与删除操作的复杂度解释。

[查看新版]  [查看修改]  [继续修改]
```

建议采用以下版本行为，实施前核对现有资源存储能力：

1. 成功后自动保存为同一资料的新版本，旧版可查看、可恢复。
2. 默认只修改用户要求涉及的内容；必要的联动改动写入结果摘要。
3. 已发布给学生的版本保持稳定，新修改作为草稿，由教师主动发布后对学生生效。
4. 修改失败不破坏原文，重试保留修改意见。
5. 多窗口或多人编辑时检查目标版本，不能静默覆盖期间产生的新版本。

### 5.6 类型边界

用户需求面向“已生成资料”，报告是明确举例。各类型可能需要不同修改能力，实施时必须列出支持范围，不能因已有报告修改能力而宣称所有资料都已支持。对于尚未支持的类型，不展示可执行但实际无效的修改入口。是否分批交付，应在实施计划中明确。

## 8. 其他讨论内容：暂不纳入本轮实施

### 8.1 代码结构审查纪要

本轮曾观察到两套认证状态并存、聊天和资料面板超过 2,000 行、师生公共能力位于教师目录、接口职责分散、应用装配与公共 UI 混合，以及默认测试命令未覆盖 `tests/frontend` 的 56 个测试文件，部分旧测试引用缺失组件。

这些结论来自静态审查和依赖分析，不是运行时故障复现。用户随后明确“先不考虑代码结构上的问题”，因此不据此启动目录迁移、组件拆分或架构重构。

### 8.2 展示优化建议的取舍

此前提出过：任务导向首页、师生不同首屏、工作台随阶段突出对话或作品、快捷提问、用户语言替换技术词、作品缩略图、真实生成阶段反馈、统一视觉层级，以及真实用户试用。

首页方案以最新澄清为准：最上端直接显示上次课程名称，配一个继续按钮，保持紧凑；不能只剩按钮，也不能扩展成大型继续工作卡片或待办仪表盘。其余建议均未自动进入本轮范围。

历史视觉回归截图只用于辅助讨论，与当前导航已有差异；没有把历史截图当成当前在线页面的验收证据，也未验证用户喜好。
