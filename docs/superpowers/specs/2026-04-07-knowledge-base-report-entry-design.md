# 知识库驱动的报告生成入口设计

日期：2026-04-07

## 1. 目标

为现有“生成报告”能力增加一个新的入口层，让用户在点击前端“生成报告”按钮后，不是直接面对空白表单，而是先看到一组可选卡片：

- 第一行：固定的报告模板卡片
- 第二行：系统基于当前勾选文档摘要实时生成的推荐方向卡片

用户点击卡片后进入可编辑输入区，系统自动带入一段默认提示词，用户可直接生成，也可继续补充要求。

本设计定义的是一条新的“知识库驱动的报告生成引导链路”，而不是现有聊天驱动 report 链路的换皮。

## 2. 产品定位

### 2.1 功能定位

该入口的核心任务是：

- 帮助用户从“已有材料”出发，更轻松地发起报告生成
- 降低空白输入成本
- 提高报告生成方向的命中率

一句话概括：

> 这不是“填写报告参数”，而是“先选报告方向，再微调生成”。

### 2.2 与现有链路的关系

系统后续应并存两条报告生成链路：

- 聊天驱动 report 链路：适合边聊边生、围绕对话继续生成
- 知识库驱动 report 入口：适合材料驱动、方向先行、快速发起

两者互补，不互相替代。

## 3. 范围与边界

### 3.1 允许使用的上下文

- 当前勾选的知识库文档
- 文档摘要
- 文档标题、类型、基础元信息
- 用户在编辑输入区补充的文本要求

### 3.2 明确不使用的上下文

- 当前聊天内容
- 历史会话内容
- conversation memory
- active context snapshot
- 引用对话内容
- 之前聊天里形成的用户偏好

### 3.3 强制隔离原则

该入口生成报告时，不读取 `conversation snapshot / conversation memory / active context`。

它的语义链路必须是：

`selected docs + doc summaries + selected card + user edited prompt -> knowledge-base report generation`

而不是：

`conversation + docs + prompt -> report generation`

## 4. 用户体验目标

### 4.1 主流程

1. 用户在知识库中勾选一组文档
2. 用户点击“生成报告”
3. 系统弹出“创建报告”入口层，而不是旧的直接表单
4. 第一行展示 4 张固定模板卡片
5. 第二行展示 4 张基于文档摘要实时生成的推荐方向卡片
6. 用户点击任一卡片后，进入编辑态
7. 输入框自动带入该卡片对应的默认提示词草稿
8. 用户补充或修改内容后点击生成
9. 系统基于勾选文档生成正式报告
10. 新报告进入右侧文件列表并自动打开

### 4.2 体验原则

- 第一屏优先解决“从哪里开始”
- 第二屏优先解决“我只想稍微改一下就生成”
- 推荐要稳，不追求炫技
- 默认语言固定为中文，不提供语言选择

## 5. 第一行固定模板卡片

第一行固定为 4 张卡片：

- `简要报告`
- `详细报告`
- `学习方案`
- `自定义报告`

### 5.1 简要报告

目标：

- 快速生成一份概览型中文报告
- 强调主旨、重点结论和关键信息提炼

默认提示词方向：

- 基于已选文档，生成一份中文简要报告
- 提炼核心主题、关键结论和主要依据
- 结构清晰、篇幅适中、避免冗长展开

### 5.2 详细报告

目标：

- 生成完整度更高、分析展开更充分的中文报告

默认提示词方向：

- 基于已选文档，生成一份中文详细报告
- 包含背景、核心内容、重点分析、结论与建议
- 尽可能完整覆盖材料中的主要信息与逻辑关系

### 5.3 学习方案

目标：

- 将材料整理成可执行的学习路径

默认提示词方向：

- 基于已选文档，生成一份中文学习方案
- 包含学习目标、重点难点、学习顺序、阶段安排和实践任务
- 输出强调可执行性，不只是复述材料

### 5.4 自定义报告

目标：

- 提供自由表达入口，作为前三类之外的兜底选择

默认提示词方向：

- 基于已选文档，生成一份中文报告
- 请围绕用户后续补充要求组织结构与内容
- 输出应结合材料内容，避免脱离文档空泛发挥

## 6. 第二行推荐卡片

### 6.1 来源

第二行推荐卡片必须基于当前勾选文档摘要实时生成。

优先使用摘要而不是全文，原因如下：

- 避免上下文过长
- 减少模型消耗
- 提升入口层响应速度
- 更适合做“方向推荐”而不是“最终生成”

### 6.2 数量

第二行固定展示 4 张推荐卡片。

### 6.3 推荐层职责

推荐层只负责：

- 识别当前材料适合生成哪些报告方向
- 产出推荐卡片
- 为每张卡片生成可编辑的默认提示词草稿

推荐层不负责：

- 直接生成最终报告
- 替代最终报告生成逻辑
- 读取聊天上下文补强推荐

### 6.4 推荐方向类型集合

为了保证第一版稳定性，推荐卡片不做完全开放式自由生成，而是限制在有限的意图集合内，再根据摘要内容做排序和具体文案生成。

第一版建议支持以下 `recommendation_type`：

- `summary`
- `comparison`
- `risk_analysis`
- `teaching_suggestion`
- `study_focus`
- `theme_outline`

系统从中选出最匹配的 4 个方向展示。

### 6.5 推荐卡片质量要求

每张推荐卡片必须满足：

- 方向明确
- 说明简洁
- 不离题
- 能直接进入生成

推荐的价值不在于“惊艳”，而在于“靠谱”。

## 7. 统一卡片数据模型

虽然 UI 上分为“固定模板卡片”和“推荐卡片”两行，但内部应统一为一套卡片对象模型，避免后续演化成两套逻辑。

建议模型：

```ts
type ReportEntryCard = {
  card_id: string
  card_type: "preset" | "recommended"
  title: string
  description: string
  prompt_draft: string
  preset_key?: "brief" | "detailed" | "study_plan" | "custom"
  recommendation_type?:
    | "summary"
    | "comparison"
    | "risk_analysis"
    | "teaching_suggestion"
    | "study_focus"
    | "theme_outline"
  recommendation_source?: "doc_summaries"
}
```

统一后应共享同一条点击链路：

`卡片 -> prompt_draft -> 编辑态 -> 最终生成请求`

## 8. 推荐卡片输出契约

推荐服务的输出不应只是“标题 + 一句文案”，而必须带完整可编辑草稿。

建议输出契约：

```ts
type RecommendedReportCard = {
  card_id: string
  card_type: "recommended"
  title: string
  description: string
  recommendation_type:
    | "summary"
    | "comparison"
    | "risk_analysis"
    | "teaching_suggestion"
    | "study_focus"
    | "theme_outline"
  prompt_draft: string
  source_doc_ids: string[]
  source_basis: "doc_summaries"
}
```

### 8.1 `prompt_draft` 要求

`prompt_draft` 必须是可直接进入编辑区并可直接提交的草稿，不只是一个方向标题。

例如不应只返回：

- “对比分析”

而应返回：

- “请基于已选文档，生成一份中文对比分析报告，重点比较各材料在核心观点、方法路径、适用场景和局限性上的异同，并给出归纳结论。”

## 9. 编辑态设计

### 9.1 进入方式

用户点击任一卡片后，进入编辑态。

### 9.2 编辑态内容

编辑态至少包含：

- 当前选中的卡片标题
- 一段默认生成说明
- 一个可编辑的文本输入区
- 生成按钮
- 返回卡片选择的入口

### 9.3 默认语言

- 默认语言固定为中文
- 不提供语言切换器
- 第一版不支持多语言

### 9.4 可编辑性原则

所有卡片，无论是固定模板还是推荐卡片，进入编辑态后都必须允许用户修改默认提示词。

## 10. 入口状态机

建议明确入口状态，避免后续前后端状态分裂。

```ts
type ReportEntryState =
  | "idle"
  | "cards_loading"
  | "cards_ready"
  | "editing_prompt"
  | "generating"
  | "completed"
  | "error"
```

### 10.1 状态说明

- `idle`
  - 尚未打开入口层
- `cards_loading`
  - 正在基于勾选文档摘要生成推荐卡片
- `cards_ready`
  - 固定模板和推荐卡片已可展示
- `editing_prompt`
  - 用户已选择卡片，正在编辑默认提示词
- `generating`
  - 用户已提交，正在生成报告
- `completed`
  - 报告生成成功
- `error`
  - 推荐卡片生成失败或正式报告生成失败

## 11. 推荐生成策略

### 11.1 输入

推荐层的输入应包含：

- `selected_doc_ids`
- 文档标题
- 文档摘要
- 必要的轻量元信息

### 11.2 规则

- 摘要优先，不读取全文
- 推荐结果应随勾选文档变化而变化
- 同一勾选集合下，应尽量保持短时间内结果稳定

### 11.3 缓存策略

为了避免每次打开入口层都重新调用模型，推荐层应允许短时缓存。

建议缓存键包含：

- 勾选文档 ID 集合
- 摘要版本标识或更新时间

可表示为：

`hash(sorted(selected_doc_ids) + summary_updated_at_snapshot)`

缓存原则：

- 同一集合且摘要未变化时，短时复用推荐结果
- 勾选集合变化后失效
- 文档摘要更新后失效

这样既能满足“实时响应当前选择”，又不会导致每次打开都重算。

## 12. 降级策略

因为推荐依赖摘要，第一版必须明确降级方案。

### 12.1 无文档勾选

如果用户没有勾选任何文档：

- 不进入推荐生成
- 直接提示用户先选择至少一个文档

### 12.2 部分文档无摘要

如果只有部分文档缺少摘要：

- 优先基于已有摘要生成推荐
- 仍允许进入入口层
- 在推荐质量上做保守处理，不强行做过度具体的推荐

### 12.3 全部文档无摘要

如果所有选中文档都没有可用摘要：

- 不做模型化推荐
- 第二行降级为 4 张保守的通用推荐卡片
- 通用推荐仍需提供可编辑 `prompt_draft`

建议通用方向为：

- 核心内容总结
- 主题结构梳理
- 学习重点提炼
- 应用建议整理

### 12.4 摘要过短或质量不足

如果摘要过短、信息不足或明显无法支持稳定推荐：

- 输出更通用的推荐标题和说明
- 避免生成过度具体、可能失准的方向

## 13. 最终报告生成契约

推荐生成与最终报告生成是两件不同的事情。

### 13.1 推荐层

职责：

- 基于摘要生成卡片和 `prompt_draft`

### 13.2 生成层

职责：

- 基于选中文档和用户最终编辑结果，生成正式报告

二者不能混用，也不能让推荐层直接替代最终生成层。

### 13.3 生成请求建议

最终生成请求至少应包含：

- `selected_doc_ids`
- `entry_mode = "knowledge_base_report"`
- `card_type`
- `preset_key` 或 `recommendation_type`
- `prompt_draft`
- `final_user_prompt`

关键要求：

- 该链路不传入 `conversation_id`
- 或者即便底层接口仍有该字段，也必须在服务端显式忽略会话态上下文

## 14. 与现有聊天 report 链路的隔离原则

这是本设计的强制约束。

### 14.1 知识库入口链路

适用于：

- 用户勾选文档后主动发起报告生成
- 用户希望系统先给方向，再补充要求

特点：

- 不依赖会话
- 不读取聊天记忆
- 推荐基于摘要

### 14.2 聊天 report 链路

适用于：

- 用户边聊边生成
- 用户在对话里要求生成、改写、延续报告

特点：

- 允许依赖对话上下文
- 适合连续问答和任务承接

### 14.3 技术要求

如果两条链路复用同一底层 report service，也必须有显式模式开关，确保知识库入口模式下不会读取 conversation context。

## 15. 结果呈现

生成完成后：

- 新报告进入右侧文件列表
- 新生成文件应直接打开
- 列表遵循现有简单排序原则

当前排序原则保持：

- 置顶项优先于普通项
- 普通项中，新生成的在最上面
- 右侧列表不按类型分组，统一在同一列表中展示

## 16. 非目标

本次设计不包含：

- 基于聊天内容生成推荐卡片
- 多语言切换
- 推荐卡片收藏与历史管理
- 用户自定义固定模板管理
- 基于全文做复杂推荐分析
- 复杂的推荐解释系统

## 17. 验收标准

满足以下条件，可视为第一版完成：

- 点击“生成报告”后，优先出现卡片入口层，而不是旧表单
- 第一行固定展示 4 张模板卡片
- 第二行展示 4 张基于文档摘要生成或降级替代的推荐卡片
- 点击任一卡片后进入编辑态
- 编辑态默认带入可编辑的 `prompt_draft`
- 不展示语言选择器，默认中文
- 推荐层与生成层职责清晰分离
- 知识库入口链路不读取聊天上下文
- 生成完成后，新报告进入右侧列表并自动打开

## 18. 推荐方案结论

采用“统一卡片模型 + 摘要驱动推荐 + 可编辑 prompt 草稿 + 与聊天链路显式隔离”的方案。

原因：

- 能显著降低用户空白输入成本
- 与 NotebookLM 式入口体验相符
- 第一版范围稳定、可实施性高
- 能与现有聊天驱动 report 链路形成清晰互补
- 便于后续继续扩展推荐质量，而不破坏入口结构
