# 报告产物引用编辑设计

日期：2026-04-06

## 1. 目标

本设计面向“报告”生成物，新增一条围绕已生成产物继续工作的稳定链路，而不是把右侧内容简单复制回输入框。

第一阶段目标：
- 右侧生成物支持“添加到对话”
- 输入区显示引用卡片，不把大纲或正文全文塞进输入框
- 用户可以基于引用的报告大纲或报告正文发起结构化修改
- 修改结果默认生成新版本，不覆盖原版本
- 修改后的新版本同步进入右侧生成物列表和课程资源列表
- 报告正文维护一份可持续承接的生成状态结构
- 为“基于生成物提问”预留同一套引用底座，但第一阶段不要求完整实现问答能力

非目标：
- 第一阶段不处理教案、课件等其他生成物
- 第一阶段不做任意文本片段级编辑，优先支持结构级定位
- 第一阶段不把所有历史版本同时展开到聊天流中

## 2. 用户体验

### 2.1 添加到对话

在右侧生成物列表中，报告大纲和报告正文增加“添加到对话”按钮。

点击后：
- 输入框上方出现一张引用卡片
- 卡片显示标题、类型、版本号、生成时间
- 输入框保持为空，用户只输入修改指令或问题
- 同一时刻只允许一个主引用卡片处于激活状态

卡片至少提供：
- 查看
- 移除引用
- 当前版本标识

### 2.2 修改交互

用户引用报告大纲后，可以输入：
- 修改第三部分，更强调课堂互动问题
- 把结论项拆成两点
- 基于这个大纲重新生成一版正式报告

用户引用报告正文后，可以输入：
- 修改摘要，压缩到 150 字以内
- 重写第二部分，风格更学术
- 保留结构，只重写结论

系统应优先将这些输入识别为“围绕当前引用产物的操作”，而不是普通开放聊天。

### 2.3 结果呈现

修改完成后：
- 生成一个新版本
- 新版本出现在右侧列表最上端
- 新版本同步进入课程资源列表
- 原版本保留
- 界面中能看出版本链关系，例如“v2（基于 v1 修改）”

如果是“基于修改后大纲重新生成正文”：
- 生成一份新的正文版本
- 正文版本记录其来源大纲版本
- 右侧列表默认展示最新正文版本

## 3. 推荐方案

采用“显式引用卡片 + 专用编辑意图识别”方案。

原因：
- 与现有 artifact、workflow_state、右侧生成物列表兼容
- 比把全文拼进输入框更稳，避免长文本污染上下文
- 便于后端精准知道用户当前在修改哪一份产物
- 便于后续扩展“基于生成物提问”能力
- 便于实现版本链和生成状态结构

不采用以下方案：
- 直接把全文插入输入框：实现快，但精度差，长文本会影响后续抽取和路由
- 单独切出编辑模式页面：交互清晰，但与现有对话流割裂，第一阶段成本偏高

## 4. 关键概念

### 4.1 ConversationArtifactReference

表示当前聊天输入区绑定的引用产物。

职责边界：
- 只负责“当前对话正在引用哪个对象”
- 属于会话态，不记录该版本是如何生成出来的
- 可随用户切换引用、移除引用或刷新恢复而变化
- 不应承担正式产物生成历史的持久职责

建议字段：
- `artifact_id`
- `artifact_type`: `report_outline | report`
- `version_id`
- `title`
- `source_conversation_id`
- `source_course_id`
- `root_artifact_id`
- `parent_artifact_id`
- `created_at`
- `generation_state_id`（正文可选）

### 4.2 ArtifactEditIntent

表示本轮用户围绕引用产物发起的操作类型。

建议拆成两个维度：

目标类型：
- `outline`
- `report`

动作类型：
- `rewrite_section`
- `expand_section`
- `compress_section`
- `reorder_section`
- `regenerate_from_outline`

第一阶段应优先覆盖的组合：
- `outline + rewrite_section`
- `outline + regenerate_from_outline`
- `report + rewrite_section`
- `report + compress_section`（摘要）
- `report + rewrite_section`（结论）

第二阶段预留：
- `ask_about_artifact`

### 4.3 ReportGenerationState

绑定到每个报告正文版本，记录正文生成和后续修订所依赖的原始信息。

职责边界：
- 只负责“这份报告版本是如何生成出来的”
- 属于产物态，和当前会话是否正在引用它无关
- 不应被前端临时引用状态反向覆盖
- 应作为正文版本后续再编辑、再生成的稳定依据

第一阶段最小建议字段：
- `state_id`
- `artifact_id`
- `version_id`
- `topic`
- `focus`
- `length_requirement`
- `style`
- `audience`
- `references`
- `source_outline_artifact_id`
- `source_report_artifact_id`
- `source_version_id`
- `generated_at`
- `generation_mode`: `initial | regenerate_from_outline | revise_report`
- `model_name`
- `trace_fingerprint` 或等价追踪字段

可后置字段：
- `edit_history`
- 更细的模型调用参数
- 非必要的完整 prompt 快照

### 4.4 ArtifactStructureNode

统一的结构解析节点模型，用于大纲和正文的结构化定位。

建议字段：
- `node_id`
- `artifact_id`
- `version_id`
- `node_type`: `summary | intro | section | conclusion`
- `title`
- `order_index`
- `content`
- `path`

说明：
- 大纲和正文都应尽量映射到同一套节点模型
- 避免后续出现“大纲一套定位、正文一套定位”的分叉实现

### 4.5 ArtifactEditRequest

表示本次围绕引用产物发起的标准化编辑请求。

建议字段：
- `artifact_reference`
- `target_type`: `outline | report`
- `target_node_id`
- `target_node_label`
- `action_type`: `rewrite | expand | compress | reorder | regenerate`
- `instruction`

### 4.6 ArtifactVersionMetadata

表示版本关系和派生来源。

建议字段：
- `root_artifact_id`
- `parent_artifact_id`
- `version_id`
- `version_number`
- `derived_from_action`
- `derived_from_reference`
- `created_at`

## 5. 前端设计

### 5.1 右侧生成物列表

报告类生成物新增按钮：
- 添加到对话
- 查看
- 删除
- 置顶

“添加到对话”行为：
- 将所选生成物写入当前对话输入区的引用状态
- 不直接展开全文到输入框
- 若已有引用，默认替换为新引用
- 第一阶段列表展示顺序按“最新版本倒序”处理，版本树关系先通过副标题表达，不强制上树形展开

### 5.2 输入区

输入区上方新增引用卡片区域。

行为约束：
- 有引用卡片时，发送消息时附带结构化引用信息
- 用户清空输入框不应自动清除引用卡片
- 用户点击卡片关闭后，本轮消息恢复为普通聊天
- 刷新页面后，如果当前会话仍有激活引用，可从会话状态恢复引用卡片

### 5.3 版本展示

右侧列表和课程资源列表都应显示：
- 版本号
- 来源关系
- 是否为最新版本

建议表现：
- 最新版本在上
- 同一根报告的各版本可折叠查看
- 第一阶段如果不做折叠树，至少在条目标题或副标题中标出 `v1 / v2 / v3`

## 6. 后端设计

### 6.1 请求协议扩展

对 `/api/chat/v2/reply` 增加可选引用字段，例如：
- `artifact_reference`
- `artifact_operation_context`

后端收到请求后，若存在引用卡片：
- 优先进入“引用产物处理链路”
- 仅当识别失败时，才回退到普通对话链路

### 6.2 意图判定

新增一层针对引用产物的意图识别，优先级高于普通 report route。

输入信号包括：
- 当前 `artifact_reference`
- 用户文本
- artifact 类型
- 当前 conversation snapshot
- 当前 workflow_state

判定结果至少包含：
- 是否为引用编辑意图
- 编辑目标类型：大纲或正文
- 目标结构节点
- 编辑动作：改写、扩写、压缩、重排、整篇重生成

建议在内部落成 `ArtifactEditRequest`，避免 runtime 在后续阶段重复拆解自然语言。

### 6.3 结构定位

第一阶段按结构定位，不做任意文本片段定位。

大纲支持定位：
- 第 N 部分
- 指定标题项
- 摘要项
- 结论项

正文支持定位：
- 摘要
- 引言
- 第 N 部分
- 指定章节标题
- 结论

为此需要一层报告结构解析器，将 markdown 或 outline 数据转成结构节点列表，再把用户修改意图映射到节点。

定位歧义处理：
- 当“第二部分”“最后一段”等表达无法稳定映射到唯一节点时，不应直接盲改
- 优先返回明确的定位说明或确认提示
- 至少要能指出系统当前准备修改的节点标题或节点类型

### 6.4 生成策略

根据意图分三类：
- 局部修改大纲节点，产出新大纲版本
- 局部修改正文节点，产出新正文版本
- 基于指定大纲版本重新生成一份新正文

局部修改不等于简单字符串替换，应由模型基于：
- 原节点内容
- 上下文结构
- 用户修改指令
- 原生成状态
来重新生成目标节点或目标章节。

### 6.5 版本链

每次修改必须生成新版本，不覆盖旧版本。

建议版本元数据：
- `root_artifact_id`
- `parent_artifact_id`
- `version_id`
- `version_number`
- `derived_from_action`
- `derived_from_reference`
- `created_at`

新版本写入：
- 对话 artifacts
- 会话状态
- 课程资源
- 右侧生成物恢复链路

展示约束：
- 列表排序和版本树关系分开处理
- 第一阶段列表按最新版本倒序
- 版本关系通过 `v2（基于 v1 修改）` 这类副标题显式展示

## 7. 生成状态结构

正文版本必须携带 `ReportGenerationState`，用于后续再编辑和再生成。

最少要能回答这些问题：
- 这份正文围绕什么主题生成
- 重点是什么
- 长度要求是什么
- 风格要求是什么
- 引用了哪些来源
- 是基于哪一版大纲或哪一版正文生成的
- 生成时间是什么时候
- 这是首次生成还是修订生成

该状态应与正文 artifact 一起持久化，而不是只存在前端内存。

状态承接要求：
- 当前引用的 artifact 应同步进入 `active_context`
- 至少更新 `active_artifact_id`、`active_artifact_type`
- 可增加 `active_reference_mode = artifact_edit`
- 这样刷新页面、继续对话或中途插入其他消息后，系统仍能知道当前焦点对象

## 8. 基于生成物提问

建议现在就纳入底层设计，但作为第二阶段能力。

原因：
- 用户在“添加到对话”后，不只会说“修改”，也会说“解释第二部分为什么这样写”“总结这份报告的核心观点”
- 该能力与引用卡片、artifact 注入、结构定位共享底座

第一阶段要求：
- 请求协议和引用状态设计要兼容后续提问能力
- 不要求完整实现 `ask_about_artifact`

第一阶段最小回退：
- 当前存在引用卡片
- 未识别到明确编辑动作
- 但用户明显在围绕该 artifact 提问

此时不应直接掉回普通聊天，可返回一条 graceful fallback：
- 告知当前已引用的是报告大纲或正文
- 告知系统既可以继续修改，也可以先解释某一部分
- 引导用户指定要修改或提问的结构节点

## 9. 错误处理

应覆盖以下情形：
- 引用的 artifact 已被删除
- 当前引用与当前课程不匹配
- 结构节点无法唯一定位
- 用户指令同时要求多个互斥操作
- 用户要求修改正文，但引用的是大纲
- 基于大纲重生成正文时缺少可用大纲内容

失败时应返回明确提示，而不是静默回退成普通聊天。

## 10. 测试范围

### 10.1 前端
- 添加到对话后显示引用卡片
- 发送消息时带上引用结构，不复制全文进输入框
- 替换引用、移除引用、刷新恢复
- 新版本生成后右侧列表置顶
- 版本号和来源关系展示正确

### 10.2 后端
- 引用大纲后的结构化修改意图识别
- 引用正文后的结构化修改意图识别
- 正确定位摘要、结论、第 N 部分、指定标题
- 基于修改后的大纲生成新正文
- 新版本元数据和生成状态落库
- 课程资源同步新增新版本
- 定位歧义时返回明确提示
- graceful fallback 不直接掉回普通聊天

### 10.3 集成
- 从右侧引用大纲 -> 修改 -> 生成新大纲版本
- 从右侧引用新大纲 -> 重新生成新正文
- 从右侧引用正文 -> 修改结论 -> 生成新正文版本
- 刷新前端后版本链仍可恢复

## 11. 分阶段实施建议

### 阶段一
- 引用卡片
- 报告大纲/正文引用协议
- 结构化修改意图识别
- 新版本生成与持久化
- 正文生成状态结构
- 收口 MVP 为 3 条主链：
- 引用大纲 -> 修改某一部分 -> 生成新大纲版本
- 引用大纲 -> 基于此重新生成一版新正文
- 引用正文 -> 修改摘要或结论 -> 生成新正文版本

### 阶段二
- 基于生成物提问
- 版本链更完整的 UI 呈现
- 更精细的结构节点定位和冲突处理

## 12. 验收标准

第一阶段完成后，应满足：
- 用户可从右侧将报告大纲或正文加入当前对话
- 用户输入结构化修改指令后，系统能识别并修改正确目标
- 修改结果生成新版本，不覆盖原版本
- 新版本出现在右侧列表最上方，并同步到课程资源
- 正文版本具备完整可追踪的生成状态结构
- 基于修改后的大纲可以生成新的报告正文
