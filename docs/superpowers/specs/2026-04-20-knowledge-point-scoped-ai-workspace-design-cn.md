# 知识点作用域 AI 工作台设计

## 1. 目标

将当前“按课程组织”的 AI 工作台升级为“课程总目录 + 知识点目录”双层作用域工作台。

升级后：

- 用户直接进入课程 AI 工作台时，默认进入课程总目录模式
- 用户从知识图谱的具体知识点点击“和 AI 聊一聊”时，进入对应知识点模式
- 聊天上下文、RAG 检索、个人知识库、历史会话、生成物列表都跟随当前作用域切换
- 课程总目录模式支持聚合查看课程级数据和所有知识点数据
- 聚合列表采用分批加载，避免一次性加载过多内容

## 2. 范围

本次设计聚焦教师端 AI 工作台的作用域切换与数据归属重构。

在范围内：

- 为 AI 工作台引入“课程总目录模式”和“知识点模式”
- 支持从知识图谱节点跳转到 AI 工作台并携带知识点上下文
- 将聊天会话、知识库文档、生成物、历史记录归属到课程级或知识点级
- 为课程总目录模式提供聚合视图
- 为历史会话列表和生成物列表引入按批次加载机制
- 定义父知识点命中子知识点的检索范围规则
- 明确旧数据保留策略

不在范围内：

- 重构知识图谱结构本身
- 自动将旧数据批量迁移到知识点目录
- 重做 DeepSearch、通用 RAG 底层引擎的存储格式
- 在本期引入复杂筛选器，如按时间、类型、创建人二次过滤
- 为课程总目录聚合视图增加无限滚动；本期采用显式“加载更多”

## 3. 当前问题

当前系统中的 AI 工作台主要围绕课程维度运行：

- 聊天请求主要依赖 `course_id + selected_doc_ids + conversation_id`
- 历史会话列表默认按用户维度返回，没有知识点一级隔离
- 右侧生成物区域更偏向当前会话和课程级资源，不具备知识点聚合能力
- 课程知识库接口和前端状态默认只区分“课程是否已选”，不区分知识点归属
- 知识图谱页面虽然已有节点详情和节点级简易问答，但还没有把节点变成 AI 工作台中的一等上下文

这会导致三个核心问题：

1. 用户围绕某个具体知识点发起问答时，检索范围过大，容易混入整门课程其他主题内容。
2. 个人文档、历史会话、生成物都无法天然归属到具体知识点，后续复用和回看成本高。
3. 课程总目录与知识点目录没有清晰边界，既不利于精确问答，也不利于教师按知识点组织教学资产。

## 4. 设计结论

推荐使用“显式作用域”方案。

系统中的 AI 工作台在任意时刻都工作在一个明确的 scope 下：

- 课程总目录作用域
- 某个知识点作用域

所有核心数据都增加统一归属字段：

- `scope_type`: `course` 或 `knowledge_point`
- `scope_id`: 当 `scope_type=course` 时为空或固定为课程根作用域标识；当 `scope_type=knowledge_point` 时为具体知识点 ID
- `course_id`: 所有数据仍然保留课程归属

前端不再只传 `course_id`，而是传“当前作用域上下文”；后端不再只按课程处理，而是先解析作用域，再决定：

- 会话写入到哪里
- 历史记录读取哪些数据
- 检索应加载哪些文档
- 生成物该挂到哪个目录

## 5. 作用域模型

### 5.1 课程总目录模式

进入方式：

- 用户直接进入课程 AI 工作台
- 用户在知识点模式下主动切回课程总目录

语义：

- 这是课程级顶层作用域，不属于任何具体知识点
- 原有历史遗留的课程级数据保留在这里
- 同时它也是一个聚合视图，能够汇总查看所有知识点数据

在课程总目录模式下：

- 聊天检索范围覆盖“课程级文档 + 所有知识点文档”
- 历史对话列表展示课程级会话和所有知识点会话的聚合结果
- 生成物列表展示课程级生成物和所有知识点生成物的聚合结果
- 个人知识库区域展示课程级文档和各知识点文档的聚合结果

### 5.2 知识点模式

进入方式：

- 用户在知识图谱中选中某个知识点后点击“和 AI 聊一聊”

语义：

- 当前工作台绑定到一个具体知识点
- 所有核心能力都围绕这个知识点展开

在知识点模式下：

- 聊天上下文绑定当前 `knowledge_point_id`
- 历史会话仅展示该知识点下的会话
- 生成物列表展示该知识点历史上所有会话生成过的内容
- 个人知识库仅加载归属于该知识点的文档
- 检索范围不再是整门课程，而是当前知识点范围

### 5.3 父知识点规则

如果当前进入的是父知识点，则其作用域不是只覆盖父节点本身，而是覆盖：

- 当前父节点
- 该父节点的所有子孙知识点

这条规则仅影响该知识点作用域的读取与检索范围，不要求把子节点数据物理迁移到父节点下。

换句话说，父知识点模式是“逻辑聚合读取”，不是“数据复制归档”。

## 6. 数据归属规则

### 6.1 历史旧数据

旧数据不迁移。

已有只按课程组织的数据继续保留在课程总目录下：

- 课程级历史会话
- 课程级个人知识库文档
- 课程级生成物

这些数据：

- 不属于任何知识点
- 在知识点模式下不自动混入
- 在课程总目录模式下可以继续看到

### 6.2 新增会话

新会话创建时必须记录：

- `course_id`
- `scope_type`
- `scope_id`

规则：

- 在课程总目录模式下创建的会话，归属课程总目录
- 在知识点模式下创建的会话，归属对应知识点

### 6.3 新增个人文档

用户导入个人文档时，必须携带当前作用域。

规则：

- 在课程总目录模式下导入，文档归属课程总目录
- 在知识点模式下导入，文档归属当前知识点
- 不同知识点之间的文档不能互相加载

### 6.4 新增生成物

所有生成物在创建时继承当前会话作用域。

规则：

- 若会话归属课程总目录，则生成物归属课程总目录
- 若会话归属知识点，则生成物归属对应知识点

这样可以保证右侧生成物列表按作用域聚合时，不需要猜测生成物来源。

## 7. 检索规则

### 7.1 课程总目录模式

聊天发起检索时，检索范围覆盖：

- 课程级文档
- 所有知识点文档

这是一种课程级聚合检索。

该模式适合：

- 教师站在课程全局问问题
- 不确定问题属于哪个知识点
- 需要跨知识点综合比较和组织教学内容

### 7.2 知识点模式

聊天发起检索时，检索范围仅覆盖当前知识点作用域。

如果当前知识点是叶子节点，则检索：

- 当前知识点自己的文档

如果当前知识点是父节点，则检索：

- 当前父节点文档
- 所有子孙知识点文档

知识点模式下不应默认混入课程总目录文档，除非后续产品另行定义一个显式的“附带课程级资料”开关。本期不设计该开关。

## 8. 列表展示规则

### 8.1 历史会话列表

课程总目录模式：

- 展示课程级会话和所有知识点会话的聚合结果

知识点模式：

- 仅展示当前知识点作用域下的历史会话
- 如果是父知识点，则展示该父节点和所有子孙节点下的会话聚合结果

### 8.2 生成物列表

课程总目录模式：

- 展示课程级生成物和所有知识点生成物的聚合结果

知识点模式：

- 展示当前知识点历史上所有会话生成过的内容
- 不是只展示当前会话生成物
- 如果是父知识点，则展示该父节点和所有子孙节点下的生成物聚合结果

### 8.3 个人知识库列表

课程总目录模式：

- 展示课程级文档与所有知识点文档的聚合结果

知识点模式：

- 仅展示当前知识点作用域下的文档
- 如果是父知识点，则展示该父节点和所有子孙节点下的文档聚合结果

## 9. 分页与加载策略

课程总目录模式下的聚合数据可能非常大，必须显式分批加载。

本期统一规则：

- 默认先加载 20 条
- 点击“加载更多”后，再加载下一组 20 条
- 后端接口要支持显式分页参数，例如 `offset + limit` 或 `cursor + limit`

优先要求分批加载的列表：

- 历史会话列表
- 生成物列表

知识点模式下，如果列表规模也可能变大，建议直接沿用相同分页协议，避免前后端维护两套读取逻辑。

本期不采用无限滚动，原因是：

- 课程总目录聚合视图语义复杂
- 教师需要明确知道当前加载到第几批
- “加载更多”更容易与作用域切换、筛选和调试共存

## 10. 前端设计

### 10.1 工作台上下文

AI 工作台需要新增统一作用域上下文，例如：

```ts
type WorkspaceScope =
  | { scopeType: 'course'; scopeId: null; courseId: string }
  | { scopeType: 'knowledge_point'; scopeId: string; courseId: string };
```

该上下文至少需要被以下区域消费：

- 左侧知识源区域
- 中间聊天区域
- 右侧生成物区域
- 顶部当前上下文展示条

### 10.2 从知识图谱跳转

知识图谱节点详情区新增“和 AI 聊一聊”入口。

点击后：

- 跳转到课程 AI 工作台
- 携带 `course_id`
- 携带 `scope_type=knowledge_point`
- 携带 `scope_id=<selected_node_id>`
- 可选携带节点标题用于前端首屏展示

### 10.3 顶部上下文栏

当前工作台顶部上下文栏应明确显示：

- 当前课程
- 当前作用域

推荐表现：

- 课程总目录模式：显示“课程总目录”
- 知识点模式：显示知识点名称

如果是父知识点，可额外显示辅助文案，如“覆盖子知识点内容”。

### 10.4 左侧知识源

左侧知识源不再只按课程读取数据，而是按当前作用域读取。

课程总目录模式：

- 显示课程级文档和所有知识点文档的聚合视图

知识点模式：

- 仅显示当前知识点作用域文档

导入文档时：

- 自动归属到当前作用域
- UI 上应明确提示“将导入到课程总目录”或“将导入到当前知识点”

### 10.5 中间聊天

聊天请求必须携带作用域上下文。

至少包括：

- `course_id`
- `scope_type`
- `scope_id`

聊天历史列表切换时，也必须用相同作用域参数请求数据，避免用户在知识点模式下看到课程总目录会话。

### 10.6 右侧生成物

右侧生成物列表不能再只依赖当前会话，而应按作用域读取聚合结果。

课程总目录模式：

- 读取课程总目录聚合生成物列表
- 首次加载 20 条
- 点击按钮继续加载下一组

知识点模式：

- 读取该知识点聚合生成物列表
- 也建议复用同一套分页协议

## 11. 后端设计

### 11.1 会话接口

聊天请求模型需要增加作用域字段。

推荐新增：

- `scope_type: "course" | "knowledge_point"`
- `scope_id: string | null`

会话持久化时，把这两个字段写入会话状态和可查询索引中。

推荐读取接口支持过滤：

- `course_id`
- `scope_type`
- `scope_id`
- `aggregate`
- `limit`
- `offset` 或 `cursor`

### 11.2 知识库接口

课程知识库接口应扩展为按作用域增删查。

推荐支持：

- 列表查询时按作用域读取
- 上传文档时写入作用域归属
- 课程总目录模式下支持聚合读取

知识点模式下，如果当前 scope 为父节点，则后端负责计算子孙节点集合并执行聚合查询，避免前端手工拼接多个请求。

### 11.3 生成物接口

课程材料或生成物接口需要支持两个维度：

- 写入时继承当前作用域
- 查询时按作用域返回

推荐查询能力：

- `scope_type=course` 且 `aggregate=true` 时，返回课程级 + 所有知识点聚合结果
- `scope_type=knowledge_point` 时，返回当前知识点或其子树范围结果

### 11.4 知识点子树解析

后端需要提供统一子树解析能力：

- 输入 `course_id + knowledge_point_id`
- 返回该节点及其所有子孙节点 ID 集合

这套逻辑可被以下模块复用：

- 聊天检索
- 历史会话查询
- 文档查询
- 生成物查询

## 12. 推荐数据模型

下面是本期推荐的最小归属字段集合。

### 12.1 会话

```json
{
  "conversation_id": "conv-xxx",
  "course_id": "computational-thinking",
  "scope_type": "knowledge_point",
  "scope_id": "node-123",
  "scope_label": "算法复杂度"
}
```

### 12.2 知识库文档

```json
{
  "id": "doc-xxx",
  "course_id": "computational-thinking",
  "scope_type": "knowledge_point",
  "scope_id": "node-123"
}
```

### 12.3 生成物

```json
{
  "material_id": "report-xxx",
  "course_id": "computational-thinking",
  "scope_type": "knowledge_point",
  "scope_id": "node-123",
  "conversation_id": "conv-xxx"
}
```

对于课程总目录数据：

```json
{
  "scope_type": "course",
  "scope_id": null
}
```

## 13. 接口建议

以下为推荐接口形态，具体路径可按现有结构调整。

### 13.1 聊天请求

```json
{
  "question": "什么是时间复杂度？",
  "conversation_id": "conv-xxx",
  "course_id": "computational-thinking",
  "scope_type": "knowledge_point",
  "scope_id": "node-123",
  "selected_doc_ids": []
}
```

### 13.2 历史会话列表

```http
GET /api/chat/conversations?course_id=computational-thinking&scope_type=course&aggregate=true&limit=20&offset=0
```

```http
GET /api/chat/conversations?course_id=computational-thinking&scope_type=knowledge_point&scope_id=node-123&limit=20&offset=0
```

### 13.3 生成物列表

```http
GET /api/courses/{course_id}/materials?scope_type=course&aggregate=true&limit=20&offset=0
```

```http
GET /api/courses/{course_id}/materials?scope_type=knowledge_point&scope_id=node-123&limit=20&offset=0
```

### 13.4 知识库文档列表

```http
GET /api/courses/{course_id}/knowledge-base/documents?scope_type=course&aggregate=true
```

```http
GET /api/courses/{course_id}/knowledge-base/documents?scope_type=knowledge_point&scope_id=node-123
```

### 13.5 文档上传

推荐让上传接口支持以下字段：

```json
{
  "scope_type": "knowledge_point",
  "scope_id": "node-123"
}
```

## 14. 错误处理

返回 `404` 当：

- 课程不存在
- 指定知识点不存在

返回 `400` 当：

- `scope_type` 非法
- `scope_type=knowledge_point` 但缺少 `scope_id`
- `scope_type=course` 却错误传入不兼容参数

返回 `403` 或 `404` 当：

- 当前用户无权访问对应课程或作用域

如果知识点已被删除但仍有旧数据挂载到该知识点：

- 后端应允许这些数据被读取到“异常归属”结果中，或者先按课程总目录兜底显示
- 本期更推荐保留记录并在日志中显式告警，不要静默丢失数据

## 15. 测试建议

### 15.1 前端

- 从课程页直接进入工作台，默认进入课程总目录模式
- 从知识图谱节点点击进入后，工作台正确显示知识点模式
- 作用域切换后，历史会话列表、知识源列表、生成物列表同步刷新
- 课程总目录模式下，“加载更多”每次追加 20 条
- 知识点模式下，不混入课程总目录旧数据

### 15.2 后端

- 会话写入正确保存 `scope_type/scope_id`
- 课程总目录模式查询可返回课程级 + 知识点级聚合结果
- 知识点模式查询只返回当前知识点或其子树数据
- 父知识点检索命中子知识点文档
- 上传文档和生成物创建时正确继承当前作用域
- 旧课程级数据在知识点模式下不会错误暴露

## 16. 实施建议

建议按下面顺序推进：

1. 后端先补齐作用域字段和查询协议  
   先让会话、文档、生成物都能稳定写入和按作用域读取。

2. 前端增加统一作用域上下文  
   让 AI 工作台三栏都从统一的 scope 读取。

3. 接入知识图谱跳转入口  
   完成从知识图谱到 AI 工作台的知识点定向进入。

4. 接入课程总目录聚合分页  
   优先完成历史会话和生成物列表的 20 条分批加载。

5. 最后收口 RAG 检索范围  
   确保课程总目录模式和知识点模式分别命中正确文档集合。

## 17. 总结

本次改造的本质不是单纯新增一个“知识点按钮”，而是把 AI 工作台从“课程单作用域系统”升级为“课程总目录 + 知识点目录双作用域系统”。

升级后：

- 教师可以站在课程全局工作
- 也可以围绕具体知识点进行隔离式问答和资产沉淀
- 历史对话、个人知识库、生成物都能形成清晰的知识点归档关系
- 课程总目录又保留了课程级统览与聚合管理能力

这套设计同时兼顾了旧数据兼容、知识点精细化组织以及后续扩展性，是当前需求下最稳妥的演进路径。
