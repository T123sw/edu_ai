# 系统现状与优化路线图

日期：2026-04-28

本文基于对当前项目代码的静态扫描，重点覆盖你提出的 6 个优化方向：资源类型扩展、图片融入报告/PPT、后台任务并行、报告与对话性能定位、从工作流走向 Agent、记忆模块建设。

## 1. 当前系统概览

### 1.1 前后端与核心目录

当前项目主要由以下部分组成：

- `Edu_AI/src`：React + Vite 前端，教师工作台、课程资源、AI 工作区、知识库、生成文件预览等都在这里。
- `Edu_AI/api/Edu_AI/app/chat`：当前 AI 对话与资源生成的主链路，包括 v2 API、路由、编排、工作流、持久化、记忆抽取、报告/PPT/教案/测验生成。
- `Edu_AI/api/Edu_AI/app/pipeline`：爬取、解析、切分等资料处理任务，已有简单异步任务模型和文件任务存储。
- `Edu_AI/api/Edu_AI/app/blog_agent`：博客生成 Agent/工作流，使用 `BackgroundTasks` 启动后台任务，支持章节和大纲人工确认。
- `Edu_AI/api/Edu_AI/app/speech`：语音转写链路，目前以百度语音识别为主。
- `Edu_AI/api/Edu_AI/rag_v2`：RAG v2，支持文档、图片 chunk、图片 embedding 回退、图片 source 返回等。
- `Edu_AI/api/Edu_AI/html2ppt`：PPT 生成引擎，支持 content protocol、Media 块、本地化媒体资源、导出 PPTX。
- `EduAgent`：较独立的深度搜索/工具型 Agent 原型或旁路模块。

### 1.2 主对话与资源生成链路

当前 v2 对话主入口是：

`/api/chat/v2/reply` 或 `/api/chat/v2/stream`

核心调用路径：

`routes_v2.py -> ReplyServiceV2 -> MainOrchestrator -> decide_route -> FastChatRuntime 或 WorkflowRuntime`

其中：

- 普通对话走 `FastChatRuntime`。
- 报告走 `ReportWorkflowRuntime + universal_report_engine`。
- PPT 走 `PptWorkflowRuntime + PptPostOutlineExecutor + html2ppt`。
- 教案走 `LessonPlanWorkflowRuntime`。
- 测验走 `QuizWorkflowRuntime`。
- 知识库直出资源另有 direct endpoint，例如 report/direct、ppt/outline、ppt/generate、quiz/direct、game/direct。

整体已经从早期单体 chat service 演进成了“路由 + 快速对话 + 多资源工作流”的结构，但本质仍是强流程编排，而不是真正的开放式 Agent。

## 2. 已具备的能力

### 2.1 资源类型

已完成或部分完成：

- 报告：对话内 workflow、知识库 direct 生成、报告编辑、报告材料持久化。
- PPT：大纲生成、人工确认、content markdown、html2ppt 导出、PPT 编辑/轮询、知识库 direct 生成。
- 教案：workflow 与知识库入口已接入。
- 测验：workflow 与知识库 direct 生成已接入。
- 小游戏：有 direct game service，并保存 HTML artifact。
- 博客：独立 `blog_agent`，具备后台任务、分阶段确认、最终材料持久化。
- 音频：前端已有音频概览入口，后端目前更偏语音输入转写，不是完整音频资源生成。
- AI 讲师/视频：已有 AI Lecturer、LiveTalking、视频检索与课程资源播放相关模块。

### 2.2 多模态与图片基础能力

当前基础设施已经比较接近“可把图片融入资源”：

- 对话上传图片：`routes_v2.py` 中有 `/images/upload`，图片会进入 `storage/chat_images`，并返回 `storage_path` 与 `image_url`。
- 对话模型输入图片：`FastChatRuntime` 会把用户图片、视频抽帧、RAG 图片 source 编码成 `image_url` block 传给模型。
- RAG 图片：`rag_v2` 会从 Markdown/Docling 中提取图片 chunk，记录 `modality=image`、`image_path`、`image_url`、尺寸等元数据，并可在检索结果里返回。
- html2ppt 媒体：`html2ppt/src/lib/media-assets.js` 已支持 content protocol 中的 Media 块，能下载/复制图片视频并注入 `Local-Path`。

缺口在于：报告/PPT 的生成器还没有统一接收“可用媒体清单”，也没有稳定地产出带媒体引用的报告 Markdown 或 PPT content markdown。

## 3. 当前主要不足

### 3.1 工作流阻塞请求，缺少统一后台任务系统

当前不同模块的后台处理方式不统一：

- `app/pipeline/tasks.py` 使用 `asyncio.create_task` 和文件任务存储，适合单进程 MVP。
- `app/blog_agent/routes.py` 使用 FastAPI `BackgroundTasks`。
- PPT 的 `PptPostOutlineExecutor.execute()` 会在请求内生成 content markdown、提交 html2ppt job，并同步轮询到完成或超时。
- 报告 workflow 也在请求内完成正文生成。
- 普通对话 stream 虽然支持 SSE，但 workflow 分支实际是先同步跑完，再把结果切片吐出。

这会导致：

- 一个长任务占用请求处理线程/worker，用户体感像“后台执行任务时不能继续别的任务”。
- 任务状态分散在 conversation state、blog task state、pipeline task store、html2ppt job store 中。
- 缺少统一取消、重试、恢复、并发数控制、超时、优先级和任务观测。

### 3.2 报告正文生成调用模型次数过多

报告正文慢的核心位置在：

- `app/chat/agents/universal_report_engine.py`
- `app/chat/tools/agent_tools.py`
- `app/chat/agents/report_generation.py`

当前流程是：

1. 槽位抽取：可能调用一次 LLM。
2. focus 评估：可能调用一次 LLM。
3. 追问/软确认：可能调用一次 LLM 或模板。
4. 大纲生成：调用一次 LLM。
5. 正文生成：`build_report_markdown()` 按章节和小节循环调用 LLM。
6. 每个小节最多重试 2 次，失败时还有 `time.sleep(0.3)`。
7. 如果存在 `REPORT_STITCH_SUMMARY_PROMPT`，最后再调用一次 LLM 做整体摘要/拼接。

因此正文阶段调用次数大致是：

`章节小节总数 * (1 + 重试次数) + 1 次总结`

如果大纲是 3 章、每章 2-3 小节，就是 6-9 次正文调用；失败重试后可能变成 12-27 次，再加前置抽取、评估、大纲调用。慢主要来自调用模型次数，而不是单纯的数据处理。

当前已有的耗时记录不足：

- `universal_report_engine.generator_node()` 只记录 generator 总耗时。
- `report_generation.build_report_markdown()` 没有把每次小节 LLM 调用耗时、重试次数、模型名、token 量、失败原因写进结构化 trace。
- 普通对话 `FastChatRuntime` 没有记录 RAG、Web、视频检索、图片编码、模型首 token、总生成耗时。

### 3.3 普通对话速度慢的潜在原因

`FastChatRuntime._prepare_generation()` 当前按顺序执行：

1. RAG 检索。
2. Web deepsearch。
3. 视频检索。
4. 图片/视频转 data URL。
5. 构造历史消息与上下文。
6. 模型调用。

如果同时打开 RAG、Web、视频，检索阶段是串行的；视频抽帧还可能触发 ffmpeg。`ChatModelGateway` 使用同步 `requests`，SSE 也在同步 generator 里调用，虽然能流式输出，但无法很好利用异步 I/O。

### 3.4 资源生成形态不统一

报告、PPT、教案、测验、博客、游戏分别有不同入口和数据结构：

- workflow 资源挂在对话状态里。
- direct 资源从知识库入口生成。
- 博客是单独 task state。
- PPT 有 html2ppt job。
- pipeline 有 crawl/parse/chunk task。

这使得前端要分别适配多套状态、轮询、预览和持久化逻辑。后端也难以共享任务队列、进度事件、模型调用 trace、资源版本管理、资源引用编辑。

### 3.5 Agent 能力还停留在“固定流程”

当前 `MainOrchestrator` 的决策逻辑是 route rules：

`fast` 或某个确定 workflow。

报告和 PPT 虽然使用 LangGraph/工作流节点，但节点路径基本固定，工具调用也是封装在流程内。它更像“多阶段生成向导”，不是具备以下能力的 Agent：

- 根据目标自主规划多步任务。
- 动态选择工具、检索、生成、审校、再生成。
- 观察中间结果并决定是否继续。
- 把长任务拆成可恢复子任务。
- 在质量和速度之间根据场景动态取舍。

### 3.6 记忆模块有雏形，但还不是完整 Agent Memory

当前已有：

- `ConversationStoreAdapter` 保存消息、workflow state、active artifact、capability policy。
- `ConversationMemoryExtractor` 从对话和结果中抽取 topics、goals、constraints、facts、evidence、teaching issues、student signals。
- `ConversationMemoryCompactor` 做规则压缩。
- `GenerationContextBuilder` 从 summary、memory、recent messages、sources、artifacts 构造资源生成上下文。
- `LLMEnhancementRouter` 已预留 LLM 增强入口，但默认关闭。

不足：

- 主要是 conversation-scoped memory，缺少跨课程、跨用户、跨资源的层级记忆。
- 记忆抽取以规则为主，中文规则里存在较多不可读文案风险，维护成本高。
- 缺少“写入策略”：哪些信息是用户长期偏好、课程事实、任务状态、资源事实、临时上下文，需要不同 TTL 和可信度。
- 缺少“检索策略”：生成报告/PPT 时如何按任务目标取相关记忆，而不是只靠最近消息和简单相关性。
- 缺少记忆可解释、可编辑、可删除的管理界面和审计日志。

## 4. 面向 6 个方向的优化建议

### 4.1 资源类型扩展：音频、博客等

建议建立统一资源生成协议，而不是为每个资源继续堆独立入口。

统一抽象：

- `ResourceType`：report、ppt、lesson_plan、quiz、blog、audio、game、mindmap、video_script。
- `ResourceRequest`：课程、知识点范围、选中文档、目标用户、输出格式、质量档位、是否允许 Web/RAG/图片。
- `ResourceJob`：job_id、resource_type、status、phase、progress、artifacts、trace、errors。
- `Artifact`：统一字段 `artifact_id/type/title/content/generation_state/version/media_assets/sources`。

音频方向可以分两层：

- 第一阶段：音频概览文本稿、播客脚本、TTS 任务记录、音频文件 artifact。
- 第二阶段：多角色播客、课件同步旁白、AI 讲师视频口播脚本、字幕与时间轴。

博客方向建议并入统一 ResourceJob：

- 保留现有 HITL 的章节确认和大纲确认。
- 把 blog task state 接入统一任务表。
- 把每段正文生成 trace 纳入模型调用观测。

### 4.2 图片融入报告与 PPT

建议建设一个 `MediaAssetManifest`，作为 RAG/上传/生成资源之间的桥。

数据结构建议：

```json
{
  "asset_id": "img_0001",
  "source": "rag|upload|generated|web",
  "modality": "image",
  "title": "图片标题",
  "caption": "建议图注",
  "storage_path": "...",
  "public_url": "/api/rag/image?...",
  "mime_type": "image/png",
  "width": 1024,
  "height": 768,
  "related_topics": ["..."],
  "source_ref": "文档名/页码/URL",
  "license": "unknown|user_upload|public|generated",
  "confidence": "high|medium|low"
}
```

落地路径：

1. RAG 查询返回图片 source 时，后端统一转成 `MediaAssetManifest`。
2. 用户上传图片也进入同一 manifest。
3. 报告生成时，把 manifest 注入 prompt，要求模型在合适章节插入 `![caption](url)`，同时保存 `media_assets`。
4. PPT 生成时，把 manifest 注入 `PptContentMarkdownGenerator`，要求模型生成 content protocol 的 `Media` block。
5. html2ppt 已能本地化 Media 资源，重点是让内容生成阶段输出合法 Media 块。
6. 前端预览报告/PPT 时显示图片引用、来源和可替换入口。

短期优先做 PPT，因为 html2ppt 已支持 Media 块，收益最快。

### 4.3 并行与后台任务

建议引入统一任务运行时，优先级高于继续扩展资源类型。

推荐阶段：

第一阶段，最小可用：

- 新增统一 `jobs` 模块，使用本地 SQLite 或现有文件存储加锁。
- 所有长任务返回 `job_id`，请求立即返回。
- 前端通过 `/jobs/{job_id}` 轮询，或 `/jobs/{job_id}/events` SSE 订阅。
- PPT 生成、报告正文、博客生成先迁移。

第二阶段，生产化：

- 引入 Redis + RQ/Celery/Dramatiq 任一队列。
- worker 进程独立于 API 进程。
- 支持并发数、队列优先级、取消、重试、超时、死信。
- 模型调用限流与 per-user 配额。

第三阶段，Agent 任务运行时：

- 每个 ResourceJob 内部拆成 step runs。
- step 支持恢复、跳过、重试、人工确认。
- 对外统一 status、progress、artifact events。

必须先迁移的阻塞点：

- `PptPostOutlineExecutor._wait_for_job_terminal_state()` 当前同步轮询 html2ppt。
- `ReportWorkflowRuntime` 正文生成当前同步跑完。
- `FastChatRuntime` 的 RAG/Web/Video 检索可并发执行。

### 4.4 性能定位与提速

建议先做“观测”，再做“重构”。否则很容易不知道慢在哪里。

统一 trace 字段：

```json
{
  "trace_id": "uuid",
  "route": "fast|workflow|direct",
  "resource_type": "report",
  "timings": {
    "context_build_ms": 12,
    "rag_ms": 480,
    "web_ms": 0,
    "media_prepare_ms": 30,
    "llm_total_ms": 8200,
    "postprocess_ms": 40,
    "persist_ms": 15,
    "total_ms": 8800
  },
  "llm_calls": [
    {
      "stage": "report.section",
      "model": "qwen3.5-plus",
      "duration_ms": 2100,
      "input_chars": 3200,
      "output_chars": 900,
      "retry": 0,
      "ok": true
    }
  ]
}
```

报告提速方向：

- 正文从“小节多次调用”改成“章节级生成”或“一次生成完整报告 + 结构化审校”。
- 对长报告保留分段生成，但并行生成章节；最后再做一次轻量拼接。
- 为不同长度设置档位：
  - fast：一次大纲 + 一次正文。
  - balanced：一次大纲 + 按章节并行正文 + 一次总审校。
  - quality：大纲 + 章节正文 + 证据核对 + 审校。
- 对 slot extraction、focus assessor 等前置 LLM 调用增加规则短路；信息足够时不调用。
- 大纲确认之后再生成正文，避免在用户还没确认时浪费大模型调用。
- 缓存同一 conversation、outline、slots 的正文生成结果，支持断点续跑。

普通对话提速方向：

- RAG、Web、Video 检索并发执行。
- 默认对话只启用必要检索，不要默认视频检索。
- 图片/视频处理使用缓存，视频抽帧已部分缓存，但要记录耗时并避免每次请求重复。
- `ChatModelGateway` 改为 `httpx.AsyncClient`，SSE 使用真正异步流。
- 模型选择分层：普通答疑用快模型；报告/PPT正文用深模型；审校用低温稳定模型；视觉理解用视觉模型。
- 对前端展示优化：先返回 status/meta，再后台运行检索或长任务，避免用户看到空白等待。

### 4.5 从工作流演进到 Agent

建议不要一次性把系统改成“完全自由 Agent”。更稳的路线是“可控 Agent 化”：

第一层：Workflow as Tool

- 现有 report/ppt/quiz/blog workflow 保留。
- Agent 只能把这些 workflow 当工具调用。
- 好处：速度和稳定性最好，迁移风险低。

第二层：Plan-and-Execute Agent

- Agent 先生成任务计划：需要检索什么、生成什么资源、是否需要图片、是否需要人工确认。
- 每个步骤调用受控工具。
- 每步可记录 trace、可恢复、可审计。

第三层：Reflective Agent

- Agent 对生成结果做质量检查：内容完整性、引用是否足够、图片是否匹配、PPT 是否过密。
- 不通过时局部重做，而不是整条链路重跑。

第四层：Multi-Agent

- Planner：拆任务。
- Researcher：RAG/Web/图片素材。
- Writer：生成正文。
- Designer：PPT/视觉布局。
- Reviewer：质量检查。
- Executor：保存/导出/发布。

速度和效果的兼顾原则：

- 普通对话永远走 fast path，不进入重 Agent。
- 用户明确要生成资源时才进入任务 Agent。
- Agent 的每一步都要有预算：最大 LLM 调用次数、最大耗时、最大检索数。
- 先用规则路由决定是否需要 Agent；不要所有请求都让 LLM 做 planner。
- 对重复任务使用模板和缓存，不让 Agent 每次从零规划。

### 4.6 记忆模块建设

建议把记忆拆成 4 层：

1. 短期上下文：最近消息、当前工作流状态、当前 artifact。
2. 任务记忆：某个报告/PPT/blog job 的 slots、计划、草稿、失败点、确认记录。
3. 课程记忆：课程目标、知识点、常用资料、学生画像、教师偏好。
4. 用户长期记忆：输出风格、常用模型、报告长度偏好、PPT 风格、是否偏好图片。

每条记忆建议包含：

```json
{
  "memory_id": "mem_0001",
  "scope": "conversation|job|course|user",
  "type": "preference|fact|constraint|artifact_ref|student_signal|source_evidence",
  "content": "...",
  "source": "user|assistant|rag|tool|system",
  "confidence": 0.0,
  "status": "active|retracted|expired",
  "created_at": "...",
  "updated_at": "...",
  "expires_at": null,
  "source_refs": []
}
```

读取策略：

- 普通对话：短期上下文 + 用户偏好少量注入。
- 报告/PPT：任务记忆 + 课程记忆 + 相关资料证据 + 用户偏好。
- Agent 规划：只读摘要和约束，不塞大量正文。
- 生成正文：读具体证据和 media manifest。

写入策略：

- 用户明确表达的偏好和事实优先写入。
- 模型推断只能写成 hypothesis，不能当 confirmed fact。
- RAG 证据写 external_evidence，要带 source_ref。
- 工作流控制语句不要进入长期记忆。
- 支持用户查看、修改和删除记忆。

当前模块可复用：

- `ConversationMemoryExtractor` 可作为短期规则抽取器。
- `LLMEnhancementRouter` 可打开成可控 LLM 抽取器。
- `GenerationContextBuilder` 可扩展为 MemoryRetriever。
- `conversation_storage` 可先承载 MVP，后续迁移 SQLite/Postgres。

## 5. 建议优先级路线

### P0：先补观测与解除阻塞

目标：知道慢在哪里，并让长任务不再卡住对话。

- 建立统一 trace schema，覆盖 fast chat、report、ppt、blog。
- 包装所有 LLM 调用，记录 stage/model/duration/input/output/retry/error。
- 报告正文生成记录章节/小节级耗时。
- FastChatRuntime 记录 RAG/Web/Video/media/model 首 token/总耗时。
- PPT 生成从同步轮询改成 job 模式。
- 报告正文生成从同步 response 改成 job 模式。

### P1：资源生成统一与图片贯通

目标：让报告/PPT 能稳定使用图片，并统一资源状态。

- 定义 `MediaAssetManifest`。
- RAG 图片 source 和上传图片统一转 manifest。
- PPT content markdown prompt 支持 Media 块。
- 报告 Markdown 支持图片引用和图注。
- 资源 artifact 增加 `media_assets` 字段。
- 前端资源预览支持查看/替换图片。

### P2：报告/PPT 性能优化

目标：把报告和 PPT 生成时间降到可接受范围。

- 报告正文改成按章节并行或一次生成模式。
- 增加质量档位：fast/balanced/quality。
- PPT 大纲、content markdown、html2ppt job 拆成独立 job steps。
- 对 direct report 采用一次生成，对 workflow report 采用可确认/可续跑。
- 对 RAG 检索结果、图片 manifest、outline 做缓存。

### P3：Agent 化

目标：让系统从“固定入口生成资源”变成“能规划、能调用工具、能检查结果”的教学 Agent。

- 把 report/ppt/quiz/blog 变成 Agent tools。
- 增加 planner，但只在复杂生成任务启用。
- 增加 reviewer，对资源质量做结构化验收。
- 支持局部重做：只重写某章节、某页 PPT、某组题。
- 引入预算控制：最多调用次数、最大耗时、最大成本。

### P4：记忆模块完善

目标：让 Agent 能长期理解用户、课程、任务和资源上下文。

- 建立分层 memory store。
- 增加 memory retrieval 策略。
- 引入 LLM 抽取但加 guard 和审计。
- 前端提供记忆查看/管理。
- 把课程级画像、资源偏好、常用输出格式沉淀下来。

## 6. 推荐下一步实施清单

建议先拆成 4 个小项目，每个都能独立验收：

1. 性能观测基座
   - 新增 `LLMCallTracer` 或 `ModelCallObserver`。
   - 包装 `ChatModelGateway.chat/stream_chat`、LangChain `llm.invoke` 调用点。
   - 在 API response trace 中返回耗时摘要。

2. 统一后台 Job
   - 新增 `app/jobs`。
   - 先用 SQLite 或文件锁存储 job。
   - 改造 PPT 生成和报告正文生成。
   - 前端用统一轮询组件显示进度。

3. PPT 图片融入
   - 从 RAG/image upload 生成 `MediaAssetManifest`。
   - 修改 `PptContentMarkdownGenerator` prompt，让它输出 content protocol Media 块。
   - 利用现有 html2ppt `localizeMediaAssets()` 完成导出。

4. 报告正文提速
   - 给报告生成增加 `generation_mode=fast|balanced|quality`。
   - fast：一次完整正文。
   - balanced：章节级并行。
   - quality：章节级 + 最终审校。
   - 保留旧路径作为 fallback。

## 7. 风险与注意事项

- 当前项目已有较多未提交改动，后续实施前建议先明确分支和变更边界。
- 终端读取中多处中文提示词显示为乱码，可能是控制台编码问题，也可能是历史文件编码污染；生成质量强依赖 prompt，可读性和版本管理需要整理。
- 不要一开始就引入完全自由 Agent，否则速度、成本和可控性都会变差。
- 后台队列引入后，必须同时设计状态恢复和幂等，否则 PPT/report 这类长任务容易重复生成。
- 图片进入报告/PPT 后要考虑来源权限、路径安全、导出时可访问性和前端预览鉴权。
- 记忆模块必须支持用户可控删除，尤其是跨课程/跨长期记忆。

## 8. 总体判断

当前系统已经具备较完整的教学资源生成雏形：对话、RAG、报告、PPT、教案、测验、博客、图片/视频输入、PPT 导出都已经有基础能力。真正限制下一阶段体验的不是“能不能生成”，而是三件事：

1. 长任务缺少统一后台运行时，导致串行和阻塞。
2. 缺少全链路性能观测，无法准确判断时间花在模型、检索、媒体处理还是导出。
3. 资源生成仍是固定 workflow，尚未抽象成可组合的 Agent 工具和可复用的任务/记忆体系。

建议下一阶段的主线是：先做观测和 Job，再做图片贯通与报告/PPT提速，最后把稳定的 workflow 包装为受控 Agent tools。这样能兼顾速度、稳定性和未来 Agent 化空间。
