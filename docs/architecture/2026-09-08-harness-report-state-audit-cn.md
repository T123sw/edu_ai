# Harness 报告流程与工作记忆自检

日期：2026-09-08。依据：用户截图 image copy 8.png、对应会话持久化状态和工具事件、当前根角色 / Skill / 工具 / 工作区代码。此次为审查，不改写用户会话，不自动提交其报告。

## 结论

当前报告交互不合格。截图中的重复确认并非大纲遗失：模型两次都理解“开始”并调用 submit_report，但应用只认可三句固定口令，拒绝提交；Skill 与工具错误又要求用户复述口令，形成循环。问题主要是确认规则不一致与工作流状态设计不足，不能笼统归因于模型记忆混乱。

## 已复现的事件链

1. 当前大纲主题“数组的实现”，revision=1，六章，持久化状态 awaiting_approval。
2. 用户第一次“开始”：模型调用 submit_report；返回 approval_required，要求“确认大纲并继续”。
3. 用户第二次“开始”：再次调用 submit_report，收到同一拒绝。
4. 两次前后大纲 ID 与版本不变，job_id=null：没有新建正文任务，也不是任务排队造成重复确认。
5. 初始大纲经历四次工具调用才成功：格式错误、组织参数不一致、格式错误、成功。说明内部契约也存在执行摩擦。

## 发现

### P0：确认规则在不同层相互冲突（已证实）

任务意图解析器 _is_outline_confirmation 接受“开始”“可以”“继续”等。Harness 工具初始化只精确接受 CONFIRM_REPORT_MESSAGES 的三句话；Skill、输出尾注和错误文案均要求固定“确认大纲并继续”。同一用户输入在上层是确认、在执行层却不是确认。

代码：backend/src/app/chat/runtime/planning/task_contract_extractor.py；backend/src/app/chat/harness/tools.py；backend/src/app/chat/harness/skills/edu-report/SKILL.md；backend/src/app/chat/harness/runtime.py。

应统一识别契约：仅当存在当前待确认大纲、用户在推进该任务且没有否定或修改要求时，将自然确认绑定到该大纲版本；不要求固定口令。没有待办时“开始”不能随意启动任务。

### P1：确认只存于单轮对象，缺少独立持久化状态（代码确认，非本次直接原因）

self.approved 是 ReportTools 的内存变量，每轮重新创建；持久化大纲主要从 awaiting_approval 直接跳 submitted，没有独立的 confirmed 状态及确认事件。模型当轮未提交或提交前发生异常时，下一轮不能从明确的确认状态继续。提交前已有 submission_key，业务层也有幂等机制，不能说完全没有防重。

应记录确认对应的 outline_id、revision、用户消息 / request_id、确认状态，并区分待确认、已确认待提交、已提交、失败、已取消。重试同一版本不能再次索要确认；修改版本必须使旧确认失效。

### P1：工作记忆来源分散，缺少统一的任务推进视图（代码确认）

应用层存 generation_workspace / discussion_workspace；Harness 存 active_outline / outlines / jobs / history；上下文另有 summary 与 memory_reference。根角色没有统一的“当前任务阶段、是否已确认、下一合法动作、阻塞原因”视图。已有 current_outline 能解释为何模型记得六章与版本，但不足以协调所有流程状态。

Harness 存储键还包含 scope_id：改变知识点会进入另一份 Harness 会话状态。该隔离有价值，但与“同一对话继续原报告”的恢复逻辑需要明确约定。截图没有显示发生这类状态丢失，不将其列为已复现根因。

### P1：Skill 是流程描述，缺少按状态推进的规则（已证实）

有生成、审阅、版本确认的文字步骤，但没有明确自然确认、已确认未提交恢复、提交异常重试等转移。当前 Skill 反而强化了固定口令。应由应用提供可信任务状态，Skill 按其执行；已确认就提交或恢复，已提交就返回真实任务状态，不能退回等待确认。

### P1：内部组织内容被直接当作大纲展示（已证实）

draft_report_outline 的 Markdown 渲染把 scope、先修、目标、各模块 explanation / example / misconception / check 全部追加，导致用户看到接近正文的内容。这是工具渲染行为，单独缩短提示词不足以解决。

应保留内部组织供正文使用，对外大纲仅展示章节标题与每章 1–3 个短要点；正文解释、例子和练习进入后续正文。此项是用户上一条要求，尚未实施。

### P1：测试覆盖了形式约束，漏掉真实对话验收（已证实）

现有确认测试主要使用固定口令，覆盖版本绑定、模型不能自授确认和重复提交，但没有覆盖截图中的“大纲→开始→正文提交”。此前 123 项后端与 6 项浏览器测试通过，只能证明所覆盖场景，不能证明完整报告交互合格。

## 修复顺序与验收标准

1. 统一上下文相关的自然确认规则；大纲→“开始”只需一次，且只创建一个任务。
2. 持久化确认及任务阶段；提交失败后保留真实状态，重试不重复确认或创建任务。
3. 向根角色提供单一任务状态视图，同步 Skill 与所有提示文案，避免互相矛盾。
4. 分离内部内容组织和用户可见大纲，落实简洁结构展示。
5. 补全连续多轮测试：开始 / 可以 / 继续；否定、修改、换题；版本变更；提交失败再试；重复请求；工作区切换后恢复。
6. 实际验收必须走完大纲→自然确认→任务→正文审阅→交付。不能再仅凭大纲生成成功宣布报告链路合格。

历史用户请求不在审查过程中自动重放。后续修复生效后，应能让当前未提交的大纲通过正常新消息继续，无需重建大纲。
