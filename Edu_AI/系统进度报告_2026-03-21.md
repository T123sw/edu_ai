## 1. 项目总体定位与当前成熟度

`Edu_AI` 当前已经从“单一聊天接口”进化为“教学场景多 Agent + RAG + 深度搜索 + 教学资源生成”的平台形态，具备以下主线能力：

1. **教学对话 Agent（主交互链路）**
   - 支持普通问答、追问补槽、报告生成流程（先大纲后正文）、SSE 流式输出。
2. **RAG 知识库体系（文档与图像）**
   - 支持文档上传/导入、向量索引、混合检索、文档摘要、文档详情与开关检索参与。
3. **多模态注入链路（已打通）**
   - 当检索源含图片时，可将图片转 base64 注入视觉模型重答。
4. **深度搜索链路（EduAgent 集成）**
   - 全网搜集 + 爬取 + 清洗 + 可选入库 RAG。
5. **教学产物生成**
   - 教案、报告、题目、教学博客（含 HITL 两阶段审阅）并可入课程资源。
6. **课程中台能力**
   - 课程信息、课程知识库、课程知识图谱、课程资源管理闭环。

**结论**：系统已具备“可演示、可连续使用、可扩展”的 MVP+ 阶段特征，重点工作可转入“性能稳定性 + 流程一致性 + 体验优化”。

## 3. Agent 架构与状态图流转（重点）

当前对话核心在：`app/chat/service.py`（`ChatService`）+ `app/chat/agents/*`

系统采用 LangGraph 风格多子图组合：

1. **SupervisorAgent（总路由）**
   - 节点：`supervisor`
   - 输出 `response_type`，分流到：
     - `chat_agent`
     - `report_agent`
     - `research_agent`

2. **ChatAgent（对话子图）**
   - `chat -> (tools?)-> chat_tools -> chat`
   - 若无工具调用则结束；有工具调用进入 `chat_tools` 执行后回到 `chat`。

3. **ReportAgent（报告子图）**
   - `extractor -> evaluator -> (ask | outline | generate)`
   - ask/outline/generate 任一完成即结束。

4. **ResearchAgent（研究子图）**
   - `research_tools -> END`
   - 主要是工具执行通道。

### 3.1 状态对象（GraphState）关键字段

定义于 `app/chat/graph_state.py`，关键字段包括：
- 基础：`question`, `conversation_id`, `history`, `conv_state`
- 路由：`intent_category`, `router_reason`, `response_type`
- 对话槽位：`slots`, `expected_slot`, `missing_info`, `ask_counts`
- 报告槽位：`report_slots`, `report_missing`, `report_outline`, `report_outline_pending`, `report_ready`
- 模型：`llm`(planner), `llm_deep`, `vlm`
- 工具开关：`rag_tool_enabled`, `deepsearch_tool_enabled`, `selected_doc_ids`
- 结果：`final_answer`, `agent_monologue`, `report_content`

### 3.2 主路由逻辑（router_node）

路由流程概述：
1. 若会话处于“待澄清”状态，优先走 `generate_content` 相关分支。
2. 否则通过 `IntentRouter` 判定 `chat` or `generate_content`。
3. 若命中“报告意图”，进入 report 流程；否则走 chat/research。

### 3.3 Chat 节点关键行为

`chat_node` 当前已实现：

1. 使用 `ResponsePlanner` 给出回答模式（explain/compare/steps/example/qa）
2. 构建消息并调用可工具化的 LLM
3. 若有 tool call：进入工具节点执行
4. 若无 tool call：
   - 直接取模型文本草稿为 `final_text`
   - 尝试从工具结果中提取图片 `image_path`
   - 如命中图片：构造 multimodal blocks（text + image_url）调用视觉模型重答
   - 如未命中：快速直出文本（已做 fast path）

### 3.4 Report 子图关键机制

- `extractor_node`：抽取本轮新增槽位（支持用户修改/补充）
- `evaluator_node`：判定缺失字段、是否追问、是否输出大纲、是否可生成正文
- `ask_node`：单点追问（防连环问）
- `outline_node`：生成或修改报告大纲（并保留 fallback）
- `generate_node`：按槽位与大纲生成 markdown 正文

**已实现的重要流程约束**：
- “先大纲，确认后正文”的隔离策略
- 对 impatient 用户支持 auto_fill 兜底
- 缺失字段追问计数，避免无限追问

## 4. 模型矩阵与各模块用模

配置源：`core/config.py`

当前是“三脑架构”：

1. **Planner（逻辑脑）**
   - 默认模型：`openai/gpt-5.4-mini`（OpenRouter）
   - 用途：意图路由、回答规划、工具调用决策

2. **Deep（深度文本脑）**
   - 默认模型：`deepseek-chat`
   - 用途：深度回答、报告正文、大纲/生成类文本任务

3. **Vision（视觉脑）**
   - 默认模型：`qwen3.5-plus`
   - 用途：仅在图片注入时触发多模态重答

### 4.1 ChatService 内实际调用策略

在 `chat_stream_with_meta` 初始化状态时：
- `llm` = planner 模型（工具路由）
- `llm_deep` = deep 模型（文本重任务）
- `vlm` = vision 模型（图片场景）

### 4.2 其它模块模型使用

- `new_rag/system.py`：
  - Embedding 走 `EmbeddingClient`（默认 Gemini embedding 兼容接口）
  - RAG 生成回答使用 RAGSystem 内 `_call_llm`（受配置影响）
- `main.py` 的 `/teacher/lesson_plan` `/teacher/report` `/teacher/questions`：
  - 显式使用 `Config.get_deep_model()` 走深度文本模型
- `blog_agent/engine.py`：
  - 通过 `rag_system._call_llm` 生成章节、小标题与正文段落

## 5. RAG 与多模态检索现状

## 5.1 RAG 能力清单

来源：`new_rag/api.py`, `new_rag/system.py`

已具备：
- 文档上传与导入（PDF/DOC/DOCX/TXT/MD）
- 分块与向量化（Chroma）
- 混合检索（向量 + BM25，条件可用）
- 文档列表、摘要、详情、内容查看
- 文档是否参与检索的开关
- 用户 owner 隔离

## 5.2 图片注入链路（已打通）

在 `chat_node` 中已实现：
1. 从 tool message 的 `sources` 中筛选 `modality=image` + `image_path`
2. 读取本地图片并编码 data URL
3. 组装多模态消息给视觉模型
4. 输出日志：
   - `[chat_node_image_inject] sources_images=... injected=...`
   - `[model_select] final_answer_role=vision|deep`

**当前观察建议**：
- 当 `sources_images=0` 时，不代表功能缺失，通常是该问句未命中图片源。
- 验证注入成功需看三项同时出现：
  - `sources_images>0`
  - `injected>0`
  - `final_answer_role=vision`

## 6. 深度搜索（DeepSearch）能力现状

模块：`app/deepsearch.py` + `app/deepsearch_pipeline.py`

流程已完整：
1. 调 EduAgent 深度搜索拿链接
2. 爬虫抓取页面/PDF
3. 内容清洗
4. 可选入库 RAG（`save_to_kb`）

适用场景：
- 本地库无答案、用户要“最新资料”、跨站点资料汇总

## 8. 当前主要风险与技术债

1. **`main.py` 体量过大**
   - 教案/报告/题目与课程资源逻辑高度耦合，维护成本高。
2. **ChatState 字段过多**
   - `GraphState` 复杂度偏高，后续扩展时易引入状态污染。
3. **部分重复/历史代码痕迹**
   - 例如 schema 中重复字段（`course_id` 重复定义），说明需要清理。
4. **提示词与流程逻辑耦合较重**
   - 部分规则依赖 prompt 微调，稳定性受模型版本变化影响。
5. **缺少统一自动化评估与回归测试**
   - 多 Agent + 多模型系统若无评测集，难以量化改动收益。
6. **运维可观测性仍偏日志级**
   - 还未形成系统化指标看板（TTFT、工具命中率、RAG 召回质量等）。

## 9. 下一阶段优化开发方向（建议按优先级）

## P0（建议 1~2 周内）

1. **性能与体验稳定化**
   - 指标化：TTFT、首包耗时、总时长、工具调用次数、失败率。
   - 目标：高频闲聊稳定秒级，RAG 问答维持可感知流畅。

2. **多模态链路可观测性增强**
   - 增加 injected 文件名/来源日志。
   - 前端可显示“本轮使用了 X 张图片证据”。

3. **报告 Agent 流程鲁棒性**
   - 引入状态机级单测（ask/outline/generate 分支覆盖）。
   - 避免边缘输入导致 response_type 误跳转。

## P1（建议 2~4 周）

1. **代码结构治理**
   - 将 `main.py` 的教师生成能力拆分为独立 router/service。
   - 将 `chat/service.py` 中 prompt、state util、tool handlers 解耦。

2. **评测集与回归体系**
   - 建立教学问答基准集（文本问答/报告需求/图片问答）。
   - 每次改动自动产出质量分 + 性能分。

3. **RAG 质量优化**
   - 增加 reranker 实际启用策略（召回候选再重排）。
   - 文档质量门控（低质量网页、短文本过滤强化）。

## P2（中期）

1. **多租户与权限域完善**
   - 课程级文档隔离、资源共享策略、审计日志。

2. **前端智能工作台升级**
   - 将 Agent 状态（routing/ask/outline/generate）可视化。
   - 提供“可解释回答来源卡片”（文档片段 + 图片证据）。

3. **生成结果可编辑工作流**
   - 教案/报告/博客支持片段级再生成与版本对比。
