目前已经实现了前端的联调，现在来讨论下我们之前所说的在对话中保存信息的设计，当用户进行了一段对话后，突然说，把之前的信息生成一份报告，这时候要直接将我们存好的对话信息直接传过去，这里该怎么设计，还是让用户在生成报告时，再去总结之前的对话历史比较好

不要二选一。

**最好的方案是：原始对话持续保存 + 轻量结构化记忆增量沉淀 + 生成报告时按需组装。**
也就是：

* **不建议**每次生成报告时再从零总结全部历史
* **也不建议**每轮都维护一份很重、很完整的“最终报告状态”

应该做成一个 **分层记忆模型**。

---

# 一、先给结论

当用户聊了一段后说：

> 把之前的信息生成一份报告

系统不应该简单地：

### 方案 A：直接把全部历史消息原样塞给报告引擎

问题：

* 太长
* 噪音多
* 很多轮是试探、闲聊、反复表达，不适合直接喂给生成器
* 成本高，稳定性差

### 方案 B：等到这句话出现时，再临时把全部历史总结一遍

问题：

* 生成时延明显增加
* 临时总结容易漏掉前面确认过的重要约束
* 每次都重新总结，会出现结果漂移
* 后面“继续改报告”时很难复用

---

## 更合理的是方案 C

### 平时

持续保存三层信息：

1. **原始消息**
2. **轻量会话摘要 / 已确认事实**
3. **少量可复用的结构化记忆**

### 到“生成报告”这一刻

动态创建一个 **ReportContext**，从这三层里取最合适的内容：

* 最近相关消息
* 会话摘要
* 已确认约束
* 活跃 artifact / workflow
* 课程上下文
* 用户显式选择的资料

然后把这个 `ReportContext` 传给报告工作流。

---

# 二、你真正要设计的，不是“要不要总结”，而是“总结沉淀到哪一层”

我建议你把对话信息拆成 4 层。

---

## 第 1 层：原始消息层

永远保留，作为事实来源。

存：

* `message_id`
* `conversation_id`
* `role`
* `content`
* `timestamp`
* `attachments`
* 关联 `course_id / artifact_id`

作用：

* 可追溯
* 出错时可回看
* 需要更深上下文时可回扫

这层不能少，但**不能直接当报告输入主材料**。

---

## 第 2 层：会话级增量摘要层

这是最重要的一层。

不要每轮都做“完整总结”，而是做**轻量增量沉淀**。
比如每轮用户发完，或者每 3~5 轮，抽取以下信息：

* 当前主要讨论主题
* 已确认的问题点
* 已确认目标
* 已提到的关键事实
* 已提到的数据/案例
* 已明确的报告对象/用途（如果有）
* 已经否定掉的方向

例如：

```ts
type ConversationMemory = {
  current_topics: string[]
  confirmed_facts: string[]
  identified_issues: string[]
  goals: string[]
  constraints: string[]
  candidate_evidence: EvidencePoint[]
  updated_at: string
}
```

这里注意两点：

### 1. 只沉淀“高价值稳定信息”

不是把每轮话都翻译一遍。

### 2. 区分“确认过”和“只是提过”

否则会脏。

---

## 第 3 层：对象级引用层

这是你们后面做“根据以上内容”最关键的一层。

你要尽量把“以上内容”对象化，而不是只靠聊天文字理解。

例如当前会话中可能已经有：

* 当前课程 `course_id`
* 当前活跃 artifact `active_artifact_id`
* 当前 report workflow `workflow_id`
* 用户选中的文档 `selected_doc_ids`
* 最近一次确认的大纲 `outline_artifact_id`

这样当用户说：

* 根据上面的内容生成报告
* 把刚才那个整理成报告
* 基于之前讨论写成一份汇报

系统不是去猜“上面”是哪几段，而是优先取：

* 活跃上下文对象
* 最近相关消息片段
* 增量摘要层内容

这会稳定很多。

---

## 第 4 层：任务态上下文层

当用户真正触发“生成报告”时，才创建。

例如：

```ts
type ReportContext = {
  conversation_id: string
  course_id?: string
  source_message_ids: string[]
  source_summary: string
  confirmed_facts: string[]
  key_issues: string[]
  goals: string[]
  evidence_points: EvidencePoint[]
  selected_doc_ids: string[]
  active_artifact_id?: string
  report_intent_source: "reply_switch" | "report_button"
}
```

这层是**报告工作流输入态**，不是长期记忆本身。

---

# 三、所以生成报告时，到底怎么取历史信息

正确做法不是“全量取历史”，而是**分级取用**。

我建议按这个优先顺序组装：

## 优先级 1：活跃对象

先看用户当前是否已经有明确对象：

* 当前课程
* 当前 artifact
* 当前 workflow
* 当前选中文档

这些应该最优先进入报告上下文。

---

## 优先级 2：会话增量摘要

再取你平时沉淀下来的：

* 问题点
* 关键事实
* 已确认结论
* 约束
* 候选证据

这部分是报告最有价值的“骨架材料”。

---

## 优先级 3：最近 N 轮相关消息

再补最近 6~12 轮里与当前话题最相关的消息。

注意不是机械取最近 N 轮，而是：

* 最近轮次
* 且和当前报告主题相关

比如用户前 30 轮里有 20 轮其实在闲聊，就不该全塞进去。

---

## 优先级 4：必要时回扫更早原始消息

只有摘要不够、对象不够、最近消息也不够时，才去更早历史里回扫。

这应该是兜底，不是默认主路径。

---

# 四、所以“平时要不要总结”——要，但不能太重

我建议你这样做：

## 平时做

### 1. 原始消息必存

### 2. 轻量增量摘要必做

### 3. 对象引用持续维护

### 4. 不做完整报告级总结

也就是说：

* **不要**每轮都总结成“报告草稿”
* **要**每轮或每几轮提炼“可用于后续生成的稳定事实”

---

# 五、什么时候触发增量摘要最合适

不是每轮都强制做一次大模型摘要。
可以分成几种策略。

## 策略 1：轻量同步抽取

每轮对话后用很轻的方式抽几个字段：

* 是否出现新问题点
* 是否出现新目标
* 是否出现新证据
* 是否出现新的约束

这个可以很轻，甚至部分规则化。

---

## 策略 2：每 3~5 轮做一次小摘要

适合在对话持续变长时，定期把会话压缩成更稳定的 summary。

---

## 策略 3：重要动作后强制总结

比如出现这些情况时，一定做一次更可靠的摘要更新：

* 用户明确说“就按这个来”
* 用户确认了大纲
* 用户明确描述了问题背景
* 用户给出关键数据或案例
* 用户说“基于以上内容生成报告”

这个时候总结价值最高。

---

# 六、对你现在这个系统，我建议一个最实用的落地方案

你已经有：

* `reply`
* `report`
* `conversation_store_adapter`
* `context_builder`
* `workflow_state`
* `active_artifact`

那最合适的做法是：

---

## 1. 在会话存储里加两个字段

除了原始消息，再维护：

### `conversation_summary`

轻量文本摘要

### `conversation_memory`

结构化摘要

例如：

```json
{
  "current_topics": ["课堂纪律", "参与度低"],
  "confirmed_facts": [
    "班级前半段注意力较差",
    "学生回答积极性不高"
  ],
  "identified_issues": [
    "开场吸引力不足",
    "课堂反馈机制弱"
  ],
  "goals": [
    "形成阶段性分析报告"
  ],
  "constraints": [],
  "evidence_points": [
    {"type": "observation", "content": "前10分钟学生分心较明显"}
  ]
}
```

---

## 2. reply 成功后，异步或轻同步更新这两个字段

也就是普通对话跑完后，不只是写 user/assistant message，还做：

* 更新 conversation summary
* 更新 conversation memory

这里最好别让主回复阻塞太久。
可以轻同步，或后面异步化。

---

## 3. 当 `reply` 中命中“生成报告”时

`ContextBuilder` 不要只拿 recent messages，应该优先拿：

* `conversation_memory`
* `conversation_summary`
* `active_artifact`
* `workflow_state`
* `selected_doc_ids`
* 再补最近相关消息

然后统一组装成 `ReportContext`。

---

## 4. report runtime 只吃 `ReportContext`

不要让 report runtime 自己再去全量扫历史消息。

也就是说：

* 历史抽取在 orchestrator / context_builder 完成
* report runtime 接收已经压缩好的上下文

这样 report runtime 会更稳定，也更容易测。

---

# 七、一个非常关键的判断标准

你可以用一句话判断这条信息该不该提前存：

## 适合提前沉淀的

* 稳定事实
* 明确问题
* 已确认结论
* 生成任务会高频复用的信息

## 不适合提前沉淀的

* 闲聊寒暄
* 模糊试探
* 尚未确认的猜测
* 一次性修辞

所以你不是“把对话都存成结构化”，而是：

**把未来大概率还会用到的信息，提前提炼出来。**

---

# 八、我不建议的两种极端

## 极端 1：每轮都做很重的总结

问题：

* 贵
* 慢
* 状态容易脏
* 用户每次试探都会污染结构化状态

---

## 极端 2：什么都不存，等生成时再全量回扫

问题：

* 成本高
* 时延高
* 结果不稳定
* 对长对话很差

---

# 九、最推荐的最终答案

如果你要一句最落地的建议，就是：

## 平时怎么做

* 保存原始消息
* 维护轻量 `conversation_summary`
* 维护结构化 `conversation_memory`
* 维护 `active_task / active_artifact`

## 生成报告时怎么做

* 创建 `ReportContext`
* 优先取 `conversation_memory + summary`
* 补最近相关消息
* 必要时再回扫更早原始历史
* 把这个压缩后的上下文传给 report workflow

---

# 十、我给你的最终结论

**不要等到生成报告时才从零总结全部历史。**
**也不要每轮都维护一份很重的最终报告态。**

最优解是：

> **原始历史持续保存，轻量高价值信息持续沉淀，真正触发“生成报告”时再动态组装成报告上下文。**

这样你同时拿到了：

* 更快的生成速度
* 更稳定的报告输入
* 更低的 token 成本
* 更好的续写/改写能力
* 更清晰的工程边界

下一步最值得做的是把这套东西具体落成一张 **“message / conversation_summary / conversation_memory / ReportContext” 数据结构表**。


我觉得你的设计很不错，那现在帮我总结下你觉得轻量对话沉淀都应该存哪些东西，哪些字段，以及资源生成的工作流（不只是报告生成）怎么承接他们

可以，我给你收成一套**能直接指导实现**的版本。

我的核心建议是：
**轻量对话沉淀不要存“完整理解”，而要存“未来生成最可能复用的信息”。**
然后所有资源生成工作流都走同一套承接方式：

**会话沉淀层 → 通用生成上下文层 → 各资源专用 assembler → 对应 workflow runtime**

# 一、轻量对话沉淀，建议分 4 类存

## 1. 原始消息层

这是事实层，必须完整保存，但不做主生成输入。

建议字段：

```ts
type MessageRecord = {
  message_id: string
  conversation_id: string
  role: "user" | "assistant" | "system" | "tool"
  content: string
  created_at: string
  attachments?: string[]
  cited_artifact_ids?: string[]
  cited_doc_ids?: string[]
}
```

作用：

* 可追溯
* 出错时回查
* 长对话兜底回扫

---

## 2. 轻量摘要层

这是给后续生成用的“压缩版会话理解”。

建议字段：

```ts
type ConversationSummary = {
  conversation_id: string
  summary_text: string
  last_updated_at: string
  covered_message_range?: {
    start_message_id?: string
    end_message_id?: string
  }
}
```

这里的 `summary_text` 不要太长，控制成：

* 当前主要讨论内容
* 已明确的问题
* 已达成的结论
* 最近正在推进的任务

它更像“会话压缩说明”，不是完整报告草稿。

---

## 3. 结构化记忆层

这是最重要的层。
它不是全文总结，而是把对资源生成最有价值的信息拆出来。

建议字段：

```ts
type ConversationMemory = {
  conversation_id: string

  current_topics: string[]              // 当前主题
  user_goals: string[]                  // 用户当前目标
  confirmed_facts: string[]             // 已确认事实
  open_questions: string[]              // 尚未解决的问题
  constraints: string[]                 // 约束，如字数/对象/风格
  audience_hints: string[]              // 面向谁：学生/家长/教研组/校方
  tone_hints: string[]                  // 正式/简洁/鼓励式等

  key_knowledge_points: string[]        // 涉及知识点
  teaching_issues: string[]             // 教学问题点
  student_signals: string[]             // 学生表现、学情信号
  evidence_points: EvidencePoint[]      // 证据点、案例、观察
  extracted_requirements: ResourceIntentHint[] // 对资源生成有帮助的意图线索

  selected_doc_ids: string[]
  referenced_artifact_ids: string[]

  last_confirmed_output_type?: string   // 最近确认的产物类型，如 report / lesson_plan
  last_confirmed_outline?: string        // 最近确认的大纲，可选
  last_updated_at: string
}
```

其中两个子结构我建议这样定：

```ts
type EvidencePoint = {
  type: "observation" | "data" | "example" | "quote" | "requirement"
  content: string
  source: "user_message" | "assistant_summary" | "document" | "artifact"
  confidence?: "high" | "medium" | "low"
  source_message_ids?: string[]
}
```

```ts
type ResourceIntentHint = {
  target_type: "report" | "lesson_plan" | "quiz" | "ppt_outline" | "flashcard" | "summary"
  signal: string
  strength: "weak" | "medium" | "strong"
}
```

---

## 4. 活跃对象层

这是解决“根据上面的内容”“把刚才那个变成报告”这类话的关键。

建议字段：

```ts
type ActiveContext = {
  conversation_id: string

  active_task_id?: string
  active_workflow_type?: string         // report / lesson_plan / quiz ...
  active_workflow_status?: string

  active_artifact_id?: string
  active_artifact_type?: string

  pinned_doc_ids: string[]              // 用户显式选中的资料
  pinned_message_ids: string[]          // 用户显式圈定的消息
  current_course_id?: string

  updated_at: string
}
```

这层的作用是：

* 少靠“猜上面是哪段”
* 多靠“当前对象是谁”

---

# 二、轻量沉淀到底该存什么，不该存什么

## 应该存的

这些是高复用信息：

* 当前讨论主题
* 用户目标
* 已确认事实
* 问题点
* 学情信号
* 证据点
* 受众、风格、长度等约束
* 最近确认的输出类型
* 当前活跃 artifact / workflow / 文档选择

---

## 不建议存得太重的

这些不要每轮都硬提炼：

* 完整逐轮推理
* 完整“用户意图树”
* 每轮都生成一版正式摘要
* 还没确认的猜测
* 闲聊句子
* 大量低价值 paraphrase

一句话就是：

**存“稳定且会复用的信息”，不要存“瞬时思考过程”。**

---

# 四、这些信息什么时候更新

我建议分三种时机。

## 1. 每轮对话后，轻量更新

更新：

* `current_topics`
* `user_goals`
* `confirmed_facts`
* `constraints`
* `selected_doc_ids`
* `referenced_artifact_ids`

这一步要轻，不要太重。

---

## 2. 每 3~5 轮，更新一次 `summary_text`

把最近讨论压缩一下。

---

## 3. 关键节点，强制更新

这些场景要重点更新：

* 用户明确说“就按这个来”
* 用户明确给出目标资源类型
* 用户提供关键案例/数据
* 用户确认大纲
* 用户点“生成报告/教案/练习”
* 用户说“根据以上内容生成…”

因为这些节点的复用价值最高。

# 五、资源生成工作流，如何统一承接这些沉淀

这里是核心。

不要让每个 workflow 自己去扫整段聊天历史。
应该统一走一个中间层：

## 总链路

**Message / Summary / Memory / ActiveContext**
→ **GenerationContextBuilder**
→ **Resource-specific Assembler**
→ **Workflow Runtime**

---

## 第一步：先构建通用生成上下文

不管生成什么资源，先组一份通用上下文。

```ts
type GenerationContext = {
  conversation_id: string
  course_id?: string

  summary_text: string
  current_topics: string[]
  user_goals: string[]
  confirmed_facts: string[]
  constraints: string[]
  teaching_issues: string[]
  student_signals: string[]
  evidence_points: EvidencePoint[]

  selected_doc_ids: string[]
  referenced_artifact_ids: string[]

  active_artifact_id?: string
  active_artifact_type?: string

  recent_relevant_messages: MessageRecord[]
  source_scope: {
    from_summary: boolean
    from_memory: boolean
    from_recent_messages: boolean
    from_docs: boolean
    from_artifacts: boolean
  }
}
```

这一步是通用的。

---

## 第二步：各资源有自己的 assembler

然后根据资源类型，再把 `GenerationContext` 装配成不同输入。

也就是：

* `build_report_input(context)`
* `build_lesson_plan_input(context)`
* `build_quiz_input(context)`
* `build_ppt_outline_input(context)`
* `build_flashcard_input(context)`

这样每个 workflow 不需要自己理解原始聊天，只需要吃“已经整理过的材料”。

# 六、不同资源类型怎么承接这些沉淀

## 1. 报告生成

最看重：

* `summary_text`
* `confirmed_facts`
* `teaching_issues`
* `evidence_points`
* `audience_hints`
* `constraints`
* 最近相关消息

适配后的输入像：

```ts
type ReportInput = {
  purpose: string
  audience?: string
  facts: string[]
  issues: string[]
  evidence: EvidencePoint[]
  style_constraints: string[]
  source_summary: string
}
```

---

## 2. 教案生成

最看重：

* `current_topics`
* `key_knowledge_points`
* `user_goals`
* `constraints`
* 学情信号
* 当前课程信息
* 已有 artifact（如前面聊过的分析报告）

适配后的输入像：

```ts
type LessonPlanInput = {
  topic: string
  knowledge_points: string[]
  teaching_goals: string[]
  learner_signals: string[]
  constraints: string[]
  reference_materials: string[]
}
```

也就是说，教案不是重新扫整段聊天，而是拿：

* 这段对话中提炼出的目标
* 知识点
* 学情
* 约束

---

## 3. 练习 / 试题生成

最看重：

* `key_knowledge_points`
* `confirmed_facts`
* `student_signals`
* 难度约束
* 题量要求
* 最近讨论的问题点

适配后的输入像：

```ts
type QuizInput = {

  weak_points: string[]
  difficulty?: string
  quantity?: number
  style_constraints: string[]
}
```

这里对话沉淀的价值非常大，因为用户常常会先聊：

* 哪些地方学生不会
* 哪些题型太难
* 想要基础题还是分层题

这些都应该在平时被轻量沉淀下来。

## 4. PPT 提纲生成

最看重：

* `summary_text`
* `current_topics`
* `confirmed_facts`
* `last_confirmed_outline`
* 已有 report / lesson_plan artifact

适配后的输入像：

```ts
type PptOutlineInput = {
  topic: string
  structure_basis: string
  key_points: string[]
  narrative_goal?: string
  reference_artifact_ids: string[]
}
```

PPT 提纲通常不是从原始聊天直接生成，而是更适合吃：

* 已有总结
* 已有报告
* 已有教案

所以 `referenced_artifact_ids` 很重要。

---

## 5. 记忆卡片 / flashcard

最看重：

* `key_knowledge_points`
* `confirmed_facts`
* `definitions / concepts`
* 最近用户明确想记忆的点

适配后的输入像：

```ts
type FlashcardInput = {
  concepts: string[]
  facts: string[]
  examples: string[]
}
```

# 七、所有资源 workflow 的统一承接模式

我建议统一成这 5 步。

## Step 1：接收请求

来自：

* `reply` 中自然切换
* 按钮显式触发

## Step 2：构建 `GenerationContext`

从：

* `ConversationSummary`
* `ConversationMemory`
* `ActiveContext`
* 最近相关消息
* 已选文档
* 已有 artifact
  中取材料

## Step 3：调用资源专用 assembler

把通用上下文压成资源专属输入

## Step 4：进入对应 workflow runtime

例如：

* `ReportWorkflowRuntime`
* `LessonPlanWorkflowRuntime`
* `QuizWorkflowRuntime`

## Step 5：写回状态

更新：

* `active_workflow_type`
* `active_artifact_id`
* `last_confirmed_output_type`
* 新生成 artifact
* 必要时更新 summary / memory

# 八、很关键的一点：不要让 workflow 直接理解整段会话

这是我最想强调的。

不要这样做：

* report runtime 自己扫全部消息
* lesson_plan runtime 自己再做一遍总结
* quiz runtime 再自己猜用户需求

这样每个 workflow 都会重复造轮子，而且行为不一致。

正确做法是：

**所有 workflow 都只吃统一的 `GenerationContext`，只是各自 assembler 不一样。**

这会带来几个好处：

* 行为一致
* 方便测试
* token 更省
* 后面加新资源类型更容易

---

# 九、我建议你补一个“生成上下文构建器”

在工程上，可以加一层专门的 builder：

```ts
type GenerationContextBuilder = {
  buildForResource(
    conversationId: string,
    resourceType: "report" | "lesson_plan" | "quiz" | "ppt_outline" | "flashcard",
    options?: {
      selectedDocIds?: string[]
      activeArtifactId?: string
      recentMessageLimit?: number
    }
  ): GenerationContext
}
```

然后各资源只做：

* `reportAssembler.from(context)`
* `lessonPlanAssembler.from(context)`
* `quizAssembler.from(context)`

这层会非常值钱。

# 一句话总结

**轻量对话沉淀应该存“主题、目标、事实、约束、问题点、证据点、活跃对象”，而不是存一份很重的完整推理态。**
**资源生成工作流则不直接扫聊天历史，而是统一承接这些沉淀，先构建通用 `GenerationContext`，再由不同资源的 assembler 转成各自 workflow 输入。**

下一步最适合做的是把这几个对象直接画成一份 **后端数据结构草案 + 字段定义文档**。
那进行多轮对话之后，该怎么对这些状态进行更新维护

多轮对话里，**不是“每轮都重建全部状态”**，而是做成：

**消息持续追加 + 轻量增量更新 + 关键节点强更新 + 生成前按需组装。**

也就是把状态维护理解成一个**增量同步系统**，而不是每轮“重新理解整段会话”。

---

# 一、先给一个总原则

我建议你把状态更新分成三层节奏：

## 1. 每轮必做：轻量更新

每次用户发言后，都做很轻的增量维护：

* 追加原始消息
* 更新当前主题
* 更新用户目标
* 更新约束
* 更新活跃对象引用
* 标记本轮是否出现“可沉淀信息”

这一步必须快，最好不用重模型，或者只用很轻的抽取。

---

## 2. 若干轮做一次：压缩更新

每 3~5 轮，或者消息累计到一定长度时：

* 刷新 `summary_text`
* 合并重复 facts / issues / constraints
* 丢弃低价值噪音
* 给会话状态做一次“收口”

这一步相当于做一次轻压缩，避免状态越来越乱。

---

## 3. 关键时刻做：强更新

遇到这些情况时，必须做一次更认真、更可靠的状态更新：

* 用户明确说“就按这个来”
* 用户确认某个结论/大纲
* 用户给出关键事实、案例、数据
* 用户切换任务类型
* 用户说“根据以上内容生成报告/教案/练习”
* 进入或退出 workflow

这时候要把状态写得更准，因为后面很可能直接拿来生成资源。

---

# 二、建议把状态维护拆成 5 个对象分别更新

---

## 1. `MessageRecord`

这个最简单，永远 append-only。

### 更新规则

每轮都追加：

* user message
* assistant message
* tool message（有的话）

### 不要做的事

* 不要覆盖原消息
* 不要把它当最终结构化状态
* 不要试图在这里“修正语义”

它是事实层，只负责留痕。

---

## 2. `ConversationSummary`

这是“会话压缩摘要”。

### 更新频率

不要每轮都全文重写。
建议：

* 每 3~5 轮更新一次
* 或当消息总长度超过阈值时更新
* 或关键节点强制更新

### 更新方式

不是从零总结全部历史，而是：

**旧 summary + 最近几轮高价值消息 → 新 summary**

也就是增量摘要，而不是全量回放。

### 推荐内容

只保留这些：

* 当前在讨论什么
* 已明确的关键问题
* 已达成的主要结论
* 当前正在推进的任务

### 不要放太多

不要把 summary 写成一篇长文，不然它会失去“压缩”意义。

---

## 3. `ConversationMemory`

这是核心，要做增量合并。

我建议每次更新时，用“字段级 merge”，而不是整对象覆盖。

---

### A. `current_topics`

存当前主要主题。

#### 更新规则

* 新话题出现时追加
* 连续多轮围绕某主题时提高权重
* 长时间没再提的主题降权或移出活跃区

#### 维护方式

最好不是纯列表，而是内部带权重：

```ts id="q4dnsm"
type TopicState = {
  name: string
  score: number
  last_seen_at: string
}
```

对外可以仍然暴露成 `current_topics: string[]`，但内部最好有 score。

---

### B. `user_goals`

存用户当前想达成什么。

比如：

* 想分析课堂问题
* 想生成报告
* 想生成教案
* 想出一套练习

#### 更新规则

* 明确表达目标时新增
* 同类目标重复出现时增强置信度
* 新目标出现时，不一定立刻删旧目标，要看是不是切换任务
* 一旦进入明确 workflow，可把当前 workflow 对应目标置为最高优先级

#### 特别注意

`user_goals` 不要只存一个，因为真实对话里用户经常会先分析，再生成，再改写。

---

### C. `confirmed_facts`

这是最需要谨慎的字段。

#### 只存什么

只存：

* 用户明确陈述的事实
* 多轮重复确认的事实
* 已在资源/文档/产物中出现并被接受的事实

#### 不存什么

* assistant 的推测
* 一次性猜测
* 模糊表达
* 尚未确认的建议

#### 更新规则

* 新 fact 出现时先候选
* 被重复提及或明确确认后，提升为 confirmed
* 与已有 fact 冲突时，不要直接覆盖，走冲突处理

我建议内部区分：

```ts id="fe7m68"
type FactItem = {
  content: string
  status: "candidate" | "confirmed" | "superseded"
  source_message_ids: string[]
  updated_at: string
}
```

对外你可以只暴露 confirmed 的部分。

---

### D. `constraints`

这是资源生成很关键的一层。

例如：

* 面向家长
* 更正式
* 控制在 800 字
* 高一物理
* 不要太学术
* 用鼓励式语气

#### 更新规则

* 新约束出现时追加
* 同类约束只保留最新有效值
* 明确否定时删除旧值

比如：

* 先说“简短一点”
* 后来说“详细一点”

这就不是并存，而是同一个 constraint slot 被覆盖。

所以这里最好拆槽位：

```ts id="y43h23"
type ConstraintState = {
  audience?: string
  tone?: string
  length?: string
  grade_level?: string
  subject?: string
  style_notes: string[]
}
```

而不是只做 `string[]`。

---

### E. `teaching_issues / student_signals / evidence_points`

这是教学场景最值钱的一组。

#### teaching_issues

存教学问题点，例如：

* 开场吸引力不足
* 学生参与度低
* 提问分层不够

#### student_signals

存学情信号，例如：

* 前10分钟注意力分散
* 基础题能做，迁移题吃力
* 回答积极性低

#### evidence_points

存支持上述判断的证据。

这三组最好联动更新：

* 先有 observation/data
* 再归纳成 issue/signal
* 生成资源时优先引用 evidence，而不是只引用抽象结论

#### 更新规则

* 同义问题合并
* 弱证据不要直接升级成核心问题
* 证据尽量保留来源 message_id / doc_id / artifact_id

---

## 4. `ActiveContext`

这是多轮对话能否稳定的关键。

建议每轮都检查并更新：

* 当前是否有 active workflow
* 当前 active artifact 是什么
* 当前 pinned doc 是什么
* 当前 course_id 是什么

### 更新规则

#### 进入 workflow 时

写入：

* `active_workflow_type`
* `active_workflow_status`

#### 生成 artifact 时

写入：

* `active_artifact_id`
* `active_artifact_type`

#### 用户显式切换时

例如：

* “先别写报告了”
* “改成教案”
* “基于刚才那个报告出 PPT”

要更新：

* workflow 切换
* artifact 引用切换
* 可能清理旧 active task

---

## 5. `GenerationContext`

这个不是长期维护对象，而是**每次生成时临时构建**。

所以它不在每轮都更新。
它是在用户触发生成动作时，由：

* MessageRecord
* ConversationSummary
* ConversationMemory
* ActiveContext
* 选中文档
* 最近相关消息

拼出来。

---

# 三、多轮对话里最关键的不是“更新”，而是“合并规则”

很多系统不是不会抽取，而是会越聊越脏。
所以你要重点设计 merge 规则。

---

## 1. 去重

相同或高度相似的信息不能一直追加。

例如：

* “学生参与度不高”
* “课堂参与偏低”
* “回答不积极”

应该合并到同一个问题簇，不要存成 3 条独立核心问题。

---

## 2. 覆盖

有些字段是“最新值为准”的。

例如：

* audience
* tone
* length
* report type
* 当前目标资源类型

这些不该无限累加。

---

## 3. 升级

有些信息不是一出现就进核心状态，而是要逐步升级：

* 候选事实 → 已确认事实
* 临时问题点 → 核心问题点
* 一次性例子 → 证据点

---

## 4. 降级 / 过期

长对话里，旧状态不处理会越来越脏。

所以建议有“过期”逻辑：

* 长时间未提及的 topic 降权
* 已被替换的 constraint 标记失效
* 已完成 workflow 的 active task 退场
* 被新的 artifact 取代的旧 artifact 只保留引用，不再 active

---

## 5. 冲突处理

例如用户先说：

* “这节课主要问题是纪律差”

后面又说：

* “其实纪律还行，主要是参与度低”

这里不要直接无脑覆盖。
最好做成：

* 原说法降级为 superseded
* 新说法升为 current
* 保留变更痕迹

这样生成时不会把两个互相矛盾的结论一起喂进去。

---

# 四、我建议的每轮更新流水线

你可以把每轮对话后的状态维护做成固定 6 步。

---

## Step 1：追加消息

把 user / assistant / tool message 存进去。

---

## Step 2：轻量抽取本轮信号

从本轮用户输入里抽这些最小信号：

* 是否有新 topic
* 是否有新目标
* 是否有新约束
* 是否有新事实
* 是否引用了文档/artifact
* 是否触发了 workflow 切换意图

这一步非常轻。

---

## Step 3：合并到 `ConversationMemory`

对每个字段做 merge：

* topics 合并去重并打分
* goals 增加/切换
* constraints 覆盖槽位
* facts 升级/降级
* evidence 去重保留来源

---

## Step 4：更新 `ActiveContext`

看本轮有没有：

* 进入 workflow
* 生成 artifact
* 选中文档
* 切换当前对象
* 中断当前任务

---

## Step 5：必要时刷新 `ConversationSummary`

不是每轮必做，而是到阈值再做。

---

## Step 6：记录状态版本

建议每次状态写回时带一个版本号或时间戳，便于排查脏状态问题。

---

# 五、最推荐的触发策略

给你一个很实用的组合。

## 每轮都做

* Message append
* 轻量 signal extract
* ActiveContext update

## 每 3~5 轮做

* summary refresh
* memory compact

## 关键节点强制做

* 用户确认
* 用户切换任务
* 用户要求生成资源
* workflow phase 变化
* 生成 artifact 成功

这样既不重，也不会拖到最后才收拾。

---

# 六、不同状态的更新示例

假设对话过程是：

### 第 1 轮

用户：

> 最近班里课堂纪律不太好，学生一开始就容易散。

更新：

* `current_topics += ["课堂纪律", "课堂开场"]`
* `confirmed_facts += ["课堂前半段学生容易分散"]`
* `student_signals += ["开场阶段注意力不集中"]`
* `teaching_issues += ["课堂开场控制力不足"]`

---

### 第 2 轮

用户：

> 我更想先分析问题，不急着出方案。

更新：

* `user_goals += ["分析课堂问题"]`
* `constraints += ["当前先分析，暂不直接给方案"]`

---

### 第 3 轮

用户：

> 另外这节课是高一物理，牛顿第二定律。

更新：

* `constraints.subject = "物理"`
* `constraints.grade_level = "高一"`
* `current_topics += ["牛顿第二定律"]`

---

### 第 4 轮

用户：

> 根据上面内容，帮我整理成一份报告。

更新：

* `user_goals` 里新增 `"生成报告"`
* `last_confirmed_output_type = "report"`
* `active_workflow_type = "report"`
* 触发构建 `GenerationContext`
* 进入 `ReportWorkflowRuntime`

这里不是临时去扫全部历史，而是直接从前 3 轮已经沉淀好的 memory + summary + 最近消息里组装报告输入。

---

# 七、要特别防止的两个问题

## 1. 状态越来越多，最后没人信

解决办法：

* 去重
* 过期
* 槽位覆盖
* 冲突标记

---

## 2. assistant 自己生成的推断污染状态

解决办法：

* 事实和推断分开存
* `confirmed_facts` 只吃高置信、已确认内容
* 建议/分析不要自动写成事实

---

# 八、工程上最推荐的实现形态

我建议你做一个专门的更新器，而不是把逻辑散在 service 里。

例如：

```ts id="nq7ugc"
type ConversationStateUpdater = {
  appendMessages(...)
  extractTurnSignals(...)
  mergeMemory(...)
  updateActiveContext(...)
  maybeRefreshSummary(...)
}
```

每轮对话结束后统一调用一次。
这样后面 report / lesson_plan / quiz 都能复用同一套沉淀逻辑。

---

# 九、一句话收口

多轮对话之后，状态维护不应该是“每轮重算全部”，而应该是：

> **原始消息持续追加，Memory 做字段级增量合并，Summary 按阈值压缩更新，ActiveContext 随任务和产物变化实时切换。**

这样系统才会越聊越稳，而不是越聊越乱。

下一步最值得做的是把这套更新规则直接写成一份 **字段级 merge 规范**，我建议至少把 `topics / goals / constraints / facts / evidence / active_context` 六类先定死。
