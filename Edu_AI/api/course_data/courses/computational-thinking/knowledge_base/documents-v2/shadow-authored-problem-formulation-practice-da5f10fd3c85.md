## 真实问题情境
某高校图书馆计划升级自动化罚款系统。 librarians 提供了以下口头规则：“学生借书逾期要罚款，老师好像不用罚。每天几毛钱，但不能超过书价本身。如果是节假日可能不算逾期。具体系统得能算出要交多少钱，还得告诉管理员是谁欠的。”
这段描述存在大量歧义，直接编码会导致逻辑错误。学生任务是将此需求形式化为清晰的输入输出规范。

## 输入输出与材料
**原始材料分析**：
-   **潜在输入**：用户身份（学生/老师）、借书日期、应还日期、实际还书日期、书价、节假日列表。
-   **潜在输出**：罚款金额、欠费用户 ID、状态标志（正常/逾期）。
-   **潜在约束**：罚款上限、计费规则、身份差异。

**形式化任务材料**：
请基于上述情境，定义函数 `calculate_fine` 的接口规范。

## 分步任务
1.  **实体提取**：列出所有影响罚款计算的变量，并命名。
2.  **类型标注**：为每个变量指定编程语言中的数据类型（如 `datetime`, `float`, `enum`）。
3.  **约束书写**：用自然语言或逻辑公式写出至少 3 条业务约束。
4.  **接口定义**：写出函数签名，明确参数顺序及返回值结构。

## 参考实现与推导
**推导过程**：
首先明确输入必须包含时间差。设 $D_{due}$ 为应还日期，$D_{return}$ 为实还日期。逾期天数 $d = \max(0, D_{return} - D_{due})$。
其次，身份决定费率。设身份为 $role \in \{Student, Faculty\}$。
约束条件：
1.  若 $role = Faculty$，费率 $r = 0$。
2.  若 $role = Student$，费率 $r = 0.5$ 元/天。
3.  罚款总额 $F = d \times r$。
4.  上限约束：$F \le Price_{book}$。

**参考代码实现**：
```python
from datetime import date

def calculate_fine(user_role, due_date, return_date, book_price):
    # 输入验证
    if not isinstance(due_date, date) or not isinstance(return_date, date):
        raise ValueError("Dates must be date objects")
    if book_price <= 0:
        raise ValueError("Book price must be positive")
    
    # 逻辑推导
    if user_role == "Faculty":
        return 0.0
    
    delta = (return_date - due_date).days
    if delta <= 0:
        return 0.0
    
    rate = 0.5  # 学生每天 0.5 元
    fine = delta * rate
    
    # 约束应用：不超过书价
    final_fine = min(fine, book_price)
    return round(final_fine, 2)
```

## 测试与边界情况
形式化的质量需要通过测试用例验证。学生需设计以下边界测试：
1.  **正常边界**：刚好当天归还（$d=0$），预期输出 0.0。
2.  **负值边界**：提前归还（$d<0$），预期输出 0.0，不能为负数。
3.  **上限边界**：逾期天数极长，使得 $d \times r > Price_{book}$，预期输出等于 $Price_{book}$。
4.  **异常输入**：`return_date` 早于 `due_date` 很多年，或 `book_price` 为负数，系统应抛出异常或返回错误码。
5.  **特殊约束**：若引入“节假日扣除”，输入需增加 `holiday_list`，测试用例需包含跨越节假日的区间。

## 评价量规
| 评价维度 | 优秀 (A) | 合格 (B) | 待改进 (C) |
| :--- | :--- | :--- | :--- |
| **输入完整性** | 涵盖所有影响结果的变量（含身份、时间、价格） | 缺少次要变量（如忽略身份差异） | 关键变量缺失（如未定义时间） |
| **约束明确性** | 清晰定义上限、费率及例外情况 | 仅定义基本费率，未定义上限 | 约束模糊，依赖隐含假设 |
| **类型准确性** | 数据类型精确（如日期对象而非字符串） | 类型基本正确但不够严谨 | 类型定义错误或缺失 |
| **边界覆盖** | 测试用例覆盖零值、负值、上限及异常 | 仅覆盖正常正值情况 | 无测试用例或用例无效 |

## 拓展问题
1.  **需求变更**：若图书馆规定“寒暑假期间不计入逾期”，你的输入输出定义需要如何修改？（提示：输入需增加学期日历信息，约束逻辑需增加区间判断。）
2.  **系统集成**：若该函数需被支付系统调用，输出格式是否需要增加货币类型代码（如 CNY vs USD）？为什么？
3.  **并发约束**：若多人同时操作同一账户，形式化定义中是否需要增加“事务锁”或“版本号”作为输入输出的一部分？简述理由。
