## 学习目标
本讲义旨在帮助学生建立“状态”与“状态转移”的抽象思维模型。学习完成后，学生应能够：
1. 准确区分系统的“状态”与“数据变量”。
2. 理解状态转移规则的决定性作用。
3. 能够使用有限状态机（FSM）模型描述简单系统的行为逻辑。
4. 识别并避免状态管理中的常见设计缺陷。

## 概念与边界
在计算思维中，**状态（State）** 是指系统在特定时刻所有相关属性的快照。它不仅仅是变量的值，更是系统当前所处情形的抽象概括。例如，一个灯泡的状态是“亮”或“灭”，而不是电压的具体数值。**规则（Rule）** 是支配状态变化的逻辑约束，通常表现为“若当前处于状态 A 且收到输入 X，则转移至状态 B"。**状态转移（State Transition）** 是系统从一个状态变迁到另一个状态的过程。

边界界定至关重要：状态必须是有限的、离散的。如果系统的属性组合无限多（如连续变化的温度值），则不适合直接用有限状态机描述，除非将其离散化（如“高温”、“低温”）。此外，状态不同于输出，输出是状态的外在表现，而状态是内在逻辑位置。

## 机制与形式化描述
状态转移机制通常由有限状态机（Finite State Machine, FSM）形式化描述。一个确定的有限状态机可以用五元组表示：
$$ M = (Q, \Sigma, \delta, q_0, F) $$
其中：
- $Q$ 是有限状态集合。
- $\Sigma$ 是有限输入符号集合。
- $\delta: Q \times \Sigma \rightarrow Q$ 是状态转移函数。
- $q_0 \in Q$ 是初始状态。
- $F \subseteq Q$ 是接受状态集合（在某些控制系统中可能不适用，但在识别器中关键）。

核心机制在于函数 $\delta$ 的确定性。对于任意当前状态 $q$ 和输入 $a$，下一个状态 $\delta(q, a)$ 是唯一确定的。这种确定性使得系统行为可预测、可验证。在实际编程中，这通常通过 `switch-case` 结构或状态模式（State Pattern）实现。

## 完整示例：电子密码锁系统
考虑一个简易的电子密码锁，密码为"123"。
- **状态集合 $Q$**：{锁定 (Locked), 输入中 (Entering), 解锁 (Unlocked), 报警 (Alarm)}
- **输入集合 $\Sigma$**：{数字 0-9, 确认键, 重置键}
- **初始状态 $q_0$**：锁定 (Locked)

**转移规则逻辑**：
1. 在“锁定”态，输入任意数字转入“输入中”态，缓存首位数字。
2. 在“输入中”态，若输入匹配密码序列，继续缓存；若确认键按下且匹配成功，转入“解锁”态；若匹配失败，转入“报警”态。
3. 在“解锁”态，超时或按重置键，返回“锁定”态。
4. 在“报警”态，需管理员重置才能返回“锁定”态。

**Python 代码实现核心逻辑**：
```python
class DigitalLock:
    def __init__(self):
        self.state = "Locked"
        self.buffer = ""
        self.password = "123"
    
    def input_digit(self, digit):
        if self.state == "Locked":
            self.state = "Entering"
            self.buffer = digit
        elif self.state == "Entering":
            self.buffer += digit
            if len(self.buffer) >= 3:
                self.check_password()
    
    def check_password(self):
        if self.buffer == self.password:
            self.state = "Unlocked"
        else:
            self.state = "Alarm"
        self.buffer = ""
    
    def reset(self):
        if self.state == "Alarm":
            print("Admin reset required.")
        else:
            self.state = "Locked"
            self.buffer = ""
```
此代码展示了状态变量 `self.state` 如何控制行为分支。

## 复杂度与权衡
使用状态机建模的时间复杂度通常为 $O(1)$，因为转移函数查找是常数时间的。然而，空间复杂度随状态数量线性增长。当状态数量激增时（状态爆炸），维护转移规则会变得困难。权衡在于：是将逻辑分散在各个状态的类中（状态模式，易扩展但类多），还是集中在一个巨大的转移表中（数据驱动，易维护但灵活性稍差）。对于简单系统，集中式转移函数更优；对于复杂业务，状态模式更佳。

## 常见误区
1. **混淆状态与数据**：例如将“用户年龄”当作状态。年龄是数据，而“未成年/成年”才是状态。状态应影响行为逻辑，而不仅仅是存储信息。
2. **忽略初始状态**：系统启动时必须明确处于哪个状态，否则行为未定义。
3. **死锁状态**：设计了进入后无法离开的状态（除非是终态）。例如上述示例中，若“报警”态没有重置规则，系统将永久卡死。
4. **隐含状态**：使用布尔标志位（如 `is_paid`）代替明确状态。当标志位增多时，组合爆炸会导致逻辑漏洞，应显式定义为状态。

## 自测题与答案
1. **问**：在一个下载任务中，“下载进度 50%"是状态吗？
   **答**：不是。这是数据。状态应为“下载中”、“暂停”、“完成”。
2. **问**：若 $\delta(q, a)$ 未定义，系统会发生什么？
   **答**：在严格 FSM 中这是非法输入。在实际系统中应抛出异常或保持原状态不变。
3. **问**：为什么推荐使用枚举（Enum）而不是字符串表示状态？
   **答**：枚举提供编译时检查，避免拼写错误导致的非法状态转移。
