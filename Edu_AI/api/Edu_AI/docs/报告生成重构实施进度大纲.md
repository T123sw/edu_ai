# 报告生成重构实施进度大纲（执行版）

> 本文档用于后续开发的**唯一进度基准**。后续开发严格按阶段推进，每阶段都有明确目标、实施项、交付物与验收标准。

---

## 0. 执行原则

1. **小步快跑，阶段闭环**：每个阶段完成后必须可运行、可验证。
2. **灰度优先**：新旧链路并存，默认可回滚。
3. **接口先行**：先定义状态与工具契约，再写节点逻辑。
4. **严禁跨阶段失控扩展**：不在当前阶段引入下阶段需求。
5. **每阶段结束必须有验收记录**：通过后才进入下一阶段。

---

## Phase 1：引擎骨架与状态模型

### 1.1 阶段目标
建立可运行的自治引擎骨架（Planner -> Executor -> Analyzer）及独立 ReportState，不替换现网主路径。

### 1.2 本阶段要做什么
1. 新建 `agents/report_state.py`
   - 定义 `PlanStep`、`ReportState`
   - 固化状态字段与类型
2. 新建 `agents/universal_report_engine.py`
   - 实现 `planner_node`（先用最小可用策略）
   - 实现 `executor_node`（先做 mock 工具分发）
   - 实现 `analyzer_node`（最小闭环判定）
   - 实现条件边（continue/replanning/awaiting_human/finished）
3. 提供 `build_universal_report_graph()` 编译函数
4. 在 `service.py` 中接入 feature flag（仅开关，不切主路）

### 1.3 怎么做（实施方法）
- 先写最小状态字段，保持可扩展
- Planner 输出强制结构化（Pydantic/TypedDict）
- Executor 暂不接真实复杂工具，先通“执行一步 + 写 observation”
- Analyzer 先实现基本状态决策规则

### 1.4 完成交付物
- `report_state.py`
- `universal_report_engine.py`
- `service.py` 中新增引擎开关与调用入口（默认关闭）

### 1.5 验收标准
1. 子图可独立 invoke 成功
2. 能完整跑通一次 `planning -> executing -> analyzing -> finished`
3. 出现 `awaiting_human` 时能正确结束子图
4. 不影响旧报告链路

---

## Phase 2：工具标准化与执行器落地

### 2.1 阶段目标
把执行器从 mock 升级为真实工具调度，建立统一工具契约，打通 ask/rag/web/generate。

### 2.2 本阶段要做什么
1. 新建 `tools/agent_tools.py`
   - `ask_human_for_clarification`
   - `submit_outline_for_review`
   - `rag_search_tool`（复用现有）
   - `web_search_tool`（复用 deepsearch）
   - `generate_long_report_content`（复用 report_generation）
2. 统一工具返回 schema（ok/tool/summary/payload/need_human/error）
3. Executor 改为真实工具路由（name -> callable）
4. 失败统一转成 `ok=false`，供 Analyzer 判定

### 2.3 怎么做（实施方法）
- 先封装适配层，避免改动旧工具本体
- 所有工具在适配层转成统一返回格式
- Executor 仅依赖统一格式，不感知工具差异

### 2.4 完成交付物
- `tools/agent_tools.py`
- `universal_report_engine.py` 的 Executor 升级版
- 工具契约文档补充（如必要）

### 2.5 验收标准
1. Executor 能按计划调用真实工具并记录 observation
2. 工具失败不会抛出未处理异常
3. `need_human=true` 工具可触发挂起路径
4. 旧 chat/research 工具逻辑不受影响

---

## Phase 3：Skill 驱动规划与 Analyzer 重规划

### 3.1 阶段目标
把“业务流程规则”从代码迁移到 Skill，形成真实 Plan-Execute-Analyze 闭环。

### 3.2 本阶段要做什么
1. Planner Prompt 元模板落地
   - 注入 skill 文本
   - 注入可用工具描述
   - 限制每轮计划步数（1-2步）
2. Analyzer Prompt 元模板落地
   - 成功/失败/挂起/完成判定
   - 重规划策略输出
3. 将 `edu-report-agent` Skill 对接到新引擎
4. 增加循环保护
   - 最大轮次
   - 最大重规划次数

### 3.3 怎么做（实施方法）
- 引入 structured output，减少模型漂移
- Planner/Analyzer 分工明确，禁止职责重叠
- 将“禁令”写入 prompt（如未确认大纲不得生成正文）

### 3.4 完成交付物
- Planner/Analyzer 完整提示词与结构化输出实现
- Skill 注入加载逻辑
- 循环保护机制

### 3.5 验收标准
1. 输入同一问题，在不同 Skill 下行为可改变
2. RAG 空结果时可自动重规划到 Web（或改关键词）
3. 能走完整闭环：补信息 -> 检索 -> 提纲 -> 挂起 -> 恢复 -> 正文
4. 不出现无限循环

---

## Phase 4：挂起恢复协议与前端协同

### 4.1 阶段目标
完善 Human-in-the-loop：挂起、恢复、状态续跑全链路稳定。

### 4.2 本阶段要做什么
1. 统一挂起状态协议
   - `status=awaiting_human`
   - `final_response`/`pending_action` 标准化
2. `service.py` 对接恢复入口
   - 把用户反馈写入 `human_feedback`
   - 重新 invoke 子图
3. 会话状态持久化补齐
   - plan/current_step/gathered_context/last_action
4. 前端响应字段统一（若已有协议则兼容）

### 4.3 怎么做（实施方法）
- 先打通后端状态恢复
- 再适配前端字段
- 保持向后兼容（旧字段可继续返回）

### 4.4 完成交付物
- 挂起恢复协议实现
- 状态持久化字段落库
- 前后端调试样例（2-3个）

### 4.5 验收标准
1. ask_human 挂起后可恢复并继续下一步
2. submit_outline 挂起后用户修改可再次规划
3. 恢复后不丢上下文（plan/context 保留）
4. 单会话多次挂起恢复稳定

---

## Phase 5：灰度切换与旧链路下线

### 5.1 阶段目标
在可回滚前提下完成主路切换，稳定后下线旧 report 固定流水线。

### 5.2 本阶段要做什么
1. Router 按开关/比例切到新引擎
2. 增加关键监控指标
   - 挂起率
   - 重规划率
   - 工具失败率
   - 完成率
3. 小流量观察与问题修复
4. 主路径切换
5. 清理旧 report 节点链与无用代码

### 5.3 怎么做（实施方法）
- 先 5%-10% 流量灰度
- 通过指标阈值再提流
- 保留快速回滚开关直到稳定周期结束

### 5.4 完成交付物
- 新引擎主路上线
- 旧链路降级为回滚备用或删除
- 重构清理 PR（删除无用 report 固定流程）

### 5.5 验收标准
1. 新引擎成为默认主路
2. 关键指标达到预期（完成率稳定、失败率可控）
3. `service.py` 仅保留总装/流式/路由职责
4. 旧 report 固定流水线不再参与主执行

---

## 6. 每阶段完成后的统一检查清单

每个阶段结束必须执行：

1. **功能检查**：核心用例至少 3 条通过
2. **错误检查**：lints/运行时异常清零或可解释
3. **回归检查**：chat/research 基本路径不受影响
4. **文档更新**：记录阶段结果、风险、遗留项
5. **是否可回滚**：确保开关可恢复旧链路

---

## 7. 进度里程碑（建议）

- M1（Phase 1完成）：引擎骨架可跑
- M2（Phase 2完成）：真实工具可执行
- M3（Phase 3完成）：Skill 驱动闭环可跑
- M4（Phase 4完成）：挂起恢复稳定
- M5（Phase 5完成）：主路切换与清理完成

---

## 8. 接下来执行方式（严格按进度）

从现在开始按以下规则执行开发：

1. 仅做当前阶段事项，不跨阶段扩展
2. 每完成一个阶段先验收再继续
3. 阶段失败先修复，不带病进入下阶段
4. 所有变更对照本文档逐项勾选
