# Chat V2 视频多模态接入设计

日期：2026-04-16

## 目标

在不替换现有 `chat v2` 主对话链路的前提下，为系统补齐视频多模态能力，覆盖两条入口：

- 知识库视频：视频上传后进入现有视频检索/向量化链路，能够在主聊天中被命中并参与回答
- 聊天直传视频：用户可在聊天输入区直接发送视频，视频会像图片一样进入消息历史、当前对话状态，并在后续轮次继续可用

回答模型继续使用已切换完成的 `qwen3.5-plus`。

## 范围

本次设计覆盖：

- 教师端知识库视频继续接入主聊天回答链路
- `chat v2` 新增 `input_videos`
- 聊天输入区支持选择视频文件并发送
- 视频消息持久化到历史消息和当前对话状态
- 回答阶段把用户直传视频和知识库命中视频一起组装到多模态消息中
- 前端消息气泡和证据区能够回显视频

本次设计不覆盖：

- 视频检索排序优化
- 视频自动摘要增强、ASR、OCR、关键帧讲解
- 视频编辑、裁剪、封面生成
- 将主聊天整体切换为 `rag_v2/query_stream`

## 设计原则

1. 保留 `chat v2` 作为主对话总线

现有主链路已经承载了这些能力：

- 状态卡片
- workflow 路由
- 报告 / PPT / 教案等生成工作流
- artifact / conversation reference
- 图片输入持久化
- 历史消息与当前对话状态维护

因此不直接切换到 `rag_v2/query_stream`。`query_stream` 适合作为“纯 RAG 流式问答接口”，但不适合作为当前主系统的整体替代。视频能力应注入 `chat v2`，而不是反过来让主系统迁就 `query_stream`。

2. 知识库视频优先复用现有视频底座

项目中已有：

- `/api/video/upload`
- `/api/video/jobs/{job_id}`
- `/api/video/search`
- 旧的 `video_search_for_chat`

这套链路已经具备视频切片、向量化和检索能力。知识库视频先复用这一套，而不是立刻把所有视频能力改写到 `rag_v2/import_video`。

3. 聊天直传视频与图片走相同持久化思路

聊天直传视频应与图片保持一致的行为模型：

- 先上传，后在 `/api/chat/v2/reply` 中引用
- 元数据进入消息历史
- 元数据进入 conversation state
- 后续轮次自动带回上下文

## 推荐方案

采用“双链路统一回答”的方案。

### 方案 A：推荐

- 知识库视频继续走 `api/video` 上传与检索
- 聊天直传视频新增 `chat v2` 的 `input_videos`
- 回答阶段统一把：
  - 用户直传视频
  - RAG / 视频检索命中视频
  组装成一份多模态上下文

优点：

- 对现有系统侵入最小
- 不会破坏 `chat v2` 的工作流和状态系统
- 能快速上线“视频参与主聊天”的能力

缺点：

- 视频能力暂时分散在 `api/video` 与 `chat v2` 两处

### 方案 B：不推荐

- 知识库视频和聊天直传视频全部改走 `rag_v2/import_video`

优点：

- 长期结构更统一

缺点：

- 会同时冲击现有视频检索、教师端上传、主聊天链路
- 风险大，改造面过宽

### 方案 C：不推荐

- 先不支持真正视频输入，只把视频转摘要文本送给模型

优点：

- 最快

缺点：

- 不是用户期待的“视频参与对话”
- 后面还得重做

## 系统结构

### 一、知识库视频进入主聊天

流程：

1. 教师端上传视频，继续走 `/api/video/upload`
2. 后端视频 ingestion 完成切片和向量化
3. 聊天链路在允许 RAG 时，同时具备文本/图片/视频检索能力
4. 命中视频片段后，将视频元数据写入 `sources`
5. 回答阶段将视频作为多模态上下文输入模型
6. 前端证据区显示视频来源卡片，可预览/播放

这里的关键不是新建一条聊天路线，而是把“视频命中结果”接入当前 `chat v2` 回答 runtime。

### 二、聊天直传视频

新增聊天视频上传入口：

- `POST /api/chat/v2/videos/upload`
- 鉴权方式与图片上传一致
- 存储目录建议：`storage/chat_videos/<owner>/<conversation-or-session>/`

上传响应返回结构化视频元数据，供后续 `/api/chat/v2/reply` 引用。

`/api/chat/v2/reply` 新增字段：

- `input_videos: ChatInputVideoPayload[]`

每个视频项至少包含：

- `video_id`
- `file_name`
- `mime_type`
- `storage_path`
- `relative_path`
- `video_url`
- `source`: `upload`
- 可选：
  - `duration_seconds`
  - `poster_url`

### 三、回答时的视频多模态注入

`fast_chat_runtime` 需要升级为：

- 支持用户输入图片
- 支持用户输入视频
- 支持知识库命中图片
- 支持知识库命中视频

统一构造多模态 user content。

逻辑顺序建议：

1. 先构造文本上下文
   - 用户问题
   - 文本知识库摘要
   - web 摘要
2. 再拼接用户直传图片
3. 再拼接用户直传视频
4. 再拼接知识库命中图片
5. 再拼接知识库命中视频

如果模型网关对“视频原文件直接输入”支持稳定，则传视频块。
如果网关只接受特定格式，则在 gateway 层统一转换，不把适配逻辑散落到业务代码中。

## 数据模型

### 请求模型

`ChatRequestV2` / `ChatReplyRequestV2` 增加：

- `input_videos`

### 消息模型

用户消息增加：

- `input_videos`

这样历史回放时，前端可以恢复视频消息气泡，后端也能在后续轮次把它重新送入模型上下文。

### conversation state

最小补丁：

- `last_input_videos`
- `last_input_video_count`

保留现有：

- `last_input_images`
- `last_input_image_count`

这样“当前围绕哪一个多模态资料继续讨论”仍然可以由状态层表达。

## 前端行为

### 知识库视频

教师端 `SourcePanel` 继续支持上传视频，保持现有行为。

需要补齐：

- 视频在左侧列表中作为知识源显示
- 视频可进入文档/资料预览
- 视频命中后在聊天证据区能看见，而不是只作为隐形检索结果

### 聊天直传视频

`ChatPanel` 增加视频选择按钮能力：

- 支持本地选择视频文件
- 发送前显示待发送视频卡片
- 允许删除待发送视频
- 成功发送后清空 pending 视频

历史消息加载时：

- 如果消息带 `input_videos`，则在用户消息气泡上方显示视频预览卡
- 若视频受保护，则通过带 token 的媒体加载方式转 blob URL 后展示

## 与 `query_stream` 的关系

`query_stream` 与当前主聊天链路的区别：

- `query_stream` 是单一的 RAG 问答接口
- `chat v2` 是系统级编排接口，承担工作流、状态写回、历史回放、生成任务等功能

因此本设计不让主系统“切到 `query_stream`”，而是只借鉴其中适合的视频/多媒体上下文组织方式：

- 命中视频后输出结构化 `sources`
- 组装受保护的媒体 URL
- 在多模态 prompt 中统一引入视频

## 错误处理

### 知识库视频

- 视频上传失败：保留现有 job 状态和失败原因
- 视频检索失败：不阻断普通聊天，降级为无视频上下文

### 聊天直传视频

- 文件类型不支持：前端立即提示
- 上传成功但文件丢失：发送时返回明确错误
- 模型端视频输入失败：
  - 优先降级为文本 + 非视频上下文回答
  - 不丢失消息历史里的视频记录

## 测试

后端：

- `chat v2` schema 接受 `input_videos`
- 视频上传接口返回标准化元数据
- conversation persistence 正确写入消息级 `input_videos`
- state 正确写入 `last_input_videos`
- runtime 能将历史用户视频重新注入上下文
- 知识库视频命中后可进入主聊天 `sources`

前端：

- `ChatPanel` 支持待发送视频卡片
- 发送 payload 包含 `input_videos`
- 历史消息可恢复视频消息
- 视频消息走带鉴权的媒体预览加载
- `SourcePanel` 保持原有视频上传流程不回退

## 分阶段实施建议

### Phase 1：知识库视频接入主聊天

- 保持 `/api/video/upload` 不变
- 将视频命中结果接入 `chat v2` 回答链路
- 在证据区显示视频来源

### Phase 2：聊天直传视频

- 新增 `/api/chat/v2/videos/upload`
- `ChatPanel` 增加视频发送
- `reply` 增加 `input_videos`
- 历史消息与状态持久化

### Phase 3：多轮上下文统一

- 历史用户视频自动回注模型
- 当前对话状态可感知最近视频输入
- 证据区与消息区体验统一

## 结论

这次视频接入应坚持两点：

- 不替换 `chat v2` 主对话链路
- 先复用现有知识库视频底座，再把聊天直传视频并入同一回答 runtime

这样可以在不破坏现有图片、多轮历史、状态卡片和工作流能力的前提下，逐步把视频真正接进主系统。
