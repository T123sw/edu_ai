# 报告生成工作流重构设计：上下文整理驱动、关键缺口追问、软确认后生成

## 1. 背景与问题

当前报告生成工作流已经能够接收来自对话系统的上下文，并且能够把部分上下文预填到报告引擎中。但当前主流程仍然存在三个结构性问题：

1. 报告工作流仍然过度依赖旧槽位模型。
2. 对话上下文虽然被注入，但没有先被系统性整理成“报告可直接消费的输入结构”。
3. 现有“槽位是否充分”的判断偏严，导致本可直接生成一版报告的场景仍然被多轮追问打断。

这会带来以下实际体验问题：

- 用户已经进行了多轮对话，但进入报告生成后，系统仍像“从零开始”一样追问。
- 对话中的有效内容无法稳定映射到报告引擎可用输入。
- 生成前追问过多，打断用户心流。
- 槽位模型过窄，无法承接对话中已经形成的主题、重点、证据、约束与分析方向。

因此，本次重构的目标不是“继续修补旧槽位”，而是将报告生成工作流改造成：

**先理解和整理上下文，再判断是否缺关键项；只有缺关键项时才追问，否则经过一次软确认后直接生成。**


## 2. 重构目标

本次重构的目标如下：

1. 报告引擎不再以旧的窄槽位作为主入口，而是以“报告输入结构”作为主入口。
2. 对话系统传入的上下文先由大模型进行分析、筛选、归纳，再映射到报告输入结构。
3. 去掉当前基于旧槽位的强制“充分性评估”机制，尤其是当前过强的 `focus_assessor` 门禁。
4. 保留“关键信息是否足够生成报告”的判断，但该判断必须建立在新的报告输入结构上，而不是旧槽位上。
5. 当上下文已经足够时，只进行一次软确认，然后直接进入报告生成。
6. 当上下文不足时，只追问关键缺口，而不是追问所有可补充信息。


## 3. 新的报告生成流程

### 3.1 总体流程

新的报告工作流应调整为：

`对话上下文 + 当前请求`
-> `上下文整理器（LLM）`
-> `报告输入结构`
-> `关键信息充分性判断`

然后分成两条路径：

#### 路径 A：上下文已足够

`报告输入结构`
-> `软确认`
-> `生成报告`

#### 路径 B：上下文不足

`报告输入结构`
-> `关键缺口识别`
-> `单轮追问关键缺口`
-> `补全后重新判断`
-> `软确认`
-> `生成报告`


### 3.2 流程原则

新的流程必须遵守以下原则：

1. 先整理，再判断，再决定是否追问。
2. 追问是例外分支，不是默认主流程。
3. 只要信息足够生成一版方向明确、结构成立、可继续迭代的报告，就应允许先生成。
4. 可增强信息的缺失，不应默认阻止生成。


## 4. 新的报告输入结构

报告工作流不再直接依赖旧的 `core_topic / focus_area / length_requirement / depth_level / format_style / dynamic_constraints` 作为主模型，而是采用新的三层输入结构。

### 4.1 第一层：关键必填层

这层决定“能不能生成一版报告”。

- `report_intent`
  - 当前用户是否明确要求生成报告。
  - 例如：`generate_report`

- `report_subject`
  - 这份报告围绕什么主题或对象来写。
  - 例如：`关羽北伐失败原因`
  - 例如：`Skills 与 MCP 的差异`

- `report_focus`
  - 本次报告重点展开哪个角度。
  - 例如：`军资供应如何引发内部失和`
  - 例如：`Skills 与 MCP 在工具集成方式上的差异`

- `report_context_summary`
  - 基于当前对话和资料整理出的报告生成摘要。
  - 作用不是展示，而是作为报告生成前的“压缩上下文包”。


### 4.2 第二层：重要增强层

这层会显著提升生成质量，但不应默认阻止生成。

- `key_points`
  - 已提炼出的核心观点、结构要点、分析维度。

- `evidence_points`
  - 可用于支撑报告论述的事实、观察、引用或证据。

- `constraints`
  - 生成约束，例如：
    - `audience`
    - `tone`
    - `length`
    - `grade_level`
    - `subject`
    - `extra_constraints`

- `source_scope`
  - 本次输入来自哪些来源：
    - 当前会话
    - 文档
    - 课程
    - 历史 artifact

- `current_course_id`
- `selected_doc_ids`
- `referenced_artifact_ids`


### 4.3 第三层：辅助状态层

这层主要用于工作流控制，不直接决定用户是否可以生成。

- `open_questions`
  - 仍未明确、但可能影响报告质量的问题

- `missing_critical_fields`
  - 当前缺失的关键字段列表

- `confidence`
  - 报告输入结构的置信度

- `soft_confirm_message`
  - 本轮软确认文案

- `followup_candidates`
  - 若信息不足，系统建议追问的候选问题


## 5. 关键信息充分性判断

### 5.1 本次保留什么

本次重构保留“是否足以生成报告”的判断。

### 5.2 本次去掉什么

本次重构去掉当前这种基于旧槽位、且偏严的“充分性评估”方式，尤其不再让：

- `focus_assessor`
- “还可以更具体，所以继续追问”

成为主流程门禁。


### 5.3 新的判断问题

新的判断问题应当是：

**“当前上下文是否已经足以生成一版方向明确、结构成立、可继续迭代的报告？”**

而不是：

- 当前槽位是否百分百完整
- 当前 focus 是否足够精细到无需后续修改


### 5.4 新的关键判断字段

第一版建议只把以下 3 项作为真正的关键必填：

- `report_intent`
- `report_subject`
- `report_focus`

这些字段缺失时，才应触发追问。

以下字段虽然重要，但不应默认阻止生成：

- `length`
- `tone`
- `audience`
- `evidence_points`
- `current_course_id`
- `selected_doc_ids`


### 5.5 何时视为“信息已足够”

只要满足以下任一组合，即可认为已具备“生成一版报告”的条件：

1. 有 `report_subject` + 有 `report_focus` + 有 `report_context_summary`
2. 有 `report_subject` + 有 `key_points`
3. 有 `report_subject` + 有较强 `evidence_points`
4. 有 `report_subject` + 最近相关消息足以表达核心分析方向

此时应直接进入软确认，而不是继续追问。


## 6. 追问机制重构

### 6.1 追问的定位

追问不再是“补槽位”，而是“补关键缺口”。

### 6.2 触发追问的条件

只有以下情况才触发追问：

- `report_subject` 不明确
- `report_focus` 不明确
- `report_subject` 与 `report_focus` 明显冲突
- 当前用户意图不明确，不确定是继续讨论还是立即生成报告
- 对话内容过于分散，无法整理出一版可生成报告的输入结构


### 6.3 追问的原则

1. 一次只追问一个关键问题。
2. 优先追问最影响生成的问题。
3. 不追问可增强信息。
4. 补齐关键缺口后，应立即重新判断是否可直接进入软确认。


### 6.4 追问类型

第一版建议只保留以下几类追问：

- `subject_missing`
  - 你希望这份报告围绕哪个主题来写？

- `focus_missing`
  - 你更希望这份报告重点展开哪个角度？

- `subject_focus_conflict`
  - 你更想写整体概述，还是只聚焦其中一个问题？

- `intent_unclear`
  - 你是想继续分析，还是现在直接生成报告？


## 7. 软确认机制

### 7.1 软确认的作用

软确认不再用于确认旧槽位，而是用于确认系统整理后的“报告生成理解结果”。


### 7.2 软确认文案

推荐统一为：

`我将基于“{report_subject}”，重点围绕“{report_focus}”，结合当前对话内容先生成一版报告。可以直接开始吗？`

当存在增强信息时，可轻量补充：

- 面向对象
- 风格
- 篇幅
- 资料来源

但这些只应作为补充说明，不应喧宾夺主。


### 7.3 软确认后的行为

- 用户确认：直接进入报告生成
- 用户修正：回写到报告输入结构后重新软确认


## 8. 例子

### 8.1 例子 A：上下文充分，应直接生成

对话前文已经形成：

- `report_subject = 关羽北伐失败原因`
- `report_focus = 军资供应如何引发内部失和`
- 已有多个事实、证据与分析点

此时用户输入：

`请基于当前内容生成一份报告`

系统应执行：

1. 用 LLM 整理当前对话上下文
2. 形成报告输入结构
3. 判断：已有明确主题、明确重点、足够摘要和证据
4. 不再追问
5. 发起软确认：
   - 我将基于“关羽北伐失败原因”，重点分析“军资供应如何引发内部失和”，先生成一版结构化报告。可以直接开始吗？
6. 用户确认后直接生成

此场景下，不应继续追问：

- 你想具体了解哪个方面？
- 你是更关注原因还是表现？


### 8.2 例子 B：上下文不足，应追问关键缺口

用户只输入：

`帮我生成一份报告`

而前面对话里也没有有效上下文。

系统整理后得到：

- `report_intent = generate_report`
- `report_subject = missing`
- `report_focus = missing`

此时系统应只追问一个关键问题：

- 你希望这份报告围绕哪个主题来写？

等用户补充主题后，再判断是否还缺 `report_focus`。

这里不应一次性追问多个问题，也不应询问全部可增强信息。


## 9. 与当前实现的差异

当前实现偏向：

`上下文 -> 旧槽位预填 -> 槽位充分性评估 -> 追问`

目标实现应转向：

`上下文 -> LLM整理 -> 报告输入结构 -> 关键充分性判断 -> 软确认/追问 -> 生成`

这意味着本次重构不是局部补丁，而是报告 workflow 的入口逻辑重排。


## 10. 本次重构应下掉或降级的旧逻辑

建议下掉或显著降级以下逻辑：

1. 不再让旧槽位模型成为 report workflow 主结构。
2. 不再让 `focus_assessor` 作为默认主门禁。
3. 不再因为“还可以更具体”就默认继续追问。
4. 不再让可增强信息缺失阻止生成。


## 11. 设计结论

报告工作流重构后的核心原则应为：

**先理解上下文，形成一份“可生成的报告输入”；再判断是否缺关键项；只有缺关键项时才追问，否则经过一次软确认后直接生成。**

这将把报告生成从“槽位驱动追问优先”转成“上下文理解优先、关键缺口追问兜底”的流程。
