# 报告生成模块彻底重构实施方案（V6）

## 1. 背景与目标

当前报告模块已经完成了“代码拆分”（`report_agent/report_runtime/report_utils/report_generation`），但主流程仍以传统固定节点思维为主。

本次重构目标是从“固定流水线”升级为“自治循环引擎（Plan -> Execute -> Analyze/Replan）”，实现：

1. **意图路由后自动进入报告自治引擎**
2. **Planner 根据 Skill 动态规划下一步**（非硬编码 if/else）
3. **Executor 统一调用工具**（ask/rag/web/outline/generate）
4. **Analyzer 统一评估结果、重规划、挂起与结束**
5. **支持 Human-in-the-loop**（追问挂起、大纲确认挂起、恢复执行）
6. **保留灰度与回滚能力**，避免一次性替换导致线上风险

---

## 2. 目标架构

### 2.1 顶层流转

- `service.py` 负责：
  - 路由（Router）
  - 主图拼装
  - 会话状态读写
  - 流式输出
- 当意图为报告生成时，路由到 `UniversalReportEngine` 子图

### 2.2 报告子图（自治循环）

子图节点仅保留三个核心节点：

1. **Planner Node**：读取 Skill + 当前状态，产出 1-2 步计划
2. **Executor Node**：执行当前步骤对应工具
3. **Analyzer Node**：评估执行结果并决定：继续 / 重规划 / 挂起 / 结束

建议图结构：

`planner -> executor -> analyzer -> (executor | planner | END)`

---

## 3. 状态模型设计（ReportState）

建议独立状态定义，避免复用旧的“超大 GraphState”：

```python
class PlanStep(TypedDict):
    step_id: str
    description: str
    tool_name: str
    tool_args: Dict[str, Any]
    status: str        # pending/completed/failed
    observation: str

class ReportState(TypedDict):
    # 输入输出
    messages: Annotated[list[BaseMessage], operator.add]
    user_input: str
    final_response: str

    # 自治循环核心
    plan: List[PlanStep]
    current_step_index: int
    gathered_context: Dict[str, str]
    past_steps: Annotated[List[Tuple[str, str]], operator.add]

    # 业务资产
    report_slots: Dict[str, str]
    report_outline: List[Dict[str, Any]]
    report_content: str

    # 控制状态
    status: str         # planning/executing/replanning/awaiting_human/finished
    human_feedback: str
    error: str
```

状态约束：
- 每轮最多执行一个 step
- `awaiting_human` 必须中断并返回前端
- `finished` 必须可直接渲染最终结果

---

## 4. 工具体系设计（Tool Contract）

统一工具接口和返回格式，便于 Analyzer 判断。

### 4.1 工具清单

1. `ask_human_for_clarification(question: str, reason: str)`
2. `submit_outline_for_review(outline_json_str: str)`
3. `rag_search_tool(query: str, top_k: int = 5)`
4. `web_search_tool(query: str)`（可复用 deep_research）
5. `generate_outline_tool(...)`（可选，或由 planner+模板生成）
6. `generate_long_report_content(confirmed_outline_json: str)`
7. `analyze_multimodal_content(...)`（可选，多模态场景）

### 4.2 标准返回建议

```json
{
  "ok": true,
  "tool": "web_search_tool",
  "summary": "检索到3条高相关结果",
  "payload": {...},
  "need_human": false,
  "error": ""
}
```

强约束：
- 所有工具失败必须 `ok=false` + `error`
- 挂起类工具必须 `need_human=true`

## 5. Prompt 设计（核心）

本重构的关键不是“多写逻辑”，而是“把业务逻辑外置为 Skill + 规划提示”。


### 5.1 Planner Prompt（元提示）

Planner Prompt 不写具体业务细节，只写元规则：

- 读取 Skill 作为业务 SOP
- 结合当前状态与工具清单，规划 1-2 步
- 优先补齐缺失信息，再检索，再大纲确认，再正文生成
- 禁止跳过大纲确认直接出正文
- 如果上一步失败，优先给补救计划

建议模板：

```text
你是报告生成引擎的 Planner。

【业务技能规则】
{skill_prompt}

【当前状态】
用户输入: {user_input}
用户反馈: {human_feedback}
草稿记忆: {gathered_context}
历史步骤: {past_steps}

【可用工具】
{tools_desc}

【输出要求】
- 仅输出结构化 JSON 计划
- 每轮最多规划 1-2 步
- step 必须可执行
- 若信息不足，优先 ask_human_for_clarification
- 未确认大纲时禁止 generate_long_report_content
```


### 5.2 Analyzer Prompt（复盘提示）

Analyzer Prompt 负责“判定闭环”：

- 步骤是否成功完成
- 是否需要重规划
- 是否需要挂起等待用户
- 是否可结束任务

建议模板：

```text
你是执行质量审计员 Analyzer。

请评估最新步骤结果并返回：
1) status: running/replanning/awaiting_human/finished
2) updated_plan: 剩余或补救步骤
3) response: 需要给用户看的文本（若挂起/结束）

判定规则：
- 工具失败/空结果 -> replanning
- 调用了 ask_human 或 submit_outline -> awaiting_human
- 所有必要目标完成 -> finished
```


### 5.3 Skill Prompt（业务卡带）

Skill 文件应写 SOP，而不是模型口号。

必须包含：
1. 必填槽位定义
2. 阶段顺序（收集 -> 检索 -> 大纲 -> 正文）
3. 禁令（不可跳步）
4. 失败补救策略
5. 挂起规则

## 6. 节点流转与挂起协议

### 6.1 正常路径

1. Planner 产出 step（如 web_search）
2. Executor 执行工具并记录 observation
3. Analyzer 判断继续执行下一步
4. 直到 finished

### 6.2 挂起路径

触发工具：
- `ask_human_for_clarification`
- `submit_outline_for_review`

Analyzer 返回：
- `status=awaiting_human`
- `final_response=给前端的提问/确认文本`

图结束，等待前端输入后恢复：
- 将用户回复写入 `human_feedback`
- 重新 invoke 子图

### 6.3 失败补救路径

- 若 `rag` 空结果：切 `web`
- 若 `web` 失败：改关键词重试
- 超过最大重试次数：降级到“最小可用大纲 + 用户确认”

## 7. 实施步骤（建议 Sprint）

### Sprint 1：引擎骨架
- 新建 `report_state.py`
- 新建 `universal_report_engine.py`
- 跑通 planner->executor->analyzer 的最小闭环

### Sprint 2：工具标准化
- 新建 `tools/agent_tools.py`
- 接入现有 rag/web/report_generation 逻辑
- 统一返回 schema

### Sprint 3：Skill 注入与挂起
- 读取 `edu-report-agent` Skill 注入 Planner
- 完成 awaiting_human 协议
- 打通前端确认恢复

### Sprint 4：灰度切换
- Router 增加 feature flag（新旧引擎可切换）
- 小流量验证
- 稳定后下线旧 report 固定流水线

---

## 8. 风险与治理

1. **Planner 漂移**：
   - 强制 structured output
   - 每轮短计划
2. **工具不稳定**：
   - Analyzer 强制补救策略
   - 最大重试与降级
3. **状态膨胀**：
   - 固化 ReportState 字段
4. **线上风险**：
   - feature flag 灰度
   - 可回滚旧链路

---

## 9. 验收标准（DoD）

1. 报告请求可完成完整闭环：
   - 规划
   - 工具执行
   - 分析与重规划
   - 大纲挂起
   - 恢复后正文生成
2. 任一工具失败不会直接崩溃，能自动补救或降级
3. Skill 文本替换后行为可变化（无需改核心 Python 逻辑）
4. `service.py` 仅承担总装与流式职责，不再包含报告固定流水线实现

---

## 10. 结语

本方案的核心价值：
- 从“写死流程”升级到“策略驱动执行”
- 从“局部修补”升级到“可复用自治引擎”
- 从“功能耦合”升级到“技能卡带化（Skill-driven）”

建议按 Sprint 顺序推进，先并行验证、后主路切换，确保稳定性与迭代速度。
