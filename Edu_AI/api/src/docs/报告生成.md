### 🗺️ 第一部分：系统架构与四大节点流转

当前图（Graph）的生命周期如下，它像一个高度精密的齿轮组：

1. **🧩 Extractor (提取器 - 图的大门)**
   - **职责**：每次图被唤醒（Invoke），无论新话局还是挂起恢复，**必定先过此门**。它阅读 `user_input` 或 `human_feedback`，利用大模型把对话榨干成 `core_topic` 等结构化槽位，并入状态树。
   - **特殊机制**：如果系统是从 `awaiting_human`（休眠）中醒来，它会在提取后把状态改成 `replanning`，一脚把沉睡的系统踹醒，推入 Planner。
2. **🧠 Planner (规划师 - 引擎大脑)**
   - **职责**：读取当前所有状态（槽位齐不齐？大纲有没有？），结合注入的 `edu-report-agent` SOP 规则，输出后续 1~2 步的具体 Tool 调用计划。
3. **🦾 Executor (执行者 - 无情的打工人)**
   - **职责**：盲目执行 Planner 给的计划。不管报错、超时还是成功，统统封装成统一的 JSON 契约（`ok=True/False`, `need_human=True/False`），并把结果写入 `gathered_context`（草稿本）。
4. **🕵️ Analyzer (分析师 - 质量品控)**
   - **职责**：审视 Executor 的战果。
   - **红绿灯决策**：工具报错？-> `replanning`；工具触发了人类确认？-> `awaiting_human`；正文生成成功？-> `finished`。

### 💉 第二部分：Skills 注入机制（灵魂卡带）

在 `service.py` 启动时，系统读取了 `.cursor/skills/edu-report-agent.md`。这个 Markdown 文件被“一鱼三吃”：

1. **静态解析（喂给 Python 兜底逻辑）**：Python 引擎用正则截取了 `### REPORT_SLOT_SCHEMA` 下的 JSON，知道了哪些槽位是必填项，用来构建 `_fallback_plan`。
2. **动态注入（喂给 Planner & Analyzer）**：SOP 规则、绝对禁令、Few-shot 示例，被整体作为 `skill_prompt` 变量，注入到了 Planner 和 Analyzer 的系统提示词中，指导它们怎么思考。
3. **按需提取（喂给 Executor 底层工具）**：底层的长文生成代码，会利用 `SkillManager` 动态提取文件底部的 `REPORT_CHAPTER_GENERATE_PROMPT`，指导大模型以什么语气写正文。

### 🎬 第三部分：极致推演 —— 全场景实战案例

**场景**：用户想写一份关于《数据结构》中平衡树的报告。

#### 🥊 Round 1：模糊起手，拦截追问
* **用户输入**：“帮我写一份数据结构的报告。”
* **🧩 Extractor**：提取到 `core_topic` = "数据结构"。发现 `focus_area` 为空。
* **🧠 Planner**：读取 SOP 发现阶段 1（缺槽位），生成计划：调用 `ask_human`。
* **🦾 Executor**：执行 `ask_human`，组装话术：“数据结构主题很好，您更想聚焦在哪一块？比如红黑树与AVL树，还是哈希表？”，返回 `need_human=True`。
* **🕵️ Analyzer**：看到 `need_human=True`，将状态置为 `awaiting_human`。
* **🚦 Controller Edge**：遇到 `awaiting_human`，直接 **`__end__` (引擎物理休眠)**。前端收到 SSE 流输出追问话术。

#### 🥊 Round 2：槽位补齐，检索与大纲生成
* **用户回复**：“重点讲红黑树和AVL树的平衡机制对比吧。”
* **（Service 唤醒引擎）**：带着旧记忆，把这句话塞进 `human_feedback`，重新 invoke Graph。
* **🧩 Extractor**：榨取到 `focus_area` = "红黑树与AVL树的平衡机制对比"，更新状态树。并将状态重置为 `replanning`。
* **🧠 Planner**：发现槽位齐了，大纲为空。遵守 SOP，生成计划：先调 `rag_search_tool`，再调 `submit_outline_for_review`。
* **🦾 Executor (执行 Step 1)**：调用 RAG 搜索红黑树资料，写入草稿本。
* **🦾 Executor (执行 Step 2)**：调用大纲工具，生成 AST JSON，并返回 `need_human=True`。
* **🕵️ Analyzer**：看到大纲提交了，将状态置为 `awaiting_human`。
* **🚦 Controller Edge**：**`__end__` (二次休眠)**。前端弹出大纲确认面板。

#### 🥊 Round 3：容错演示（假设发生工具报错的 Edge Case）
* *【假设情况】*：在 Round 2 执行 `rag_search_tool` 时，由于向量库宕机，Executor 抛出了异常！
* **🦾 Executor**：捕获异常，包装返回 `{"ok": False, "error": "connection refused"}`。
* **🕵️ Analyzer**：发现 `ok=False`。遵守 SOP 禁令，不吞错，将状态置为 `replanning`，并在 JSON 里输出 `updated_plan: [{"tool_name": "web_search_tool"}]` (自动降级为全网搜索)。
* **🚦 Controller Edge**：遇到 `replanning`，流转回 Planner，系统**完成自我修复**，不会卡死！

#### 🥊 Round 4：大纲确认，终极生成
* **用户回复**：“大纲没问题，直接生成吧。”
* **（Service 唤醒引擎）**：把这句话塞进 `human_feedback`。
* **🧩 Extractor**：发现没有新槽位，清空 feedback，进入 `replanning`。
* **🧠 Planner**：槽位满，大纲满，且用户已同意。遵守 SOP 阶段 4，规划：调用 `generate_long_report_content`。
* **🦾 Executor**：唤醒底层 `build_report_markdown`，读取卡带里的 `REPORT_CHAPTER_GENERATE_PROMPT`，耗时 30 秒，写出 3000 字的高质量正文。把结果写入状态树的 `report_content`。
* **🕵️ Analyzer**：发现 `report_content` 存在，判定任务彻底完成。输出状态 `finished`。
* **🚦 Controller Edge**：遇到 `finished`，**`__end__` (彻底结束)**。
* **（Service 收尾）**：捕获到 finished，将最终生成的报告保存到数据库，返回给前端。
