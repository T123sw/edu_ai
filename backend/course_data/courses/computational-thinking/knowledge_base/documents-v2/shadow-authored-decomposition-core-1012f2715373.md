## 学习目标
1. 理解问题分解的本质，能够将复杂计算问题划分为独立的子问题。
2. 掌握子问题边界的定义方法，明确输入输出接口规范。
3. 能够评估分解方案的合理性，识别高耦合与低内聚的设计缺陷。

## 准确概念与边界
问题分解（Problem Decomposition）是指将一个难以直接解决的大型问题，划分为若干个规模较小、相互独立且易于解决的子问题的过程。子问题边界（Subproblem Boundary）则是划分这些子问题的界限，通常通过“接口”（Interface）来体现。

在计算思维中，边界的核心在于**信息隐藏**与**契约式设计**。一个良好的边界意味着子问题内部的具体实现细节对外部不可见，外部仅需知道如何通过接口传递数据并获得结果。界定的关键在于数据流与控制流：
- **数据流边界**：明确子问题接收什么格式的数据（输入），返回什么格式的结果（输出）。
- **控制流边界**：明确子问题在什么条件下被调用，以及异常情况下如何反馈。

若两个子模块之间共享过多内部变量，则称为**高耦合**，意味着边界模糊；若一个模块内部功能杂乱，承担过多职责，则称为**低内聚**，意味着分解粒度不当。

## 机制与步骤
实施问题分解通常遵循以下四步机制：
1. **目标抽象**：明确最终要解决的核心问题是什么，忽略次要细节。
2. **自然切割**：根据数据处理的阶段或功能逻辑，寻找自然的断点。例如，数据处理通常分为“输入 - 处理 - 输出”三个阶段。
3. **接口定义**：在切割处定义明确的接口规范，包括参数类型、返回值及异常处理。
4. **独立求解与集成**：分别实现子问题，并通过接口将它们连接起来验证整体功能。

数学上，若原问题为 $P$，分解后的子问题集合为 $\{p_1, p_2, ..., p_n\}$，则需满足：
$$ P \approx \bigcup_{i=1}^{n} p_i $$
且子问题间的交集（耦合度）应最小化，即 $p_i \cap p_j \rightarrow \emptyset$（逻辑依赖最小）。

## 完整示例：文本词频统计
假设需要编写程序统计一篇英文文章中出现频率最高的前 10 个单词。

**分解方案：**
1. **子问题 A（数据加载）**：读取文件内容，返回原始字符串。
2. **子问题 B（文本清洗）**：接收字符串，去除标点、统一大小写，返回单词列表。
3. **子问题 C（频率计算）**：接收单词列表，统计频次，返回字典。
4. **子问题 D（结果排序）**：接收字典，排序并截取前 10 名，返回最终列表。

**接口与代码实现（Python）：**
```python
def load_text(path):
    # 子问题 A：边界为文件路径输入，字符串输出
    with open(path, 'r', encoding='utf-8') as f:
        return f.read()

def clean_text(text):
    # 子问题 B：边界为原始字符串输入，单词列表输出
    words = ''.join(c if c.isalpha() else ' ' for c in text).lower()
    return words.split()

def count_words(words):
    # 子问题 C：边界为列表输入，字典输出
    freq = {}
    for w in words:
        freq[w] = freq.get(w, 0) + 1
    return freq

def get_top_n(freq_dict, n=10):
    # 子问题 D：边界为字典输入，列表输出
    return sorted(freq_dict.items(), key=lambda x: x[1], reverse=True)[:n]

# 集成主流程
def main():
    text = load_text('article.txt')
    words = clean_text(text)
    freq = count_words(words)
    result = get_top_n(freq)
    print(result)
```
在此示例中，`clean_text` 与 `count_words` 之间的边界非常清晰：前者不负责计数，后者不负责清洗。若需修改清洗规则（如保留数字），只需修改 `clean_text`，不影响其他模块。

## 复杂度与权衡
分解并非越细越好。过度分解会增加**接口调用开销**与**系统复杂性**。
- **时间复杂度**：函数调用本身存在栈帧开销，若子问题粒度过小（如将每个加法操作封装为函数），总耗时 $T_{total} = \sum (t_{exec} + t_{call})$ 会显著增加。
- **维护成本**：接口越多，修改一处可能引发的连锁反应越大。
- **权衡原则**：子问题的粒度应使得单个模块的逻辑复杂度控制在人类认知范围内（通常一个函数不超过 50 行代码），同时保证接口稳定性。

## 常见误区
| 误区 | 正确理解 |
| :--- | :--- |
| 认为分解就是随意拆分代码行 | 分解必须基于逻辑功能，而非物理行数。 |
| 忽略接口的一致性 | 子问题间传递的数据结构必须明确约定，避免隐式依赖。 |
| 子问题之间存在状态共享 | 理想的子问题应是无状态的，或通过参数显式传递状态。 |

## 自测题与答案
1. **问**：在词频统计示例中，若将“读取文件”与“清洗文本”合并为一个函数，违反了什么原则？
   **答**：违反了单一职责原则，导致模块内聚度降低，后续若需更换数据源（如从数据库读取），则必须修改清洗逻辑。
2. **问**：定义子问题边界时，最重要的文档是什么？
   **答**：接口规范（Interface Specification），明确输入参数类型、返回值及副作用。
3. **问**：若子问题 $p_1$ 的执行结果直接依赖 $p_2$ 的内部变量而非返回值，这属于什么现象？
   **答**：属于高耦合现象，破坏了边界封装性，是不良设计。
