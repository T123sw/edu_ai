## 真实问题情境
某电商仓库需要开发一个“物流运费计算引擎”。业务规则如下：
- 基础运费按重量计算，每公斤 5 元。
- 偏远地区加收 20% 费用。
- 超重货物（超过 50kg）每公斤加收 2 元附加费。
- 系统需接收订单列表，输出包含每单运费的详细报告。
现有代码将所有逻辑写在一个 200 行的主函数中，难以维护且容易算错。你需要将其重构为模块化系统。

## 输入输出或材料
- **输入材料**：一个包含字典的列表，每个字典代表一个订单，结构为 `{"id": "A01", "weight": 10.5, "is_remote": False}`。
- **输出材料**：一个包含计算结果的列表，结构为 `{"id": "A01", "final_fee": 52.5}`。
- **开发环境**：Python 3.8+ 标准环境。

## 分步任务
1. **接口设计**：不写代码，先定义三个函数的签名（名称、参数、返回值）。建议拆分为：重量验证、基础费用计算、总费用组装。
2. **模块实现**：分别实现上述函数，确保每个函数只做一件事。
3. **管道组装**：编写主函数 `process_orders`，调用上述模块处理整个列表。
4. **异常处理**：在验证模块中处理负数重量或非数字输入。

## 参考实现/推导
以下是符合模块化原则的参考实现。注意接口如何隔离变化逻辑。

```python
def validate_weight(weight):
    """接口：输入重量，返回有效重量或抛出异常"""
    if not isinstance(weight, (int, float)):
        raise TypeError("重量必须是数字")
    if weight <= 0:
        raise ValueError("重量必须大于 0")
    return weight

def calculate_base_fee(weight, is_remote):
    """接口：计算单件运费，不包含异常检查"""
    base_rate = 5.0
    fee = weight * base_rate
    if is_remote:
        fee *= 1.2  # 偏远地区加成
    if weight > 50:
        fee += (weight - 50) * 2  # 超重附加
    return round(fee, 2)

def process_orders(orders):
    """接口：处理订单列表，返回结果列表"""
    results = []
    for order in orders:
        try:
            w = validate_weight(order["weight"])
            fee = calculate_base_fee(w, order["is_remote"])
            results.append({"id": order["id"], "final_fee": fee})
        except Exception as e:
            results.append({"id": order["id"], "error": str(e)})
    return results

# 测试数据
data = [
    {"id": "A01", "weight": 10, "is_remote": False},
    {"id": "A02", "weight": 60, "is_remote": True},
    {"id": "A03", "weight": -5, "is_remote": False}
]
print(process_orders(data))
```

## 测试与边界情况
模块化优势在于可独立测试。针对 `calculate_base_fee` 设计测试用例：
1. **正常边界**：重量 50kg，非偏远。预期：$50 \times 5 = 250$。
2. **超重边界**：重量 51kg，非偏远。预期：$51 \times 5 + 1 \times 2 = 257$。
3. **偏远边界**：重量 10kg，偏远。预期：$10 \times 5 \times 1.2 = 60$。
4. **异常输入**：重量 0 或负数。预期：在 `validate_weight` 阶段抛出异常，主程序捕获并记录 error 字段，不导致程序崩溃。

测试代码应独立于主逻辑，例如使用 `assert` 语句验证函数返回值是否符合数学预期。

## 评价量规
| 维度 | 优秀 (5 分) | 合格 (3 分) | 待改进 (1 分) |
| :--- | :--- | :--- | :--- |
| **接口清晰度** | 函数名语义明确，参数类型注释完整，无多余参数。 | 函数名可读，但参数含义需看内部代码才能理解。 | 函数名模糊（如 func1），依赖全局变量传参。 |
| **模块独立性** | 修改运费率只需改一个函数，不影响其他模块。 | 修改逻辑需改动多处，但尚可运行。 | 牵一发而动全身，逻辑硬编码在主循环中。 |
| **异常处理** | 能优雅处理非法输入，程序不崩溃，有错误报告。 | 程序会崩溃，或 silently fail（静默失败）。 | 无任何检查，假设输入永远合法。 |
| **代码复用** | 计算逻辑被封装，可被其他系统调用。 | 逻辑封装但依赖特定数据结构。 | 代码复制粘贴，无复用。 |

## 拓展问题
1. **策略模式应用**：如果运费规则经常变动（如双十一打折），如何设计接口使得无需修改 `process_orders` 就能更换计费规则？提示：将计费函数作为参数传递。
2. **性能优化**：如果订单量达到百万级，函数调用的开销是否显著？如何平衡模块化与性能（如使用向量化操作）？
3. **持久化接口**：设计一个新模块 `save_report`，将结果保存为 CSV 文件。思考该模块应依赖什么接口输入，是否应依赖具体的文件路径字符串？
