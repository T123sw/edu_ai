# 项目拆解与计划审阅

`ProjectPlan` 的机器契约以 `app.pbl.project_workflow.ProjectPlan` 为准；调用 `model_json_schema()` 取得完整 schema。示例 JSON 使用同一契约，不另造字段。

## 计划字段

- `schemaVersion`：当前为 1，与已有公开练习 schema 独立。
- `title`、`goal`：项目名称与最终可观察成果。
- `runtimeKind`：所需执行能力 `js_function` 或 `react_app`；这只是需求声明，不会自动启用平台能力。
- `editableFiles`：建议由学习者编辑的文件；平台仍须与固定模板的许可列表取交集，模型不能借此修改权限。
- `requirements[]`：稳定 `id` 与成果描述 `description`。
- `steps[]`：`id/title/objective`，前置 `dependsOn`，`entryCondition`，完成后 `deliverable`，关联 `requirementIds`、`focusFiles`、`newCheckIds`。
- `checks[]`：`id/stepId/kind/requirementIds/setup/actions/expected/requiredAssertions/viewport`；这是检查规格，不是已执行结果。`expected` 为可省略或为空的说明列表；最终断言由单步材料提供。`function_case` 描述调用和结果，`ui_scenario` 描述真实页面动作和结果。后续转换为固定运行器支持的检查包。

本步 requirementIds 可以包括需要继续保持的前序需求；这些需求由累计执行的前序检查覆盖，无需在本步重复新增检查。尚未覆盖的新需求由本步检查覆盖，不能借用未来检查。每个新增检查仍归属当前步骤并关联本步需求。

首版使用线性主线：第一步无前置，后续依赖紧邻的前一步。同一份工程逐步增加能力；分支、选修和多工程协作不在本契约中悄悄引入。每步允许只关注部分文件，但不能要求修改未声明的文件。

## 拆解方法

1. 从最终成果列出用户能观察到的行为，给每项稳定 ID。按当前目标写明必要的边界行为、无效输入反馈与恢复约定，不预设业务规则。
2. 按依赖和教学负担分组，一组成为一个步骤。每步结束都应有可以运行或检查的新成果。
3. 检查每一步是否有明确起点与增量，避免只按“写 HTML / 写 CSS / 写 JS”或“第 1/2/3 个函数”机械拆分。
4. 为每个验收点写确定的初始状态、操作与预期；“按钮能用”“结果正常”不足以成为业务验收。
5. 将验收点映射到需求和步骤。所有需求最终必须被检查覆盖；同一需求可以跨步骤逐步实现。
6. 只有需求包含布局时才规划相应几何检查，不能仅检查控件存在。将要求写成可测关系并在题面和成果里说明。检查窗口由目标决定，不强制双窗口，也不要求允许滚动的长内容一屏显示。
7. `requiredAssertions` 可省略；布局断言未指定 viewport 时使用 desktop。普通可见性/文字检查仍使用 `visible/enabled/text/value/count`。步骤实际检查覆盖已声明的能力即可，允许额外有效断言；text/value/enabled 可证明 visible。明确指定的窗口继续遵守。
8. 为未来验证器留稳定界面约定，如按钮可访问名称、结果显示区的 role/name；不要强制 CSS 类名或用户内部变量名。

## 可选教学质量参考（不调用独立审阅、不作为发布门槛）

以下用于生成时组织内容；新流程不再要求模型审阅批准：

- 是否仍满足用户原始目标，而非把不会实现的功能删掉后自称完成。
- 前一步的成果是否足以开始下一步。
- 本步检查是否需要未来知识或未来功能。
- 后续正常演进是否会让之前检查无故失败。临时界面若后来需要移除，不应成为永久累计检查；改验收持续保留的成果，或重新设计步骤。
- 初始骨架是否已经替用户完成关键学习目标。

模型审阅意见不能代替程序结构检查或浏览器运行证据。运行能力不足时可以交付“待接入计划”，不能交付可运行项目。
