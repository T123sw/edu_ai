# 累计验收、证据与发布

## 生成期验证

对第 N 步的私有累计参考工程执行第 1..N 步全部检查。每个检查从约定的干净状态开始，跨动作序列内部可以保留状态，不能依赖前一条独立检查遗留的页面状态。全部检查 ID 必须完整、唯一。

运行并记录以下证据；只有参考工程的实际检查失败才阻断发布，教学起点与负例效果记为质量提示：

1. 初始工程可以加载，但没有提前完成整个项目。
2. 第 N 步开始时的参考起点能否通过本步新增检查（通过时提示教学增量不足，不要求重生成）。
3. 本步完成参考工程通过累计检查。
4. 本步典型错误是否触发失败；未失败时记录负例区分度不足。

布局骨架可以含部分必要结构，不要求每个新增检查在起点都失败；若起点已经通过本步全部检查，记录教学增量不足，不阻断参考工程已经通过的项目。

第 N 步不执行 N+1 的检查。最终参考工程和用户最终工程分别在各自同一完整快照上执行全量检查，不合并多个历史通过报告凑出全项目通过。

## 报告身份与可信边界

宿主生成 projectId、artifactVersion、planHash、stepId、templateVersion、checkPackageHash、workspaceHash、runId；模型不填写用户完成状态。报告包含实际执行的 check IDs、状态、观察值和错误分类。未知、重复、缺失、旧版本或旧快照的结果不计为当前通过。

多文件 workspaceHash 使用现有源码哈希规则的扩展：规范文件路径排序后，以 UTF-8 对路径/内容对的确定性 JSON 序列化计算 SHA-256；模板与检查包另带版本/哈希，不能仅哈希编辑器当前文件。Python/前端实施时必须共享测试向量。

浏览器自行上报的结果继续标 `browser_reported`；服务端运行证据单独标记，不混淆来源。能通过功能检查不证明使用了指定算法或已经掌握知识。

编辑后保留“曾在快照 X 通过”的学习历史，当前工程标为待复验。完成下一步需当前快照累计检查通过；回看教程不受此限制。工程保存成功与检查通过是两个独立状态。

## 恢复记录与发布

检查点最少包含 phase、Skill 版本、planHash、stepId、模板/检查包版本、参考快照哈希、材料/检查报告引用、修复次数和错误分类。计划或检查契约变更后，旧证据不可复用；失效范围包括受影响步骤及其后续步骤。取消/租约失效后不得发布。

发布前程序确认所有步骤材料齐全、检查集合覆盖全部需求、私有参考验证通过、公开白名单正确，并完成持久化回读。公开材料只含教程、允许的起始文件、步骤目录、契约和公开检查要求；不含参考答案、模型推理、私有失败源码或凭据。

若只有计划 JSON 或模拟报告，状态只能是计划/草稿。不得写入 `saved=true`、用户完成、项目已上线等标记来替代真实工具回执。
