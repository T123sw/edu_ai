# 项目拆解与计划审阅

`ProjectPlan` 的机器契约以 `app.pbl.project_workflow.ProjectPlan` 为准；调用 `model_json_schema()` 取得完整 schema。示例 JSON 使用同一契约，不另造字段。

本次调用先按宿主 templates 与 constraints 判断整个目标能否运行。若必要能力不可用，只输出 `{"unsupportedGoal":"缺少的运行能力及原因"}`，不继续生成 steps 或“待接入计划”。这仍是同一次规划调用，不增加审阅阶段。当前 Nodebox 不支持带请求体的 HTTP 交互，包括 JSON、表单、上传；即使 Express 本身能实现，也不代表宿主能执行和验收。用户要求这些能力时直接说明不支持，不将其改写为查询参数、模拟请求或只做读取部分。

## 计划字段

- `schemaVersion`：当前为 1，与已有公开练习 schema 独立。
- `title`、`goal`：项目名称与最终可观察成果。
- `runtimeKind`：所需执行能力 新工程填写 `sandpack_project`，同时提供 runtime（模板、入口、额外依赖）和 editableFiles。旧 js_function/react_app 仅供兼容。
- `editableFiles`：学习者可编辑的完整工程文件清单，最多 32 个文本文件；宿主管理 package.json 和测试文件，模型不能修改这些保留路径。
- `requirements[]`：稳定 `id` 与成果描述 `description`。
- `steps[]`：`id/title/objective`，前置 `dependsOn`，`entryCondition`，完成后 `deliverable`，关联 `requirementIds`、`focusFiles`、`newCheckIds`。
- `checks[]`：`id/stepId/kind/requirementIds/setup/actions/expected/requiredAssertions/viewport`；这是检查规格，不是已执行结果。`expected` 为可省略或为空的说明列表；最终断言由单步材料提供。`function_case` 描述调用和结果，`ui_scenario` 描述真实页面动作和结果；`http_scenario` 描述 Node 服务请求及响应。后续转换为固定运行器支持的检查包。

本步 requirementIds 可以包括需要继续保持的前序需求；这些需求由累计执行的前序检查覆盖，无需在本步重复新增检查。尚未覆盖的新需求由本步检查覆盖，不能借用未来检查。每个新增检查仍归属当前步骤并关联本步需求。

首版使用线性主线：第一步无前置，后续依赖紧邻的前一步。同一份工程逐步增加能力；分支、选修和多工程协作不在本契约中悄悄引入。每步允许只关注部分文件，但不能要求修改未声明的文件。

## 拆解方法

1. 从最终成果列出用户能观察到的行为，给每项稳定 ID。按当前目标写明必要的边界行为、无效输入反馈与恢复约定，不预设业务规则。
2. 按依赖和教学负担分组，一组成为一个步骤。每步结束都应有可以运行或检查的新成果。
3. 检查每一步是否有明确起点与增量，避免只按“写 HTML / 写 CSS / 写 JS”或“第 1/2/3 个函数”机械拆分。
4. 为每个验收点写确定的初始状态、操作与预期；“按钮能用”“结果正常”不足以成为业务验收。
5. 将验收点映射到需求和步骤。所有需求最终必须被检查覆盖；同一需求可以跨步骤逐步实现。
6. 只有需求包含布局时才规划相应几何检查，不能仅检查控件存在。将要求写成可测关系并在题面和成果里说明。检查窗口由目标决定，不强制双窗口，也不要求允许滚动的长内容一屏显示。
7. `requiredAssertions` 可省略；布局断言未指定 viewport 时使用 desktop。普通逻辑与组件行为随后使用当前模板支持的标准 Jest、页面操作或 Node HTTP，requiredAssertions 无需填写，也不作为普通断言类型门槛；禁用、选中、空集合等可直接表达。几何检查使用 Playwright，明确指定的窗口继续遵守。
8. 为未来验证器留稳定界面约定，如按钮可访问名称、结果显示区的 role/name；不要强制 CSS 类名或用户内部变量名。

## 可选教学质量参考（不调用独立审阅、不作为发布门槛）

以下用于生成时组织内容；新流程不再要求模型审阅批准：

- 是否仍满足用户原始目标，而非把不会实现的功能删掉后自称完成。
- 前一步的成果是否足以开始下一步。
- 本步检查是否需要未来知识或未来功能。
- 后续正常演进是否会让之前检查无故失败。临时界面若后来需要移除，不应成为永久累计检查；改验收持续保留的成果，或重新设计步骤。
- 初始骨架是否已经替用户完成关键学习目标。

模型审阅意见不能代替程序结构检查或浏览器运行证据。运行能力不足时仅返回 unsupportedGoal，当前接口不发布“待接入计划”。


## 从需求行为推导可区分的场景

在本次生成中把需求展开为“对象 × 操作 × 前置状态 × 可观察结果”，再对照前序检查实际执行的动作和断言补齐本步覆盖。requirementId 被引用不代表其中所有行为已验证。无需输出另一份审阅报告，也不增加模型调用或审核关卡。

- 同一规则适用于多个独立对象时，各对象都要验证正常变化与需求明确的边界；一个对象正确不能代替另一个对象。操作后同时观察目标对象和应保持不变的对象，避免误操作、串状态。
- 区分“动作没有效果”和“在边界本来就不该变化”。从能产生变化的状态执行并断言变化，再从边界执行并断言边界；只在边界点击无法发现空处理函数。
- 可逆操作验证完整往返；多状态入口从不同状态进入并回到默认状态，不只检查初始默认状态。每次转换后读取结果，只有点击没有后续断言不证明行为。
- 同一清理或重置动作可能作用于多种旧状态。按需求从各类可观察旧状态触发，分别验证旧内容消失与新内容正确，而非只验证一种旧状态。
- 集合操作使用至少两个可区分的对象验证隔离；筛选后的局部显示与全局统计分别检查。仅在需求涉及这些能力时采用，不额外发明业务规则。

在计划既有检查 ID 内增加必要的动作与断言即可，不因覆盖细化而删改检查 ID。每项新页面自带准备过程；长场景可合理分配给本步现有检查。每个 label 准确描述实际覆盖的行为。预期由需求决定，参考代码仅用来确定目标和操作接口。优先选能区分常见错误的输入与状态，不追求无意义的组合穷举。

按需求选择模板，不默认将 Vue、原生 JS 或 Node 转为 React。入口须在 editableFiles 中；运行所需的入口、HTML、组件和模块均列入清单，不列 package.json。参考宿主 starterFiles 决定入口结构。Node 默认 CommonJS，监听 3000；前端与 API 同源，不依赖真实数据库或外部服务。

当前启用模板以宿主 templates 为准；不要选择未列出的 Vue TypeScript 模板。static 用于 HTML/CSS，原生 JavaScript 交互选 vanilla。Node 仅无请求体接口；需要 JSON 请求体、数据库或外部服务的目标明确说明暂不支持，不缩减需求。
