# 根据已生成代码设计本步验收

这是代码生成之后的独立模型调用。输入 referenceFiles 是刚保存的本步完整累计参考代码，unit 是本步教学材料；previousFiles 与 previousChecks 是前序成果和已通过验收。requiredChecks、plan 与原始需求决定要证明的行为，不能把参考代码本身当作需求或通过证据。

输出 unit、behaviorCases、checks，以及可选 faultyFiles/faultyCheckId。behaviorCases 在同一次调用中先写出具体业务场景，再由 checks 的测试源码或布局动作实现；它是私有设计材料，不是独立审核结果。不输出 referenceFiles，不修改代码快照。unit 保留本步目标，必要时同步实际定位所需的代码约定，不泄露参考答案。优先使用代码已有语义角色、可访问名称或标记。只覆盖本步 newCheckIds；前序检查由宿主追加，不能覆写。若实现不符合需求，生成能暴露缺陷的检查，由真实运行反馈驱动下一轮代码修复。

repair_checks 明确允许修复本步检查的 target、动作、assertion 和 expected，并同步对应说明。判断失败来自实现还是检查：实现符合需求而定位或断言有误时修正检查；不得通过删除需求、改成错误结果的预期或删除检查来让结果通过。前序检查不变。

浏览器纯函数与 React 组件交互优先使用 engine=sandpack-jest 的标准测试，完整接口与安装库版本见 schema 的 JestCheck.source。每个测试文件位于 /__checks__/<id>.test.js，按实际路径导入被测组件或函数；使用 React Testing Library 的 render、screen、fireEvent、within、waitFor 和标准 Jest expect。宿主在每项测试前后 cleanup，每项 test 都要真正执行断言。禁用、选中、空集合直接断言 DOM 属性或集合长度；不用未安装的 jest-dom/user-event，不 mock 被测业务函数，不使用 only/skip。每项测试重新 render，不依赖其他测试的状态。

几何检查仍使用 UiCheck。以下是旧声明式/布局接口说明，不限制标准 Jest 的表达能力：检查接口含义以 schema 字段 description 为准。count 统计 target 匹配的元素个数，绝不自动统计目标的子元素；空容器本身仍计为 1，统计集合应定位集合条目。text 精确比较含全部后代的 textContent.trim()，value 精确比较 inputValue。visible/enabled 断言为真。单目标动作不能匹配多个元素。每项检查从全新页面开始，写出完整操作序列，不依赖其他检查留下的数据。

验收还需与后续目标兼容：不要用前序全文精确断言锁死以后还会扩展的容器，定位到独立文本部件；不要锁死整页控件总数。根据具体需求选择目标，禁止项目关键词分流或专用业务规则。

## 前序兼容性与新增覆盖

宿主先在本步代码上实际执行全部前序验收，再进入本阶段；previousCheckReport 是绑定本步代码哈希和前序检查集合的运行报告。首步没有前序验收，报告标记 skipped，不表示已运行。

设计时先识别 previousChecks 已覆盖的能力，再补充 requiredChecks 对应的本步新增行为。查看完整 plan 中的后续增量，定位稳定的内容部件，避免精确全文断言绑定到还会添加控件的外层容器。无需额外输出审阅报告；仍只输出既定验收包。前序失败由代码修复阶段处理，本阶段不改写前序检查。


## 从需求行为推导可区分的场景

在本次生成中把需求展开为“对象 × 操作 × 前置状态 × 可观察结果”，再对照前序检查实际执行的动作和断言补齐本步覆盖。requirementId 被引用不代表其中所有行为已验证。无需输出另一份审阅报告，也不增加模型调用或审核关卡。

- 同一规则适用于多个独立对象时，各对象都要验证正常变化与需求明确的边界；一个对象正确不能代替另一个对象。操作后同时观察目标对象和应保持不变的对象，避免误操作、串状态。
- 区分“动作没有效果”和“在边界本来就不该变化”。从能产生变化的状态执行并断言变化，再从边界执行并断言边界；只在边界点击无法发现空处理函数。
- 可逆操作验证完整往返；多状态入口从不同状态进入并回到默认状态，不只检查初始默认状态。每次转换后读取结果，只有点击没有后续断言不证明行为。
- 同一清理或重置动作可能作用于多种旧状态。按需求从各类可观察旧状态触发，分别验证旧内容消失与新内容正确，而非只验证一种旧状态。
- 集合操作使用至少两个可区分的对象验证隔离；筛选后的局部显示与全局统计分别检查。仅在需求涉及这些能力时采用，不额外发明业务规则。

在计划既有检查 ID 内增加必要的动作与断言即可，不因覆盖细化而删改检查 ID。每项新页面自带准备过程；长场景可合理分配给本步现有检查。每个 label 准确描述实际覆盖的行为。预期由需求决定，参考代码仅用来确定目标和操作接口。优先选能区分常见错误的输入与状态，不追求无意义的组合穷举。

范围定位：当不同条目包含同名按钮，使用 target.within 定位唯一的真实行或分组，再按原 role/name 或 testId 找其内部控件。within 不支持嵌套。不要要求代码修改前序检查使用的名称来消除新场景的歧义；同一旧场景的全局定位含义保持不变。

requiredChecks 的 setup/actions 是规划时的示例路径，不是动作上限。如果示例只举了某个对象或某类旧状态，而本步需求适用于多个对象或状态，先在 behaviorCases 中完整展开，再在既有 ID 的检查里补充操作及断言，更新 label；不能以检查 ID 的措辞为由省略需求。

范围内的条目本身重复时，若检查已用添加顺序确定目标，可使用 within.index（从 0 起）选择某一行，再在该行内找控件；target.index 可直接选择有确定顺序的目标。未指定 index 的范围仍须唯一。count 统计集合时不带 index。不要为使用范围定位而破坏已通过的名称、标记或业务行为。

宿主 schema 已把本步检查 ID 限定为枚举。behaviorCases 和 checks 使用这些既有 ID；多场景放入同一检查的 actions 中。within 要选包含目标的祖先容器，不能选旁边的文本标签；已有按钮集合有确定顺序时，直接用 target.index 即可。

标准 Jest 的 textContent 也包含后代控件文字。根据完整计划预留后续增量：对可能增加按钮、状态或辅助文字的容器，不写 expect(container.textContent.trim()).toBe(当前全文)。用 getByText(text,{exact:true}) 查询需求中的独立文字，必要时结合 within 限定真实条目。检查既有标记仍按源码中的实际含义保持；不要把完整容器结构冻结成永久契约。

Node 使用 HttpCheck（engine=http），每项在全新服务内顺序执行 requests，当前只支持不带请求体的调用，可先执行无请求体 POST/DELETE 再 GET 验证状态变化。Nodebox 的请求体传输存在上游缺陷，带 JSON、表单或上传内容的接口目标返回 unsupportedGoal，不能静默改用查询参数绕过需求。检查真实状态码与 JSON/文本，不 mock 路由。请求均为相对路径，不依赖其他检查；精确 JSON 不包含不可预测时间。Vue/Svelte/静态页面优先用 UiCheck 操作真实预览，不要求 React App。

原生 JavaScript/TypeScript 的 ui_scenario 通过 UiCheck 操作实际预览，function_case 才通过 Jest 调用纯函数。测试函数导出或计算结果不能代替按钮点击、输入和显示更新；检查标题应与实际动作和断言一致。

UiCheck 的规范字段为 id、label、actions、可选 viewport，不需要 engine。不要从 JestCheck 或 HttpCheck 复制 engine 字段；这两种检查才分别使用 engine=sandpack-jest 和 engine=http。修复本步格式错误时，删除报错的多余字段，保留实际动作与断言。
