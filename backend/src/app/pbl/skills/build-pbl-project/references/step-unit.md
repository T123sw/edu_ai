# 每一步都是完整练习单元

模型制作的是一个项目中的增量练习，不是互不相关的多个代码沙箱。

## 输入

计划及其哈希、当前 step、前序步骤摘要、固定工程模板、当前步骤检查规格、私有前序参考快照、校验问题（修复时）。首步起点为初始工程，后续起点为上一步成果。生成材料时使用私有参考工程推演，不读取其他用户代码；实际学习时使用当前用户的工程。

## 输出包

| 部分 | 内容 | 可见性 |
| --- | --- | --- |
| `StepUnit` | stepId、title、objective、instructionsMarkdown、explanationMarkdown、hints、focusFiles、checkIds | 用户可见 |
| 检查包 | 稳定检查 ID、固定运行器支持的调用/点击/输入/断言、期望值、初始化规则 | 用户可看检查要求；执行权限归平台 |
| 累计参考快照 | 前序成果加本步实现的多文件映射 | 私有，用于生成期验证 |
| 负例 | 起始未实现状态、可选典型错误及检查 ID；可只提交修改的许可文件，其余继承参考工程 | 私有验证材料，不能充当真实报告 |

`StepUnit` 的字段约束和与计划的一致性由 `validate_step_unit(plan, payload)` 检查。`checkIds` 是本步新增检查；学习者点击“检查本步”时，由程序追加所有前序检查，而不是让模型决定哪些旧检查可以省略。

`instructionsMarkdown` 是前端原样展示的完整题面，不能用 `objective` 的一句话摘要代替。模型应使用学习者能理解的日常语言，先描述要做出的东西，再说明已有起点、页面组成或本步交互、完成效果和必要边界。不要用“渲染显示区”等技术措辞代替任务描述。按钮文字和初始状态放在可见要求中；检查依赖的 data-testid、role 等标识放到正文末尾独立的“代码约定”小节，解释它对应哪个页面部件、如何填写，以及只是供系统识别、不会改变外观。不能隐藏检查依赖的条件。通常采用少量短段落或条目，复杂要求可增加，不能省略关键条件。篇幅由模型组织，不由前端截断或规则摘要。

题面不重复标题、示例块、长篇原理、逐行编码教程和验收按钮操作指南。项目题不统一套用输入输出格式：前端展示本步 deliverable 和全部本步检查 label。deliverable 描述完整成果，label 描述可理解的具体要求，不能用技术选择器作标签。不能用局部状态代替整个步骤的成果。原理与做法放入 `explanationMarkdown`，提示放入 `hints`，不默认给出可复制的完整答案。布局步骤说明初始控件与状态，交互步骤说明操作和结果，不把未来步骤的功能提前当成本步要求。

完整格式以宿主 schema 为准，不从固定项目示例推导内容。运行 `validate_plan.py <plan.json> --step-unit <unit.json>` 检查二者一致性。

## 工程接续

- 平台提供并锁定依赖、入口、检查基础设施；模型不能生成安装命令后要求宿主随意执行。
- 初始工程只安装一次。后续切换步骤不把模型参考文件、标准答案或另一份 starter 覆盖到用户文件。
- 项目可能包含多个编辑文件，检查报告必须绑定全部参与构建的文件，而不只绑定当前打开的文件。
- 如确需在后续引入模板文件，必须由平台显式合并，并保留用户修改与冲突副本；首版优先在初始工程预置必要文件以避免这种迁移。
- 学生工程和私有参考快照分别保存；公开对象使用显式字段白名单，不能把整个模型候选直接下发。

## 检查规格转换

函数类检查对应固定导出调用、输入和预期；页面类检查对应干净页面起点、真实点击/输入与 DOM 可观察结果。参考实现通过后可采用检查包；负例未失败记录为质量提示，不阻断可运行成果。

`setup/actions/expected` 自然语言规格必须先转换成受支持的可执行检查，再运行验证；不能把这些文字当成已经执行的用例。可见、可用、可点击只证明对应状态与操作，不能证明布局要求完成。对于计划中的布局要求，必须生成 above/not_overlapping/within_viewport 等真实几何检查，并使用计划指定窗口。检查 label 不能承诺动作没有验证的能力（例如只点击按钮却宣称键盘聚焦已验收）。负例保留无关成果，只破坏当前某项要求，以验证对应检查确实能发现问题。业务行为由相应步骤的真实操作与结果检查证明。
